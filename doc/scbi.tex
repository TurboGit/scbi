\section{Introduction}

SCBI is a Source Code Build Infrastructure.

The goal is to automate the build procedures from sources. The main features are:

\begin{itemize}
	\item Allow recursive build of dependencies
	\item Building from a VCS (currently supported \emph{Git}, \emph{Subversion} and \emph{Mercurial})
	\item Supports build variants and auto-variants
	\item Supports for cross compilation
	\item Building a specific branch or tag
	\item Building from an archive
	\item Building from a user's checkout for easy debug with controlled environment
	\item Support for build plans (modules with specific variant and/or version)
\end{itemize}

The driver is written in Python (it needs \code{python3} and its YAML
module, \code{python3-yaml} on Debian); the plug-in modules are YAML files.

For developer of new plug-in modules in SCBI, all setup, source copy and installation are transparent actions, developers just need to fill the hooks to configure, build and install (generally just calling \code{configure} from \code{autotool} or \code{cmake} and \code{make}).

Those hooks are very close to what would have been typed when building manually from the command line. The goal is to reduce as much as possible the gap between a standard manual build and the commands used on plug-in modules.

When properly setup, building any software should be as easy as:

\cmd{scbi \ddash{}plan=ver mysoft}

We'll see how to achieve that in this document.

\section{Using}

\subsection{Module reference}
\label{modref}
\index{module reference}

A module is described in an SCBI plug-in script (one plug-in in one file). It can be referenced in different places (as dependency in other plug-ins, build plan, etc...) with the following format which is called a \emph{module reference}:

\code{[for\_module=]name[/variant][:version]}
\label{dev}

\begin{description}[style=nextline]
	\item[for\_module] The name of the plug-in depending on this plug-in reference. This is optional and can be used to select a specific variant or version when the plug-in \code{name} is used as a dependency on \code{for\_module}. When specified on a build plan it is possible to use an alternative syntax, see \code{@for} \seeref{formodule}.

	\item[name] The name of the plug-in. This is the main reference for the plug-in. The corresponding plug-in script must be named identically and located in \code{\$SCBI\_PLUGINS}.

	\item[variant] \label{variant}This is a name to identify a build variant for the module. For example an application can be built with different configuration and or dependencies.

	\begin{description}[font=\texttt]
		\item[<ID>] The variant name. This will trigger specific hook routines from the plug-in scripts.

		\item[native] \index{variant!native}A variant name that can be defined to use the distribution package. This name \code{native} is mandatory in this case and requited when using the \code{auto} mode (see below). When a \code{native} variant is referenced the \code{build-depends} hook is not used (\seeref{native variant}).

		\item[auto] \index{variant!auto}A specific variant name which checks the dependencies of the defined \code{native} variant and use it if all dependencies are available (not necessary installed). The \code{auto} variant should not be defined in a plug-in script but only used in references. The \code{native} and \code{auto} variant can be used together to build a package or use the native one depending on the availability of the dependencies on the running OS. If used together with other variants, the \code{auto} variant must be the first one in the module reference, that is just after the slash. For example:

		\code{module/auto.fast:v1.3}

		Finally, the \code{auto} variant can only be defined in a build plan or on the command line.

		\item[@] \index{variant!@}This is only available on the command line. To specify that the actual variant is the one described in the build plan. If not defined in the build plan, then the \code{default} variant is used as if it was not specified.
	\end{description}

	\item[version] The version to build. This version string can be either:

	\begin{description}[font=\texttt]
		\item[<ID>] A reference to a VCS version (branch or a Git SHA-1 for example), or an archive version when starting with \#.
		\item[dev] \index{version!dev}To take the source from a user's checkout.
		\item[keep] \index{version!keep}To specify that the module sources should not be updated. So the \emph{setup, }\emph{configure}, \emph{build}, \emph{install} and \emph{wrapup} steps are not conducted and the module's will keep its current status as it was built last time. If the module didn't get built yet the \emph{keep} status is ignored.
		\item[skip] \index{version!skip}To specify that the module must be completely ignored. It is as if the plug-in was not present in the dependencies.
		\item[force] \index{version!force}To enable an otherwise skip module (possibly set to \emph{skip} in a build plan).
		\item[@] \index{version!@}This is only available on the command line. To specify that the actual version is the one described in the build plan. If not defined in the build plan, then the default version is used (e.g. \code{master} for Git) as if it was not specified.
	\end{description}

	The version can be set to \code{force} on the command line to tell that the plug-in should not be skipped. On the command line it is always possible to force a build of a module to a specific variant and/or version. But if one need to build the default variant or version it is required to pass the \code{force} as version.

	That is, the following command will never overwrite a build plan as it is a default reference to a plug-in:

	\cmd{scbi --plan=xyz mod}

	But this will do:

	\cmd{scbi --plan=xyz mod:force}
\end{description}

The following are examples of module references:

\begin{description}[style=nextline]
	\item[lcms2] Build \code{lcms2} from repository main (master/trunk) branch.

	\item[lcms2/fast] Build \code{lcms2} \emph{fast} variant from repository main (master/trunk) branch.

	\item[gimp=lcms2/slow] When a direct dependency of project \code{gimp}, build \code{lcms2} \emph{slow} variant from repository main (master/trunk) branch.

	\item[lcms2:v2.0] Build \code{lcms2} from repository using branch (or tag) \emph{2.0}.

	\item[lcms2/fast:v2.0] Build \code{lcms2} \emph{fast} variant from repository using branch (or tag) \emph{2.0}.

	\item[lcms2/@:v2.0] Build \code{lcms2} using the variant as defined in the build plan and from repository using branch (or tag) \emph{2.0}.

	\item[lcms2:bfaf7b82ed] Build \code{lcms2} from repository using sources from SHA-1 \emph{bfaf7b82ed} (Git only).

	\item[lcms2:\#v1.0] Build \code{lcms2} using sources from archive version \emph{1.0}.

	\item[lcms2:dev] Build \code{lcms2} using sources from user's repository checkout found in \code{\$SCBI\_GIT\_REPO} (assuming \code{lcms2} is using Git). For a discussion about user's check-out \seeref{userco}.

	\item[lcms2:skip] Skip \code{lcms2} from the build. This is especially useful when set on a build plan or the command line to specify that the plug-in is to be ignored.
\end{description}

\subsection{Environment}
\label{build-env}
\index{environment}

An environment is a set of shell variables used to control the build environment. SCBI comes with defaults that can be used as-is, but one can fine tune the build environment using the following variables.

\subsubsection{Description}

\begin{description}[before=\let\item\myitem]
	\item[SCBI\_DEFAULT\_ENV] The scbi default environment file to use.

	\item[SCBI\_ENV\_DIR] The directory from where the environment file has been loaded.

	\item[SCBI\_VERSION] The scbi driver version string.
	\\This version is \version.

	\item[SCBI\_PLUGINS] The directories where the SCBI plug-ins are located.
	Default is \file{\$HOME/.config/scbi}.

	\item[SCBI\_PLAN] The name of the build-plan to use if any.

	\item[SCBI\_ROOT] The default root directory to use by SCBI. \\
	Default is \file{\$HOME/dev}.

	\item[SCBI\_BDIR] The default directory for the build directory.  This is also called the sandbox directory. \\
	Default is \file{\$SCBI\_ROOT/builds}.

	\item[SCBI\_MODULES\_DIR{[<module-name>[@src|@build]]}] An associative array giving the \emph{install}, \emph{source} or \emph{build} directories for a given module name and variant. It is possible to get the \emph{source} and \emph{build} directories by adding respectively \code{@src} and \code{@build} at the end of the \code{<module-name>}. For example \code{SCBI\_MODULES\_DIR{[<module-name>@src]}} points to the source directory and \code{SCBI\_MODULES\_DIR{[<module-name>@build]}} point to the build directory. This associative array can be used in hooks \code{config}, \code{build} and \code{install}.

	\item[SCBI\_CACHE\_DIR] A variable pointing to the build's cache dir. Setting this variable to \emph{no} disables the cache. The cache makes it possible to reuse a previous build instead of rebuilding a module. Default is \file{\$HOME/.cache/scbi}.

	\item[SCBI\_PROGRESS] \index{progress}When the output is a terminal,
	\code{scbi} shows the progress of the build, \code{[<n>/<total>]
	<module>}: the module being handled and the number of modules to
	handle (with \ddash{}deps, all the dependencies). It is never written
	to the logs. The values are:
	\begin{description}
		\item[line] (default) a transient line after an empty line, at the
		end of the output, redrawn after each output line and erased at
		the end;
		\item[bar] a status bar on the last row of the terminal (the
		output scrolls above it) with also the time elapsed since the
		start of the build, refreshed every second;
		\item[no] no progress (also with \ddash{}quiet).
	\end{description}

	\item[SCBI\_PREFIX] The default global install directory. Each module after being installed into the sandbox are copied into this global installation directory. \\Default is \file{\$SCBI\_BDIR/install}. Each module can disable global installation (\seeref{global-install}).

	\item[SCBI\_GIT\_REPO] The directories where the user's Git checkouts are to be found. \\ Default is \file{\$SCBI\_ROOT/repositories/git}.

	\item[SCBI\_SVN\_REPO] The directories where the user's Subversion checkouts are to be found. \\ Default is \file{\$SCBI\_ROOT/repositories/svn}.

	\item[SCBI\_HG\_REPO] The directories where the user's Mercurial checkouts are to be found. \\ Default is \file{\$SCBI\_ROOT/repositories/hg}.

	\item[SCBI\_ARCHIVES] The directories where the archives are located. \\Default is \file{\$SCBI\_ROOT/.archives}.

	\item[SCBI\_LOGS] The directories where the logs are located. \\Default is \file{\$SCBI\_ROOT/.logs}.

	\item[SCBI\_PATCH] The directories where the patches are located. \\Default is \file{\$SCBI\_ROOT/.patches}.

	\item[SCBI\_HOST] The host triplet identifying the running environment.

	\item[SCBI\_TARGET] The target triplet for the builds. \\Default is \code{\$SCBI\_HOST}.

	\item[SCBI\_JOBS] The number of simultaneous jobs to use to build. This variable is to be used in module scripts. \\Default set to actual number of cores. This can be overwritten using \code{--jobs} option.
	\label{njobs}
	\item[SCBI\_HALF\_JOBS] Half the simultaneous jobs to use to build. This variable is to be used in module scripts. \\Default set to actual number of cores divided by 2. This can be overwritten using \code{\ddash{}jobs} option.\label{half-njobs}
\end{description}

\subsubsection{Environment files}
\label{envfile}
\index{environment!file}

The environment can be set in the following files (Python files,
\seeref{python-env-files}) searched in this exact order:

\begin{description}
	\item[\code{\$PWD/.scbi-env.py}] The local environment found in the current working directory.

	\item[\code{\$PWD/../.scbi-env.py}] The local environment found in the parent of the working directory. This environment can then be shared for a set of repositories.

	\item[\code{\$HOME/.scbi-env.py}] The local environment found in the HOME. This environment can then be shared by all builds.

	\item[\code{\$SCBI\_PLUGINS/.env.py}] The default global environment used for all builds.
\end{description}

Also note that instead of the default \file{.env.py} (or \file{.scbi-env.py} for local environment files) a specific environment file can be specified with the \code{\ddash{}env=<name>} command line option (\file{.env-<name>.py}, \seeref{cmdline}).

Example, to use environment \file{.env-next.py} to build \code{lcms2}:

\cmd{scbi \ddash{}env=next lcms2}

Or using an environment variable:

\cmd{export SCBI\_DEFAULT\_ENV=next}

\cmd{scbi lcms2}

\subsection{Discriminants}
\label{discriminants}
\index{discriminants}
\index{plan|discriminants}

A list of discriminants are generated for each build. Those discriminants can be used in barrier (\seeref{plan-barrier}). The discriminants are host and target specific and can be used to tune build plans.

The discriminant list contains:

\begin{itemize}
	\item The hostname,
	\item The domain name,
	\item The OS (e.g. \code{windows}, \code{linux})
	\item The OS name (e.g. \code{debian})
	\item A 3 letters acronym for the OS name (e.g. \code{deb}, \code{fed})
	\item The OS major version,
	\item The OS code name,
	\item The architecture (i.e. \code{x86\_64}, \code{i686}),
	\item For cross configuration the \code{cross} discriminant and each part of the target triplet prefixed with \code{target-} (e.g. \code{target-mingw32}, \code{target-arm})
\end{itemize}

Use option \ddash{}stat to see the list of discriminants for the running machine.

\subsection{Build plans}
\label{build-plan}
\index{build plan}

A build-plan is a file listing for each module a specific version to build. It is equivalent to list all versions on the command line:

\cmd{scbi lcms2:v2 aws:v1}

But it is preferable to use a build plan to ensure a reproducible build and have all information properly recorded into a version control for example.

A build-plan is a file named \file{.plan-<name>} and listing the versions (\seeref{modref} about module references) for each software:

File \file{.plan-next}:
\begin{lstlisting}
 lcms2:v2
 aws:v1
\end{lstlisting}

A version specified for a meta-module is propagated to all aggregated modules and recursively to all aggregated meta-modules by default see \ref{propagate-version}. Note that this specification is \emph{soft}, meaning that it won't override any specific version specified for a module anywhere in the build plan or on the command line.

Some specific actions are supported with the following syntax:

\begin{description}
	\item[\code{\#}] To start a comment line.

	\item[\code{@load <name>}] To load another build-plan as a base for the new plan. Every descriptions after this will overwrite the loaded build plan.

	This is a simple way to derive a build plan from another one.

	File \file{.plan-next}:

	\begin{lstlisting}
		# the next line will load build plan standard
		@load standard
		lcms2:v2
		aws:v1
	\end{lstlisting}

	\item[\code{@set <variable-name> = <value>}] To set a variable to the specified \code{value} that can be referenced later in the plan using \code{\$<variable>} or \code{\$\{<variable>\}}. This make it possible to share a version for a set of related plug-ins for example.

	\begin{lstlisting}
		@set VERSION = v2
		@set VARIANT = fast

		module1/$VARIANT:$VERSION
		module2:$VERSION
	\end{lstlisting}

	\item[\code{@ref <m2> as <m1> [version <pattern>]}] To propagate a variant/version from another module.

	\begin{lstlisting}
		module1/var:1.2
		@ref module2 as module1
	\end{lstlisting}

	Here \code{module2} will use the variant and version of \code{module1}. The above plan is equivalent to:

	\begin{lstlisting}
		module1/var:1.2
		module2/var:1.2
	\end{lstlisting}

	But this may come handy when inheriting of a plan to set reference of a plug-in inheriting from another one.

	On can also use a \code{pattern} to create the module1 version from module2 version. The pattern can be composed of 3 parts: \code{<prefix>/<regpat>/<suffix>}.

	\begin{description}
		\item[prefix] If present, a simple string that will be added as prefix.
		\item[regpat] A regular expression pattern where the first and second match will be use for creating the final version.
		\item[suffix] If present, a simple string that will be added as suffix.
	\end{description}

	\begin{lstlisting}
	module1/var:1.2.3
	@ref module2 as module1 version v/[0-9].[0-9]/
	\end{lstlisting}

	Here \code{module2} will use the variant of \code{module1} and the version starting with \code{v} followed by the major and minor version of \code{module1}. The above plan is equivalent to:

	\begin{lstlisting}
		module1/var:1.2.3
		module2/var:v1.2
	\end{lstlisting}

	\item[\code{@on <discriminants> use <module-reference>}] To set a module reference only if the running OS is matching the discriminants (\seeref{discriminants}). If all discriminants are matching the module reference will overwrite previous definitions.

	\begin{lstlisting}
	#  Skip lcms2 on Debian-9
	@on deb,9 use lcms2:skip
	#  Use v2 of lcms2 on Fedora
	@on fed use lcms2:v2
	\end{lstlisting}

	\item[\code{@for <plug-in> use <modref>}] To specify a specific variant and/or version of a plug-in when used as dependencies of a specific module.
	\label{formodule}

    \begin{lstlisting}
	@for c-darktable use c-exiv2/auto:v0.27.5
    \end{lstlisting}

	\item[\code{@alias <plug-in1> use <plug-in2>}] To set an alias for modules in dependencies. If \code{<plug-in1>} is not found while looking at dependencies then \code{<plug-in2>} will be tried. This may be handy to propose a public alternative to some private plug-in.

	\begin{lstlisting}
	@alias private-plugin use alternative-plugin
	\end{lstlisting}

	\item[\code{[ <barrier> ... ] /variant:version}] To create a group. The barrier if present must evaluate to true or the group is ignored.

	A group can be used in a build plan to group together all modules with the same version and/or variant. To define a group:

	\begin{description}
		\label{plan-barrier}
		\item[ {[} <barrier>] Start with a square bracket and an optional barrier. The barrier is a condition starting with \code{=} or \code{/=} and the name of a \code{variant} or \code{discriminant} (\seeref{discriminants}).

		\code{\ddash{}plan=name/variant1.variant2}

		The barrier can have multiple variants or discriminants separated with a comma:

		\code{= deb,9}

		All of them must be set for the barrier to be true.

		Finally the barrier can have three groups of values. For a \code{=} condition only one of the group can match (OR) for the barrier to evaluate to TRUE. For a \code{/=} condition all groups must match (AND) for the barrier to evaluate to TRUE. Examples:

		\begin{itemize}
		\item {[} = deb,9 deb,11

		Will be true on GNU/Debian 9 and 11.

		\item {[} /= deb,9 deb,11

		Will be true on all versions of GNU/Debian except version 9 and 11.

		\end{itemize}

		The group will be evaluated only if the barrier evaluate to true otherwise it will be skipped. If the barrier is not specified the group will always be evaluated (i.e. the barrier is by default TRUE).

		\item[ {]} /variant:version ] Ends with \code{/variant:version} which is the variant and version to apply to all modules in the group. Both \code{variant} and \code{version} are optional.
	\end{description}

	Without a barrier, will always be open:

	\begin{lstlisting}
		lcms2:v2
		[
			moduleA
			moduleB
		] /speed:v3
	\end{lstlisting}

	With a barrier based on a variant (will be open if the build plan is for example \code{\ddash{}plan=name/variant1.variant2}):

	\begin{lstlisting}
		lcms2:v2
		[ = variant1
			moduleA
			moduleB
		] /speed:v3
	\end{lstlisting}

	With a barrier based on discriminants (will be open on Debian 10):

	\begin{lstlisting}
		lcms2:v2
		[ = deb,10
			moduleA
			moduleB
		] /speed:v3
	\end{lstlisting}
\end{description}

And finally, to build one just need to pass the build plan as option:

\cmd{scbi \ddash{}plan=next lcms2 aws}

Note that if a module is set as \code{skip} on the build plan, to build the default version one need to force it on the command line:

\cmd{scbi \ddash{}plan=next lcms2:force aws}

A set of variants separated with a dot can be specified with the build plan. In the following example we set the \code{mpi} variant of the build plan \code{next}. This will activate all groups having the following barrier "\code{= mpi}".

\cmd{scbi \ddash{}plan=next/mpi lcms2:force aws}

It is possible to list the final build plan (that is all modules with their corresponding version) using \code{\ddash{}list-plan} option. See \ref{cmdline}.

A build-plan can be set in the following files searched in this exact order:

\begin{description}
	\item[\code{\$PWD/.scbi-plan-<name>}] A local build plan found in the current working directory.

	\item[\code{\$SCBI\_PLUGINS/.plan-<name>}] A global build-plan.
\end{description}

\subsection{Standalone source archive}
\label{standalone}
\index{source archive}

Using the \code{\ddash{}standalone} option it is possible to build a fully self contained source archive. This archive embed all necessary sources and scripts to rebuild the software without the need to get access to repositories or source archive files.

On the root of the archive a build script is provided, so starting a build from such standalone source archive boil done to:

\begin{description}
	\item[Uncompress] \cmd{tar xf sa-archive.tgz}
	\item[Enter the directory] \cmd{cd sa-archive}
	\item[Start the build] \cmd{./build}
\end{description}

By default the archive is created into \code{/tmp}, but it is possible to change the location setting the \code{SCBI\_TMP} environment variable. This may be needed as such archive can be very large.

The file \code{build-deps} is generated into the root directory and contains the \code{apt} command with all external (OS) dependencies needed to build the software.

\subsection{Command line}

\subsubsection{Description}

The SCBI command line:

\cmd{scbi [command] [options] module-ref1 [module-ref2 ... module-refn]}

For a description of the module reference, \seeref{modref}.

It is possible to list the module currently supported by running \code{scbi} with \code{\ddash{}help} or \code{\ddash{}stat} option or with \code{[TAB]} key if completion support is activated (\seeref{completion}).

\subsubsection{Commands}
\label{cmdline}

A set of sub-commands are available:

\begin{description}
	\item[show] To display plan, dependencies and module's reference. (\seeref{show}).

	\item[shell] To enter a shell or run a command with an environment for a plug-ing. (\seeref{shell}).

	\item[store] To handle the SCBI's Private Store. (\seeref{store}).

	\item[lint] To check plug-ins syntax and report some possible errors. (\seeref{linter}).

	\item[source-archive] To create a source archive from the VCS described in plug-ins. (\seeref{createsourcearchive}).
\end{description}

\subsubsection{Options}
\label{cmdline}

The following options are supported:

\begin{description}[font=\texttt]
	\item[-h | \ddash{}help] List options and usage information.

	\item[-v | \ddash{}version] Display version information of the SCBI driver and versions from plug-ins distributions coming from other sources\footnote{Note that for this to be supported the plug-ins distribution must have generated and installed a file name \file{.scbi*version.txt} next to the plug-ins.}.

	\item[-q | \ddash{}quiet] Do not display the information logs.

	\item[\ddash{}color:{[}no|light|dark{]}] Enable colored output for \code{light} or \code{dark} console background. The default is \code{no}.

	\item[\ddash{}ini{[}=<section>{]}] Load the ini file given \code{section}. If no section given the global/common values are used.

	\item[\ddash{}prefix=<dir>] The installation directory to use instead of the default \file{\$SCBI\_PREFIX}.

	\item[\ddash{}build-dir=<dir>] The root build directory to use instead of the default \file{\$SCBI\_BDIR}.

	\item[\ddash{}flat] Use a flatter directory structure in the sandbox. The actual directory for building the module will be moved at the top of the build directory into the sandbox and will be named using a simple number. This option may come handy on Windows to avoid too long path-name due to OS limitation.

	\item[-e | \ddash{}env=<name>] Use environment file \code{.env-<name>} instead of the default \code{.env}. (\seeref{build-env})

	\item[\ddash{}plan=<name>{[}/variant{]}] Use build plan file \code{.plan-<name>}. (\seeref{build-plan}) with an optional \code{variant}.

	\item[\ddash{}enable-<name>] Enable feature \emph{name}, (\seeref{enable-feature}).

	\item[-t | \ddash{}target=<name>] Specify the target to build for, the default is same as the host. This is needed for cross-compilation only.

	\item[-S | \ddash{}no-setup] Skip the setup step.

	\item[-W | \ddash{}no-wrapup] Skip the wrapup step.

	\item[-I | \ddash{}no-install] Skip the install step.

	\item[-u | \ddash{}update] Update the repositories before building.

	\item[-s | \ddash{}setup] Do the setup step (default)

	\item[-c | \ddash{}config] Do the config step (default)

	\item[-b | \ddash{}build]  Do the build step (default)

	\item[\ddash{}build-target=<target>] \index{build-target}The build step
	runs the \code{build-<target>} hook of the module instead of
	\code{build} (see \emph{Hooks}).

	\item[-i | \ddash{}install] Do the install step (default)

	\item[\ddash{}clean-install] Clean installation directory

	\item[\ddash{}clear-cache] Clear the module's plan cache to force a full recomputation of auto module and meta-module module plan propagation. This is done automatically in many cases but some are not possible or too costly to detect automatically. The case taken into account are:
	\begin{itemize}
		\item Plan has changed (name and/or content),
		\item Some packages have been installed/removed from OS using \code{apt}, \code{dnf}, \code{pacman},
		\item Some OS discriminants have changed (name, version, etc.),
		\item The modules passed on the command line have their reference changed,
		\item The build target has changed.
	\end{itemize}

	\item[-w | \ddash{}wrapup] Do the wrapup step (default).

	\item[\ddash{}archive] Check for archives only if explicitly specified in the module reference. If this option is not specified an archive for the plug-in will be search into the archive cache directory (\file{\$SCBI\_BDIR/.archives}).

	\item[\ddash{}tests{[:only]}{[=OPTIONS]}] Do a standard build cycle and run the testsuite if any. If suboption \code{only} is specified only run the testsuite (no build is checked/done). The optional OPTIONS parameters is passed as 4th parameter of the tests hook (\seeref{tests-hook})

	\item[-d | \ddash{}deps{[:warning]}] Check all dependencies and build them if necessary. Do not fail when a missing external dependencies is found when sub-option \code{warning} is set.

	\item[-a | \ddash{}create-archive] Build binary archive when build is successful.

    \item[\ddash{}standalone] Create a standalone source archive

	\item[-l | \ddash{}log:{[}yes|no|on-failure{]}] Control the log level to display. The default is \code{on-failure} which displays the command log only in case of failure.

	\item[-f | \ddash{}force] Do not check if build id is matching, force a rebuild.

	\item[-p | \ddash{}purge{[:only]}] Remove module build directory, then if \code{only} is not specified build the module. The simple \code{-p} option corresponds on \code{--purge}.

	\item[\ddash{}dry-run] Only list modules to be handled.

	\item[\ddash{}stat:{[}short|full{]}] Display some statistics about current setup. With sub-option \code{short} only displays the environment status. With sub-option \code{full} also gives stats about module's build time.

	\item[-n | \ddash{}no-patch] Do not apply patches.

	\item[-j | \ddash{}jobs=<n>] Max compilation jobs, set variable \code{SCBI\_JOBS} which can be used in module scripts. (\seeref{njobs}).

	\item[\ddash{}safe] Build in safe mode. If a module needs to be built the previous build directory is removed. This ensures that the old configuration and/or build artifacts won't interact in any way with new build.

	\item[\ddash{}plugins=<directory>] Specify a non default location for the modules and plug-ins directory. This overrides the \code{SCBI\_PLUGINS} environment.
\end{description}

A completion support for bash is provided. If activated many options will give hints about possible values like listing plans for \code{\ddash{}plan=} option or listing the supported modules.

\subsubsection{Options from INI file}
\label{inifile}

An ini file can be used to store options to be used. Such file contains sections. The sub-option given to \code{\ddash{}ini} option is the section to be activated. Also the \code{common} section is always activated and takes precedence over the global settings. A sub-command will also use the section named \code{scbi-<sub-command>} making it possible to have specific setting for sub-commands.

The global settings, first in the file and so not in a specific section, are always used.

The searched ini files are:

\begin{itemize}
	\item \$HOME/.scbi
	\item \$PWD/.scbi
	\item \$SCBI\_INI\_FILE
\end{itemize}

The following options are supported in the ini file:

\begin{itemize}
	\item env, plan, target
	\item root-dir, plugins, prefix, build-dir
	\item git-repo, svn-repo, hg-repo
	\item jobs, archive, patch
	\item setup, config, build, install, wrapup
	\item force, update, purge, archive
	\item modules (list of modules as passed on command line)
	\item enable (list of features)
	\item options (specific options as passed on command line)
	\item run (specific command line to run)
	\item tests (yes, only), tests-list (list of tests to pass)
\end{itemize}

All other options are set as exported variables.

Example:

\begin{lstlisting}[language={Ini}]
prefix = $HOME/sandbox

[aws]
   env = std
   modules = c-aws

[common]
   git-repo = $HOME/dev/git
   jobs = 2

[scbi-show]
   stat = no
\end{lstlisting}

\section{Creating new plug-ins}

To create a new plug-in for SCBI you need to create a single YAML file
(one per module) into \code{\$SCBI\_PLUGINS}, named
\file{<plug-in>.yaml}.

The plug-in describes, using different hooks, the steps for building. One for configuring, one for building and one for installing. These are the mains steps generally used to build all software.

The steps are described by a few commands (the command language,
\seeref{yaml-command-language}). And some hooks are just descriptions to retrieve artifacts (like VCS sources or archive file).

The format of the file is described first, then all the supported hooks
and the calling order conducted by SCBI.

\subsection{Plug-in format}
\label{yaml-plugin}
\index{YAML plug-in}

A plug-in is a YAML file named \file{<name>.yaml}. It is a recipe: it is
only read by the driver.

\subsubsection{Structure}

The file is a mapping. The following keys are reserved, all the other ones
are hook names (including \code{pre-<step>} and \code{post-<step>}):

\begin{description}[font=\texttt]
	\item[plugin] The plug-in name, optional, must match the file name.
	\item[vars] Global variables, \code{\{NAME: value\}}.
	\item[variants] Variants including other variants
	(\seeref{yaml-variants}), \code{\{all: [ai, hdr, jxl]\}}.
	\item[inherit] List of inherited plug-ins (\seeref{inheritance}), each
	one a mapping with the keys \code{from}, \code{hooks},
	\code{custom-hooks}, \code{no-variant} and \code{name}.
	\item[with-variants] Variants with no build step, which only depend on
	other modules or OS packages (e.g. a \code{native} variant using the OS
	libraries, \seeref{native variant}):
	\code{\{native: \{packages: [...], env: [...]\}\}}.
	\item[functions] Custom functions callable from the other hooks (or used
	as custom hooks for \code{inherit}): \code{\{name: \{params: [A, B], run: <shell>\}\}}.
\end{description}

All scalars are strings: \code{yes}, \code{no}, \code{true} or
\code{1.10} are never converted to booleans or numbers.

\subsubsection{Hooks and variants}

The value of a hook is either its body (the plain hook) or a mapping where each key names \emph{exactly one} qualifier:
\code{\_} (the plain hook), \code{common} (cumulative hooks only),
\code{default} or a variant name. The key \code{cross} holds the same kind of
mapping (or directly a body) used when the target is not the host. There is
no key combining variants: for a module reference \code{m/a.b} the driver
takes the first defined variant for the hooks like
\code{config} or \code{install}, and all of them for the cumulative hooks
like \code{depends} or \code{config-options}.

\begin{lstlisting}
plugin: c-gmp
with-variants:
  native:
    packages: [os@-gmp-dev:[v]]
    env: [set-var GMP_INCLUDE_DIR /usr/include]
vcs:
  proxy: default
  options: none
  protocol: mercurial
  url: https://gmplib.org/repo/gmp/
build-depends: [c-sandbox]
depends:
  vcs: [os@-autotools-dev, os@-automake]
env:
  - add-to-var C_INCLUDE_PATH $PREFIX/include
  - add-to-var LD_LIBRARY_PATH $PREFIX/lib
out-of-tree: false
config:
  _: ./configure --prefix=$PREFIX
  vcs: ./configure --enable-maintainer-mode --prefix=$PREFIX
  cross:
    _: ./configure --prefix=$PREFIX/$TARGET --host=$TARGET
build: make -j$SCBI_JOBS
install: make install
\end{lstlisting}

\subsubsection{Variants including other variants}
\label{yaml-variants}
\index{YAML plug-in!variants}\index{variant!including variants}

A variant can be defined as including other variants, to share their
definitions without repeating them:

\begin{lstlisting}
variants:
  all: [ai, hdr, jxl]
\end{lstlisting}

When looking for the hooks of the module reference \code{c-darktable/all}
the driver uses the variants \code{all ai hdr jxl}, in this order: each
variant is followed by the variants it includes (recursively), a variant
already listed is not repeated. So \code{all} gets the \code{depends} of
\code{ai}, \code{hdr} and \code{jxl} (cumulative hook) and, for a hook like
\code{config}, the first one defined for \code{all}, \code{ai}, \code{hdr}
or \code{jxl}. A hook defined for \code{all} itself is still used.

Only the hooks lookup is affected: the variant keeps its name for the
sandbox directory, the build identifier, the logs and the build plans.

\subsubsection{Hook bodies}

The parameters of a hook are defined once for all by SCBI (for example
\code{PREFIX TARGET VARIANT} for \code{config}, \code{VERSION} for
\code{archive}, \code{PREFIX TARGET VARIANT KIND REF} for \code{patches},
\code{PREFIX TARGET VARIANT OPTIONS} for \code{tests}) and are available as
variables in the body; they are not declared in the plug-in.

\begin{description}
	\item[command hooks] (\code{setup}, \code{config}, \code{build},
	\code{install}, \code{wrapup}, \code{tests}, \code{version}, \code{run}
	and the \code{pre-}/\code{post-} steps): a body in the command
	language (\seeref{yaml-command-language}), run by the driver without
	any shell. A syntax error is reported when the plug-in is loaded,
	with the line in the file.
	\item[value hooks] (\code{vcs}, \code{archive}, \code{depends},
	\code{patches}, \code{config-options}, \code{prefix}, \code{out-of-tree}...):
	a list of values, one per line of output (a single value can be given as a
	string). \code{vcs} and \code{archive} can also be given as a mapping of
	their fields (\code{proxy}, \code{options}, \code{protocol}, \code{url},
	\code{file}, \code{dir}).
	\item[environment hooks] (\code{env}, \code{build-env},
	\code{tests-env}): a list of actions \code{<verb> <arguments>} where the
	verb is one of \code{add-to-var}, \code{prepend-to-var},
	\code{append-to-var}, \code{remove-from-var}, \code{set-var},
	\code{define-var}, \code{unset-var}, \code{export}, \code{system-compiler},
	\code{target-env}, \code{no-target-env}, \code{mkdir}, \code{import}
	(\code{import opam env} runs the command, without a shell, and applies
	the variable assignments, \code{export} and \code{unset} statements it
	prints),
	\code{local NAME VALUE} (a variable for the following actions of the hook)
	or \code{assign NAME VALUE} (a shell variable, part of the environment if
	it is already exported). Actions are applied in order. The actions on
	variables go through the \code{define\_var} of the Python environment
	file, if any (\seeref{python-env-files}).
\end{description}

Values and environment actions are not shell code: they may only refer to
variables (\code{\$VAR}, \code{\$\{VAR\}}, with the suffix and prefix
removal forms \code{\$\{VAR\%pattern\}}, \code{\$\{VAR\%\%pattern\}},
\code{\$\{VAR\#pattern\}}, \code{\$\{VAR\#\#pattern\}}, the replacement
forms \code{\$\{VAR/pattern/string\}} (first match) and
\code{\$\{VAR//pattern/string\}} (all matches, \code{\textbackslash/} is a
\code{/}), and \code{\$\{VAR:+word\}}, \code{word} when the variable is
not empty), to
\code{\$\{SCBI\_MODULES\_DIR[<module>[@src|@build]]\}} and to the
following functions (the arguments are expanded as in a shell, including
unquoted glob patterns):
\code{\$(get-version)}, \code{\$(get-build-type <kind> <default>)},
\code{\$(is-enabled <feature> [then] [else])},
\code{\$(last-modified-directory <glob>)}, \code{\$(get-os-inc-dir <glob>)},
\code{\$(get-os-lib <file>)}, \code{\$(get-os-lib-dir <file>)} (a
library of the system, as \code{serial/libhdf5.so}, and its directory),
\code{\$(get-os-bin <program>)}, \code{\$(get-os-bin-dir <program>)} (a
program of the system and its directory),
\code{\$(command-path <tool>)} (the tool found in \code{PATH}, empty when
none, as \code{command -v}), \code{\$(store-key <key>)} (the value of
the key in \file{\$SCBI\_PLUGINS/.store}, lines \code{<key> <value>}),
\code{\$(output <command> <args>)} (the standard output of the command,
run without shell),
\code{\$(basename <path>)}, \code{\$(dirname <path>)}, \code{\$(ls <glob>)}, \code{\$(uppercase
<words>)} and \code{\$(lowercase <words>)}. A default value is given
with \code{\$\{VAR:-default\}}.

\index{if (in values)}
\code{\$(if <condition> then <words> [else <words>])} gives the words after
\code{then} when the condition is true, else the words after \code{else}
(nothing when there is no \code{else}). The condition is written as the
guards of the list items (\seeref{yaml-conditions}); \code{then} and
\code{else} are keywords only outside quotes and parentheses.

\index{local variable (in values)}
An item \code{NAME = <value>} of a value hook or of an environment hook
sets a variable for the following items of the hook (it gives no value
and is not part of the environment). The value is the result of a
function when it starts with one (\code{BT = get-build-type CMAKE
Release} is \code{BT = \$(get-build-type CMAKE Release)}), else a text
expanded as a value. For example:

\begin{lstlisting}
config-options:
  - BT = get-build-type CMAKE Release
  - -DLLVM_ENABLE_ASSERTIONS=$(if $BT == Debug then ON else OFF)
  - -DOPT=$(uppercase $VARIANT)
\end{lstlisting}

The same result without a variable:
\code{-DLLVM\_ENABLE\_ASSERTIONS=\$(if build-type(CMAKE,Release) == Debug
then ON else OFF)}.

\subsubsection{Command language}
\label{yaml-command-language}
\index{YAML plug-in!command language}

The command hooks and the functions of a YAML plug-in are written in a
small command language interpreted by the driver: no shell is involved.
External commands are run as processes with the environment of the hook,
built-ins are part of the driver. A body is a text block, one step per
line; \code{\#} starts a comment, blank lines are ignored, a line ending
with \code{\textbackslash} continues on the next one. Blocks are given by
indentation:

\begin{lstlisting}
config: |
  BT = get-build-type CMAKE Release
  if not is-link(../src/.git):
      ln -s ../../src/.git ../src/.git
  if cross:
      cmake -DCMAKE_BUILD_TYPE=$BT -DTARGET=$TARGET $(config-options) ../src
  else:
      cmake -DCMAKE_BUILD_TYPE=$BT $(config-options) ../src
version: |
  write prj.gpr:
      with "aunit";
      project prj is end prj;
  if ok("gprbuild -p -q $(if cross then --target=$TARGET) prj.gpr 2> /dev/null"):
      echo $VERSION_OK
  else:
      echo $VERSION_ERROR
\end{lstlisting}

\begin{description}
	\item[commands] The words are split as by a shell (quotes, backslash)
	and expanded by the driver: variables and their forms (see above),
	\code{\$(<function> args)}, unquoted glob patterns (left as they are
	when nothing matches). A variable holding a list gives a word per
	element, other values are never split, an unquoted word expanding to
	nothing is removed. Leading \code{NAME=value} words set the
	environment of the command only. \code{\&\&}, \code{||}, pipes
	\code{|} and the redirections \code{>}, \code{>>}, \code{<},
	\code{2>}, \code{2>>}, \code{2>\&1}, \code{\&>} work as in a shell.
	\item[assignments] \code{VAR = <words>} sets a variable of the hook
	(one word: a value, several: a list); \code{VAR = <function> <args>}
	sets it to the result of a function (see \emph{Functions} below).
	Variables are local to the hook call; \code{export VAR = ...} also
	sets it in the environment of the following commands.
\end{description}

\textbf{Functions.} \index{YAML plug-in!functions of commands}
A function gives a value or a list. It is used in an assignment,
\code{VAR = <function> <args>}, or in the words of a command as
\code{\$(<function> <args>)}, which gives the same value: an unquoted
word made of the call only gives one word per element of a list (an
element with spaces stays one word, an empty result no word), otherwise
the elements are joined with spaces, e.g. \code{cmake \$(config-options)
../src} or \code{echo \$(uppercase \$VARIANT)}. A call cannot be nested
in \code{\$(if ...)}.

\begin{description}
	\item[config-options] the list of the values of the
	\code{config-options} hooks of the module for its variant.
	\item[get-build-type <kind> <default>] the build type of the module:
	\code{SCBI\_<module>\_BUILD\_TYPE}, else
	\code{SCBI\_<kind>\_BUILD\_TYPE}, else \code{<default>}.
	\item[get-version] the version of the module in the build plan.
	\item[is-enabled <feature> {[<then>]} {[<else>]}] \code{<then>}
	(default \code{yes}) when the feature is enabled for the module, else
	\code{<else>} (default empty).
	\item[last-modified-directory <glob>] the most recently modified file
	or directory matching the pattern, empty when none matches.
	\item[output <command line>] the standard output of the command,
	without its final newlines; the status of the command is the status of
	the step.
	\item[output-words <command line>] the words of the standard output of
	the command, as a list.
	\item[first-line <value>] the first line of the value.
	\item[status] the exit status of the previous step (\code{\$?} in a
	shell).
	\item[basename <path>] the last component of the path.
	\item[dirname <path>] the path without its last component
	(\code{.} when there is none).
	\item[command-path <tool>] the full path of the tool found in
	\code{PATH} of the hook environment, empty when not found.
	\item[all-variants <variant>] the list of the variants of a variant
	string (\code{a.b} gives \code{a} and \code{b}), empty for
	\code{default}.
	\item[uppercase <words>, lowercase <words>] the words in upper or
	lower case.
	\item[if <condition> then <words> {[else <words>]}] the first words when
	the condition is true, else the second ones (empty without
	\code{else}), as \code{\$(if ...)} in values; the condition is one of
	the \code{if} blocks below.
	\item[all-modules] \index{all-modules}the list of the modules of the
	build of the module, in build order: its dependencies (all kinds),
	the meta-modules and the modules they aggregate, and the module
	itself. The status of each one is given by the conditions
	\code{depends-kind(\$M)}, \code{is-meta(\$M)}, \code{is-aggregate(\$M)}
	and \code{is-aggregated(\$M)} (see \emph{Blocks} below), e.g. to keep
	the modules installed on their own:
	\code{if depends-kind(\$M) == default and not is-aggregated(\$M):}.
	\item[hook-output <module> <hook> {[<args>]}] \index{hook-output}the
	output of a hook of another module (variant from the build plan),
	called with the arguments, e.g. a custom hook (a function
	\code{<module>-<hook>} of the plug-in), empty when the module has no
	such hook; for a value hook (\code{modules}, \code{depends}...) the
	list of its values.
\end{description}

\textbf{Built-in commands.} \index{YAML plug-in!built-in commands}
They run in the driver; any other command is an external program or a
function of the plug-in.

\begin{description}
	\item[cd {[<dir>]}] \index{cd} changes the current directory of the
	hook (\code{\$HOME} without argument); fails when the directory does
	not exist.
	\item[echo {[-n]} <words>] \index{echo} writes the words separated by
	a space, followed by a newline unless \code{-n} is given. It is the
	output of a hook giving a value (\code{version}...).
	\item[return {[N]}, exit {[N]}] \index{return}\index{exit} end the
	hook (or the plug-in function) with the status \code{N} modulo 256
	(\code{return -1} is 255), or with the status of the previous step.
	\item[true, :, false] succeed (\code{true},
	\code{:}) or fail (\code{false}), doing nothing.
	\item[export NAME{[=value]}...] \index{export} puts the variables in
	the environment of the following commands, setting them first when a
	value is given.
	\item[unset NAME...] \index{unset} removes the variables from the hook
	and from its environment.
	\item[check-versions <v1> <op> <v2>] \index{check-versions} succeeds
	when the comparison of the two versions is true; \code{<op>} is one of
	\code{=}, \code{==}, \code{!=}, \code{<}, \code{<=}, \code{>},
	\code{>=}.
	\item[copy <source>... <destination>] \index{copy} copies files and
	directories, directories always recursively (symbolic links are
	copied as links), as \code{cp -r}: into \code{<destination>} when it
	is an existing directory (it must be one for several sources), else to
	\code{<destination>}; existing files are replaced, existing
	directories merged. It has no option. The converter of Bash plug-ins
	turns \code{cp} and \code{cp -r} into \code{copy}; the system
	\code{cp} is still available for other options (\code{cp -a}...).
	\item[<function> <args>] a function of the plug-in
	(\code{functions:}), its parameters set to the arguments.
\end{description}

\textbf{Blocks.} \index{YAML plug-in!blocks of commands}
A block line ends with \code{:}; its body is the following lines
indented more than it.

\begin{description}
	\item[if <condition>:] runs its body when the condition is true;
	followed by any number of \code{elif <condition>:} and an optional
	\code{else:}, the first branch whose condition is true is run. The
	conditions are the ones of values (\seeref{yaml-conditions}) plus:
	\begin{description}
		\item[is-dir(path), is-file(path), is-link(path)]
		the path is a directory, a regular file, a symbolic link;
		\item[empty(\$VAR)] the value is empty (\code{not empty(\$VAR)}: it
		is not);
		\item[ok("<command line>")] the command succeeds: any external
		command or built-in, with its arguments and redirections; its
		standard output is discarded, its error output is shown unless
		redirected, e.g. \code{2> /dev/null};
		\item[status] the exit status of the previous step, e.g.
		\code{status == 0};
		\item[depends-kind(\$M), is-meta(\$M), is-aggregate(\$M), is-aggregated(\$M)]
		the status of a module of \code{all-modules}: the kind of
		dependency (\code{default}, \code{build} or \code{tests}), a
		meta-module, a meta-module aggregating its modules, a module
		installed in an aggregate;
		\item[\$VAR, "text"] variables and quoted strings as operands.
	\end{description}
	\item[for NAME in <words>:] runs its body once for each word, the
	words being expanded as the ones of a command (a list variable gives
	its elements, glob patterns their matches), with \code{NAME} set to
	the word.
	\item[write FILE:] writes the body, expanded, to the file (created or
	truncated); \code{\textbackslash\$}, \code{\textbackslash`} and
	\code{\textbackslash\textbackslash} give the character, as in a
	here-document.
	\item[append FILE:] as \code{write}, appending to the file.
	\item[write-raw FILE:, append-raw FILE:] as \code{write} and
	\code{append}, the body not expanded.
\end{description}

The status of a body is the status of its last step: a failing command
does not stop it unless the next one is chained with \code{\&\&}. An
error gives the plug-in file, the hook and the line.
\code{\$PWD} is the current directory of the hook. \code{return N} and
\code{exit N} give the status modulo 256 (\code{return -1} is 255).

The plug-in converter (\code{python3 -m scbi.convert})
translates the Bash command hooks to this language. It reports, instead
of converting, the constructs which have no equivalent (\code{eval},
\code{while}, nested functions, arithmetic, calls of runtime functions
other than the built-ins above...).

\subsubsection{Conditions}
\label{yaml-conditions}
\index{YAML plug-in!condition}

An item of a value list or of an environment list can be guarded by a
condition, it is then a mapping with a single key \code{if <condition>}:

\begin{lstlisting}
patches:
  - fix-common.diff
  - if ref =~ ^7.8: fix-7.8.diff
  - if version(lib2) > 1.9: [a.diff, b.diff]
build-env:
  - if target =~ mingw32: set-var OS Windows_NT
\end{lstlisting}

A condition compares operands with \code{==}, \code{!=}, \code{=\textasciitilde}
(regular expression) or \code{<}, \code{<=}, \code{>}, \code{>=} (versions, as
\code{check-module-version}), combined with \code{not}, \code{and}, \code{or}
and parentheses. The operands are \code{ref} (the module version),
\code{target}, \code{host}, \code{variant}, \code{kind} (the kind of the
module version: \code{DEV}, \code{BRANCH}, \code{VERSION}...), \code{cross} (true
when the target is not the host), \code{version(<plug-in>)} (version in the
build plan), \code{build-type(<kind>[,<default>])}, \code{enabled(<feature>)},
\code{exists(<path>)}, \code{empty(<value>)} (e.g. \code{empty(\$VAR)},
\code{not empty(\$VAR)}), \code{on <discriminants>} (as in build plans,
\seeref{discriminants}), and literal strings. Conditions never select
between variants, this is done with the qualifiers.

\subsection{Hooks}

Each hook is a key of the plug-in file, all of them are optional. In
this reference a hook which can be given per variant is written
\code{<hook> [<variant>]} and \code{<hook> [common|<variant>]} for the
cumulative hooks (\seeref{yaml-plugin}). The parameters are variables
of the hook body; the result of a value hook is its list of values.

\subsubsection{Description}

\begin{description}[font=\large\texttt]

	\item[vcs {[}<variant>{]}] \index{hook!vcs}Describe the module source VCS.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} NONE
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item proxy : name of a proxy, or \emph{default} to use default system one. (\seeref{proxy}).
			\item options : comma separated list of options, possible values are \emph{none}, \emph{no-recursive}, \emph{lfs}, \emph{submodule:PATH:URL}. The later option is to change the \code{URL} for a given submodule while cloning or updating the module repository. It is possible to specify multiple \emph{submodule} options.
			\item protocol : \emph{git}, \emph{svn}, \emph{hg}
			\item URL : repository location with protocol
			\item DIR (optional): name of the directory if the repository is hosting multiple projects. This is mostly needed for Subversion non standard repository layout. If \code{URL} is pointing to the tree where \code{trunk}, \code{branches} and \code{tags} directories are found, then SCBI will check for the actual sources in:
			\begin{itemize}
				\item \code{<root>/trunk/\$DIR}
				\item \code{<root>/[branches|tags]/<VER>/\$DIR}
				\item \code{<root>/[branches|tags]/\$DIR/<VER>}
			\end{itemize}.
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
vcs:
  proxy: default
  options: none
  protocol: git
  url: http://github.com/mm2/Little-CMS
\end{lstlisting}

	The fields can also be given as a list of values, in this order. A
	specific \code{vcs} hook can be selected in the environment by two means:

	\begin{description}[style=standard]
		\item[\code{SCBI\_<module>\_VCS\_VARIANT}] \hfill \\
		If environment variable \code{SCBI\_<module>\_VCS\_VARIANT} is set then the \code{vcs} hook of variant \code{\$\{SCBI\_<module>\_VCS\_VARIANT\}} is looked for before the generic one. This is specific to module name \code{<module>}.

		\item[\code{SCBI\_VCS\_VARIANT}] Same as above for the all modules.
	\end{description}

	\index{rewrite!rewrite\_vcs}
	And finally the function \code{rewrite\_vcs(record)} of the environment
	file (\seeref{python-env-files}) takes the five values of the
	\code{vcs} hook and returns them, possibly rewritten.

	\item[archive {[}<variant>{]}] \label{hookarchive}\index{hook!archive}Describe the archive filename and location of the archive containing the module sources.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$VERSION}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
		\item proxy : name of a proxy, or \emph{default} to use default system one. (\seeref{proxy}).
		\item options : comma separated list of options to be used on the command line for the tool used (see protocol below). Use \emph{none} if no option are needed.
		\item protocol: \emph{scp}, \emph{cp}, \emph{wget}, \emph{curl}, \emph{ftp}, \emph{none}.
		\item URL: location where the archive can be downloaded.
		\item filename : name of the archive with a possible \$VERSION in the pattern.
		\item DIR (optional) : name of the directory (with a possible \$VERSION) to use as source container if the archive is hosting multiple projects.
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
archive:
  proxy: default
  options: --no-check-certificate
  protocol: wget
  url: http://some.server.fr/sources
  file: cmake-$VERSION.tar.gz
\end{lstlisting}

	A specific \code{archive} hook can be selected in the environment by two means:

	\begin{description}[style=standard]
		\item[\code{SCBI\_<module>\_ARCHIVE\_VARIANT}] \hfill \\
		If environment variable \code{SCBI\_<module>\_ARCHIVE\_VARIANT} is set then the \code{archive} hook of variant \code{\$\{SCBI\_<module>\_ARCHIVE\_VARIANT\}} is looked for before the generic one. This is specific to module name \code{<module>}.

		\item[\code{SCBI\_ARCHIVE\_VARIANT}] Same as above for the all modules.
	\end{description}

	\index{rewrite!rewrite\_archive}
	And finally the function \code{rewrite\_archive(record)} of the
	environment file (\seeref{python-env-files}) takes the six values of the
	\code{archive} hook and returns them, possibly rewritten.

	\item[patches {[}common|<variant>{]}] \index{hook!patches}Returns the patch files to apply. REF is the actual module version making it possible to apply a patch selectively.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT \$KIND \$REF}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <patch-file-1>
			\item <patch-file-2>
			\item if ref =\textasciitilde{} 7.8: <patch-for-7.8>
			\item ...
		\end{enumerate}
	\end{description}

	\item[version {[}<variant>{]}] \index{hook!version}Returns the current version of the installed module.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} version or \code{\$VERSION\_OK} or \code{\$VERSION\_ERROR}
		\begin{enumerate}
			\item the version as a string corresponding to the current installed version. Can be \$VERSION\_OK or \$VERSION\_ERROR if the actual version cannot be determined.
		\end{enumerate}
	\end{description}

	\item[external-env {[}common|<variant>{]}] \index{hook!external-env}Used to compute the module's build identifier and will trigger a rebuild of the module if the value returned by this hook changes. This may be needed if the module must setup its sources depending on some external environment. The return value has no semantic, it must just reflect a change of value, generally just returning the value of the controlling environment variable is sufficient.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} value
		\begin{enumerate}
			\item \code{\$SOME\_VAR}
		\end{enumerate}
	\end{description}

	\item[build-depends {[}common|<variant>{]}] \index{hook!build-depends}Lists all modules required to build the actual module. To keep the module generic it is better to use the simple module name here and have a build-plan to specify a specific version and/or variant.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <module1>
			\item <module2>
			\item ...
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
build-depends: [gnat]
\end{lstlisting}

	\item[tests-depends {[}common|<variant>{]}] \index{hook!tests-depends}Lists all modules required to run the test-suite for the module. These are generally some tools or frameworks like \code{cunit} which are only needed to run the tests.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <module1>
			\item <module2>
			\item ...
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
tests-depends: [libcunit1]
\end{lstlisting}

	\item[depends {[}common|<variant>{]}] \index{hook!depends}Lists all modules required to build the actual module and to use/execute it. These are either other modules handled by SCBI or distribution packages. A dependent module can be specified as a full module-reference (\seeref{modref}) so with variant and/or version even if this is a generally a bad idea. To keep the module generic it is better to use the simple module name here and have a build-plan to specify a specific version and/or variant.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <module1>
			\item <module2>
			\item ...
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}

  - xmlada
  - asis
\end{lstlisting}

	\item[env {[}common|<variant>{]}] \index{hook!env}Set the environment to use this module as a dependency. This is the exported environment. The know how to set the environment using the helper routines \seeref{set-env}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\begin{enumerate}
			\item \code{add-to-var} <name> <value>
			\item ...
		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}

	Example:
	\begin{lstlisting}

  - add-to-var PKG_CONFIG_PATH $PREFIX/lib/pkgconfig
  - add-to-var PATH $PREFIX/bin
\end{lstlisting}

	\item[build-env {[}common|<variant>{]}] \index{hook!build-env}Set the environment needed to build this module.
	Those settings are not exported and only visible and used for the module. The \code{build-env} hook sees only the environment of the build dependencies.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\begin{enumerate}
			\item set-var <name> <value>
			\item ...
		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}

	\item[setup {[}<variant>{]}] \index{hook!setup}To put in place the sources just before configuration step. This is generally not needed as the sources are setup by \code{scbi} using the information provided by the archive or vcs hook. This may be needed in some complex case or if the sources are generated based on the running environment.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} NONE
	\end{description}

	\item[out-of-tree {[}<variant>{]}] \index{hook!out-of-tree}Whether to build out of the source tree or not. Default is \code{true}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} \code{\textbf{true} | false}
	\end{description}

	Example:
	\begin{lstlisting}

\end{lstlisting}

	\item[only-explicit-build {[}<variant>{]}] \index{hook!only-explicit-build}Whether to build when found in dependencies or only when the plug-in is passed on the command line. 	\begin{description}[font=\textit,style=standard]

	\begin{lstlisting}

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET [\$VARIANT]}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <option1>
			\item <option2>
			\item ...
		\end{enumerate}
	\end{description}

	\begin{description}[font=\textit,style=standard]

		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}

		\item[return] \tabto{2cm} NONE
	\end{description}

	\item[prefix {[}<variant>{]}] \index{hook!prefix}The directory for the installation of the module. The returned value can be set to NONE to skip the installation step. If this hook is not defined the module will be installed into \code{\$SCBI\_PREFIX}.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} string

		\item[return] \tabto{2cm} NONE

\subsubsection{Calling order}
\index{hook!calling order}

Some of the hooks are called by the main SCBI driver when needed as they are returning information of some artifacts. Those hooks do not have specific calling order:

\begin{itemize}
	\item vcs
	\item archive
	\item version
	\item external-env
	\item out-of-tree
	\item prefix
	\item env
	\item build-env
	\item depends
	\item build-depends
	\item run
\end{itemize}

For all other hooks there is a specific calling order which is:

\begin{enumerate}
	\item setup
	\item config
	\item build
	\item install
	\item wrapup
\end{enumerate}

It must be noted that for those steps the driver has generic internal
steps and the plug-in can define \code{pre} and \code{post} steps, run in
this order:

\begin{description}[font=\texttt,style=nextline]
	\item[generic pre-<step>] \index{hook!pre-}The generic pre step handled internally by the driver (\code{pre-install} removes the previous installation).
	\item[pre-<step>] The pre step action done before the main step.
	\item[<step>] The default step.
	\item[generic <step>] The generic step handled internally (\code{setup}, \code{install}).
	\item[post-<step>] \index{hook!post-}The post step action.
\end{description}

For example, the generic internal setup step is used by the scbi driver to setup the sources (creating the build environment and populating the proper sources to compile) using the \code{vcs}, \code{version}, \code{tar} and \code{out-of-tree} hooks.

The \code{patches}, \code{depends}, \code{build-depends}, \code{tests-depends}, \code{env}, \code{build-env}, \code{external-env} and \code{config-options} can have a \code{common} variant which is cumulative with the corresponding variant hooks or with the default hook. If a variant hook is present then the default hook is not called, we stop at the first \code{<variant>} call below (\code{\_} is the plain hook):

\begin{enumerate}
	\item \code{cross: common}
	\item \code{cross: <variant>}
	\item \code{cross: \_}
	\item \code{common}
	\item \code{<variant>}
	\item \code{\_}
\end{enumerate}

The \code{cross} hooks are used when the target is different than the host.
\index{hook!cross}

For all other hooks there is no \code{common} variant. Again if a variant hook is present the default hook is not called, we stop at the first \code{<variant>} call below:

\begin{enumerate}
	\item \code{cross: <variant>}
	\item \code{cross: \_}
	\item \code{<variant>}
	\item \code{\_}
\end{enumerate}

\subsection{Meta-module}
\label{meta-module}
\index{meta-module}

A meta-module is a module listing a set of modules to build. This can be used to aggregate some related modules that are generally built together but not depending on each others.

Other modules can depend on a meta-module.

A module defining the hook \code{modules} (possibly with variants) becomes a meta-module. Furthermore a meta-module defining the hook \code{aggregate} becomes an aggregate meta-module.

\begin{description}[style=nextline]
	\item[modules {[}common|<variant>{]}] \index{hook!modules}Lists the aggregated modules.
		\begin{description}[font=\textit,style=standard]
			\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET [\$VARIANT]}
			\item[return] \tabto{2cm} array
				\begin{enumerate}
					\item echo <module1>
					\item echo <module2>
		\end{enumerate}
	\end{description}

	\item[propagate-version {[}<variant>{]}] \index{hook!propagate-version}\label{propagate-version}Whether the meta-module's version and/or variant are to be propagated to aggregated modules. Default is \code{version}.
		\begin{description}[font=\textit,style=standard]
			\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET [\$VARIANT]}
			\item[return] \tabto{2cm} \code{\textbf{version} | variant | both | no}
		\end{description}

	\item[aggregate {[}<variant>{]}] \index{hook!aggregate}\label{aggregate}If set to \code{direct} or \code{recursive} the meta-module becomes an aggregate meta-module. In this case artifacts of all modules listed in \code{modules} hook are copied into the aggregate meta-module and the environment of all aggregated modules is pointing to the aggregate module. With this option it is possible to group into a single place the artifacts of multiple modules. When \code{direct} is used only the modules listed in the \code{modules} hook are aggregated, if \code{recursive} is used all dependencies are also aggregated. Default is \code{false}.
	\begin{description}[font=\textit,style=standard]
	\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET [\$VARIANT]}
	\item[return] \tabto{2cm} \code{direct | recursive | \textbf{no}}
	\end{description}

	\item[prefix {[}<variant>{]}] \index{hook!prefix}\label{prefix}The directory for the installation of the meta-aggregate module. This hook is not used for standard meta modules. The returned value can be set to NONE to skip the installation step. If this hook is not defined the module will be installed into \code{\$SCBI\_PREFIX}.
	\label{global-install}
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} string
		\begin{enumerate}
			\item <install\_dir>
			\\ or
			\item NONE
		\end{enumerate}
    \end{description}
\end{description}

And can list a build-plan to use for building all listed modules:

\begin{description}
	\item[plan {[}<variant>{]}] \index{hook!plan}Returns the build-plan to use.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} NONE
		\item[return] \tabto{2cm} string
		\begin{enumerate}
			\item <plan-name>
		\end{enumerate}
	\end{description}
\end{description}

Example:

\begin{lstlisting}
modules:
  - gnatcoll-core
  - gnatcoll-bindings
  - gnatcoll-db
plan: stable
\end{lstlisting}

A module listed in a meta-module can itself be a meta-module. A meta-module can define only a limited set of hooks, that is:

\begin{itemize}[font=\texttt]
	\item setup
	\item propagate-version
	\item external-env
	\item build-depends
	\item plan
	\item modules
	\item prefix
	\item wrapup
\end{itemize}

It is possible to specify a version for a meta-module even if there is no sources as this version will be propagated to all aggregated modules and recursively for all meta-modules. To disable this feature it is necessary to define the hook \code{propagate-version} as \code{no}.

The \code{external-env} hook can be used to ensure that the \code{wrapup} hook is run consistently. That is, if the \code{wrapup} hook use some environment variables or enabled options (\seeref{enable-feature}) to generate a package or take any action when a change is made on aggregated modules one need to add in the \code{external-env} hook the used environment.

\subsection{User's defined final step}
\label{module-final-step}
\index{hook!module-final-step}

After a successful build of a module or aggregate meta-module the
function \code{module\_final\_step(ctx)} of the environment file
(\seeref{python-env-files}) is called, if defined. It can be used to
update an application packaging for example.

\code{ctx} gives the information about the module:

\begin{description}
	\item [prefix] The installation directory for the module.
	\item [target] The build target for the module.
	\item [variant] The variants for the module.
	\item [module] The module plug-in's name.
	\item [formodule] The module depending on the current one, \code{@root} for a module given on the command line.
	\item [modref] The module reference as found in the dependencies.
	\item [depends\_kind] The kind of dependency for the module, values are \code{default}, \code{build} or \code{tests}
	\item [is\_meta] Wether the module is standard meta or aggregate meta, values are \code{yes}, \code{no} or \code{aggregate}
	\item [is\_aggregated] Wether the module is aggregated into a meta-module, values are \code{yes} or \code{no}.
	\item [is\_up\_to\_date] Wether the module is up-to-date or not, values are \code{yes} or \code{no}. A module may be up-to-date but not yet handled as the dependency kind was rejected.
\end{description}

and the methods \code{get(var)}, \code{is\_enabled(feature)},
\code{module\_ref(modref)}, \code{module\_name(modref)},
\code{target\_dir(module, variant)}, \code{ilog(...)} and
\code{env\_actions(hook="env", modref=None)}.

Example:

\begin{lstlisting}
import os
import subprocess

def module_final_step(ctx):
    #  Handle only standard dependencies
    #  (skip build & tests dependencies)
    if ctx.depends_kind != "default":
        return
    app = f"/some/dir/{ctx.module}"
    #  Copy if not up-to-date or not yet copied
    if ctx.is_up_to_date == "no" or not os.path.isdir(app):
        subprocess.run(["rsync", "-a", f"{ctx.prefix}/.", app])
\end{lstlisting}

\index{define-var!redefinition}
\code{ctx.env\_actions()} gives the environment actions (action,
variable, value) of the \code{env} hooks of the module (and of the
modules it aggregates for a meta-module), for example to write a launch
script setting the environment of an application:

\begin{lstlisting}
def module_final_step(ctx):
    with open(f"{ctx.prefix}/env.dump", "w") as f:
        for action, var, value in ctx.env_actions():
            f.write(f"{action} {var} {value}\n")
\end{lstlisting}

\subsection{Setting environment}
\label{set-env}
\index{variable!add}
\index{variable!set}
\index{variable!unset}
\index{variable!prepend}
\index{variable!append}
\index{variable|delete}
\index{helpers!define-var}
\index{helpers!add-to-var}
\index{helpers!prepend-to-var}
\index{helpers!append-to-var}
\index{helpers!set-var}
\index{helpers!unset-var}
\index{helpers!remove-from-var}

The following actions are used to set environment variables in the \code{env}, \code{build-env} and \code{tests-env} hooks. They permit a fine control about the way the variables are set and avoid duplicate values. Each action goes through the function \code{define\_var} of the environment file when it is defined (\seeref{python-env-files}).

\begin{description}[style=nextline]
	\item[define-var {[PREPEND|APPEND|ADD|SET|UNSET]} <VARIABLE> <VALUE>] Prepend, append, add or set a variable depending on the first action parameter. Note that a single character action is supported as alias.
	\begin{description}
		\item[PREPEND | P] Prepend \code{<VALUE>} in \code{<VARIABLE>}, remove previous value if it exists. This ensures that the value is found after the current ones if needed.
		\item[APPEND | A] Append \code{<VALUE>} in \code{<VARIABLE>}, remove previous value if it exists. This ensures that the value is found before the current ones.
		\item[ADD] Add \code{<VALUE>} in \code{<VARIABLE>} if it is not already present. The place of the value in the variable is not important, it may be at the start, middle or end.
		\item[REMOVE | R] Remove \code{<VALUE>} from \code{<VARIABLE>} if it is present. This can be the single value in \code{<VARIABLE>} or one of the value in a list like for \code{PATH} or \code{LD\_LIBRARY\_PATH} variables.
		\item[SET | S] Set \code{<VARIABLE>} to \code{<VALUE>} removing all previous values. After this call we always have a single value set.
		\item[UNSET | U] Unset \code{<VARIABLE>}. After this call \code{<VARIABLE>} is not set.
	\end{description}

	\item[prepend-to-var <VARIABLE> <VALUE>] short hand for \code{define-variable PREPEND <VARIABLE> <VALUE>}.
	\item[append-to-var <VARIABLE> <VALUE>] short hand for \code{define-variable APPEND <VARIABLE> <VALUE>}.
	\item[add-to-var <VARIABLE> <VALUE>] short hand for \code{define-variable ADD <VARIABLE> <VALUE>}.
	\item[remove-from-var <VARIABLE> <VALUE>] short hand for \code{define-variable DELETE <VARIABLE> <VALUE>}.
	\item[set-var <VARIABLE> <VALUE>] short hand for \code{define-variable SET <VARIABLE> <VALUE>}.
	\item[unset-var <VARIABLE>] short hand for \code{define-variable UNSET <VARIABLE>}.
\end{description}

Example:

\begin{lstlisting}
build-env:
  - set-var MYMODULE_USE_CLANG no
env:
  - add-to-var CMAKE_PREFIX_PATH /some/path
  - prepend-to-var PATH /priority/dir/bin
\end{lstlisting}

\subsubsection{Overriding define\_var}
\label{define-var-override}
\index{define\_var}\index{environment!define\_var}

All the actions above end in a single function, \code{define\_var}. An
environment file (\seeref{python-env-files}) can define its own
\code{define\_var} to change how the environment of the modules is set,
for all the plug-ins at once:

\begin{lstlisting}
def define_var(env, action, name, value):
    ...
\end{lstlisting}

It is called for each action of the \code{env}, \code{build-env} and
\code{tests-env} hooks, in order, with:

\begin{description}
	\item[\code{env}] the environment being built: \code{env.apply(action,
	name, value)} does the default action (as described above, with the
	recording in the \file{env.cmd} file of the module), \code{env.get(name)}
	gives the current value of a variable;
	\item[\code{action}] \code{ADD}, \code{SET}, \code{PREPEND},
	\code{APPEND}, \code{REMOVE} or \code{UNSET} (the short form
	\code{S}, \code{P}... when a plug-in uses it with \code{define-var});
	\item[\code{name}, \code{value}] the variable and the value, expanded.
\end{description}

The action is done only if the function calls \code{env.apply}: it can
change the value or the variable, call \code{env.apply} several times, or
ignore an action (it is then not recorded in \file{env.cmd} either). For
example, to keep \code{LD\_LIBRARY\_PATH} unchanged and use
\file{/opt/local} instead of \file{/usr/local}:

\begin{lstlisting}
def define_var(env, action, name, value):
    #  no module may change LD_LIBRARY_PATH
    if name == "LD_LIBRARY_PATH":
        return
    #  the packages are installed in /opt/local, not /usr/local
    value = value.replace("/usr/local", "/opt/local")
    env.apply(action, name, value)
\end{lstlisting}

To get the actions of a module without changing the build environment
(to write a launch script for example), use \code{ctx.env\_actions()} in
\code{module\_final\_step} instead (\seeref{python-env-files}).

\subsection{Setting a proxy}
\label{proxy}
\index{proxy}

When a Web protocol is used to retrieve an archive with the sources or a VCS it may be necessary to pass through a proxy. In the archive and vcs hook description the name of a proxy can be given. The function \code{proxy(name, env)} of the environment file (\seeref{python-env-files}) is then called with this name and the environment (a dictionary) of the download or VCS commands, to change.

A typical setting is:

\begin{lstlisting}
def proxy(name, env):
    if name == "enterprise":
        for var in ("http_proxy", "https_proxy", "ftp_proxy"):
            env[var] = "http://myproxy.org:3128"
        env["no_proxy"] = "localhost,.net"
\end{lstlisting}

Note that this setting will be available only during the download of the archive file or the VCS and won't be polluting other module download not requiring a proxy.

\subsection{Feature}
\label{enable-feature}
\index{feature}\index{helpers!is-enabled}\index{is-enabled}

It is possible to enable a feature using the command line \code{\ddash{}enable-<feature>} or some environment variables:

\begin{description}[style=nextline]
	\item [SCBI\_<feature>\_FEATURE] The \emph{feature} is set for all plug-ins with the corresponding value (\code{true} or \code{false}).
	\item [SCBI\_<plugin>\_<feature>\_FEATURE] The \emph{feature} is set for the given plug-in with the corresponding value (\code{true} or \code{false}).
\end{description}

This option activate the feature named \code{feature}. This is a convenience function and it is up to the user to decide about the semantic of the enabled feature. For \code{SCBI} driver this is only a flag set or not.

In module's plug-ins the feature can be checked with the \code{is-enabled} function:

\code{is-enabled <name> [then-value] [else-value]}

which returns \code{yes} by default or \code{then-value} if set when the feature is enabled, and the empty string by default or \code{else-value} if set when it is not. In conditions \code{enabled(<name>)} is true when the feature is enabled.

Some example, setting the \emph{installer} feature:

\cmd{scbi \ddash{}enable-installer ...}

or

\cmd{export SCBI\_installer\_FEATURE=true}

A feature check in a command hook:

\begin{lstlisting}
wrapup: |
  if enabled(installer) or enabled(appli):
      makeself ...
\end{lstlisting}

Or setting a specific compiler option, example of a \code{config-options} hook:

\begin{lstlisting}
config-options:
  - -DCMAKE_CXX_FLAGS=-march=$(is-enabled safe-arch x86_64 native)
\end{lstlisting}

\subsection{Build kind}
\index{helpers!get-build-type} \index{build kind}

One of the most generic build variant that must be handled is the \code{Release} vs \code{Debug} one. To support this more easily without requiring to create a specific variant hook there is a simple support using the function \code{get-build-type}:

\cmd{get-build-type <config> <default>}

(\code{\$(get-build-type <config> <default>)} in a value,
\code{VAR = get-build-type <config> <default>} in a command hook,
\code{build-type(<config>,<default>)} in a condition).

The \code{<config>} represents the configuration tool (CMAKE or CONFIGURE for example). But it can be whatever string.

This function will return the build-kind for the calling module and system type (\code{cmake} or \code{configure}) and if not specified the default value is returned.

The actual build kind for the given module can be set using some environment variables in the following order:

\begin{description}[style=nextline]
	\item [SCBI\_<module>\_BUILD\_TYPE] Build kind for this specific module.
	\item [SCBI\_<CONFIG>\_BUILD\_TYPE] Build kind for the builder kind.
\end{description}

And then this can be used in the \code{config} hook simply with:

\begin{lstlisting}
config: |
  BUILD_TYPE = get-build-type CMAKE Release
  cmake -DCMAKE_INSTALL_PREFIX=$PREFIX -DCMAKE_BUILD_TYPE=$BUILD_TYPE ../src
\end{lstlisting}

With the above example, if no variables are set in the environment to set the build type the default \code{Release} will be used. To force a \code{Debug} build one can set in the environment file or in the current shell:

\begin{lstlisting}
 export SCBI_CMAKE_BUILD_TYPE=Debug
\end{lstlisting}

Which will force a \code{Debug} build for all modules using \code{cmake}, or:

\begin{lstlisting}
 export SCBI_lcms2_BUILD_TYPE=Debug
\end{lstlisting}

With will force a \code{Debug} build for the \code{lcms2} plug-in only. In both cases, the corresponding plug-in must have been coded to use the \code{get-build-type} function as seen above. Note that the \code{export} must use \emph{underscores} instead of dashes in plug-in name as dashes are forbidden in variable name.

\subsection{Checking installed tools}
\index{helpers!check-tool}\index{check-tool}

It may be needed to check for the existence of a tool installed on the machine. It may not be a direct dependency but a tool needed for a specific need. For example the need to have \code{makeself} installed to create a self installer.

In a command hook the function \code{command-path} gives the path of a tool (empty if not found):

\begin{lstlisting}
wrapup: |
  MS = command-path makeself
  if empty($MS):
      echo Required tool makeself missing
      exit 1
\end{lstlisting}

\subsection{Checking dependency version}
\index{helpers!get-module-version}\index{get-module-verson}
\index{helpers!check-module-version}\index{check-module-verson}

The version of a dependency in the build plan can be checked in a plug-in. This can be used for example to apply a patch for a specific version of a dependency.

In a condition \code{version(<plug-in>)} is the version of the plug-in in the build plan, compared as versions with \code{<}, \code{<=}, \code{>}, \code{>=} or with a regular expression (\code{=\textasciitilde}):

\begin{lstlisting}
patches:
  - if version(lib2) > 1.9: new-lib2.diff
config: |
  if version(lib2) =~ ^2.0:
      ./configure --with-lib2-2.0
  else:
      ./configure
\end{lstlisting}

In a command hook \code{check-versions <v1> <op> <v2>} succeeds when the comparison is true.

\subsection{Inheritance}
\label{inheritance}
\index{inheritance}\index{inherit-plugin}\index{helpers!inherit-plugin}

It is possible to create a plug-in by inheriting from the definition
of another plug-in. This is done with the key \code{inherit}, a list of
inherited plug-ins:

\begin{lstlisting}
inherit:
  - from: <name>
    hooks: [<hook1>, <hook2>]
    custom-hooks: [<hook1>, <hook2>]
    no-variant: false
    name: <name>
\end{lstlisting}

\begin{description}
	\item[from] The name of an existing plug-in from which we want to inherit all the current hooks.
	\item[no-variant] Whether to not inherit from any hook's variant (\code{true}): only the default variants will be inherited.
	\item[hooks] The hooks to inherit from. If not specified all SCBI supported hooks are inherited.
	\item[custom-hooks] The custom hooks (plug-in functions) to inherit from.
	\item[name] The name to be used for the inherited plug-in instead of the default plug-in name. This makes it possible to inherit from multiple modules having the same hook and chain them manually.
\end{description}

The hooks defined by the plug-in itself take precedence over the
inherited ones. This may be handy if a module need to redefine only
the \code{vcs} or \code{proxy} hook for a specific context.

\subsection{Variants without build (with-variants)}
\label{native variant}
\index{native variant}\index{variant!native}
\index{with-variants}

For a plug-in it is sometimes needed to have a native variant to use the OS libraries instead of building from sources. It is possible to do so by creating the variant hooks manually. All hooks must be nop action except the \code{depends} hooks which may list the OS libraries and possible the \code{env} hook which may need to define some environment variables.

The key \code{with-variants} can be used to automate this action, for
a native variant or any variant which only depends on other modules or
packages:

\begin{lstlisting}
with-variants:
  native:
    packages: [pckA:[v], pckB]
    env: [set-var ROOT_DIR /usr]
\end{lstlisting}

The variant name is the key (\code{native}, any variant name can be
used). \code{packages} lists the modules or OS packages the variant
depends on, or \code{NONE}, \code{env} the environment actions. The value \code{NONE} will create an empty \code{depends} hook and can be used if the actual OS dependency has been installed manually on the machine. A possible reason is that the library has not been packaged by the OS maintainers. The \code{[v]} tag can be used to check that install \code{<package>} has the version specified for the plug-in.

With the example above, when \code{natv} has version \code{1.2} in the build plan, the variant \code{native} of \code{natv} has:

\begin{itemize}
	\item a \code{depends} hook listing \code{pckA:1.2} and \code{pckB};
	\item an \code{env} hook with the actions of \code{env};
	\item \code{prefix} set to \code{NONE};
	\item empty \code{build-env}, \code{build-depends}, \code{config}, \code{build} and \code{install} hooks.
\end{itemize}

\subsection{Getting configuration options}
\label{get config options}
\index{get-config-options}\index{helpers!get-config-options}

It is often needed to set configuration options based on the variant we want to build. This is for example to activate an external module.

In a command hook:

\begin{lstlisting}
  OPTIONS = config-options
\end{lstlisting}

sets \code{OPTIONS} to the list of the values of the \code{config-options} hooks of the module: the \code{common} one, then those of each variant of the module reference.

The \code{common} hook is designed to contain all the common options to be used regardless of the selected variant.

For example:

\begin{lstlisting}
plugin: mod
config-options:
  common: [-DPREFIX=/my/path]
  mpi: [-DMPI=ON]
  openmp: [-DOpenMP=ON]
config: |
  OPTIONS = config-options
  cmake $OPTIONS ../src
\end{lstlisting}

If the current module reference is \code{mod/mpi} the \code{cmake} command will be:

\begin{lstlisting}
	cmake -DPREFIX=/my/path -DMPI=ON ../src
\end{lstlisting}

And if the module reference is \code{mod/mpi.openmp} the \code{cmake} command will be:

\begin{lstlisting}
	cmake -DPREFIX=/my/path -DMPI=ON -DOpenMP=ON ../src
\end{lstlisting}

A list variable gives one word per element: an option containing spaces is kept as one argument.

\subsection{OS dependencies}
\label{OS dependencies}
\index{os dependencies}

The hook \code{depends} list dependencies to other plug-ins or external libraries/tools. As the name of the external dependency packages may be different depending on the Linux distribution and version it is possible to use an OS independent naming.

\begin{lstlisting}
	os@-<name>
\end{lstlisting}

The \code{os@-<name>} is then search against a table to find the corresponding OS package name.

A distribution acronym is represented by a 3 letters name (deb, ubt, rhl for example). See output of the \code{\ddash{}stat} option for the currently supported distributions.

An alias table is searched into the following places and in this specific order:

\begin{enumerate}
	\item \code{.pkgs-<distrib>[-<id>]} into \$SCBI\_PLUGINS (default \file{~/.config/scbi})
	\item \code{.scbi-pkgs-<distrib>[-<id>]} into \$SCBI\_BDIR (build directory)
	\item \code{.scbi-pkgs-<distrib>[-<id>]} into \$PWD (current directory)
\end{enumerate}

\begin{description}
	\item [\code{<distrib>}] The acronym of one of the supported distribution. The \code{<distrib>} can also have appended the \emph{major} and \emph{minor} version of the distribution. The separator between the name and version is the tilde \textasciitilde{}.

For example on \code{Debian 10.6} the searched files will be, and in that order:

\begin{enumerate}
	\item \code{.pkgs-deb}
	\item \code{.pkgs-deb\textasciitilde{}10}
	\item \code{.pkgs-deb\textasciitilde{}10.6}
\end{enumerate}

So \code{.pkgs-deb\textasciitilde{}10} can add new dependencies or override some dependencies that are set in \code{.pkgs-deb}.

\item [\code{<id>}] An optional random string that can be added for project's specific aliases. Such a file is loaded after the default one (without the \code{<id>}) so can override some entries if needed.
\end{description}

\subsection{Private Store}
\index{Private Store}
\index{API|Private Store}

See below (\ref{store}) how to handle the SCBI's private store. From a
command hook the \code{scbi store} sub-command can be used:

\begin{lstlisting}
wrapup: |
  scbi store LICKEY 89AXCDPPP6BGG
  KEY = output scbi store LICKEY
\end{lstlisting}

\section{The driver}
\label{python-driver}
\index{Python driver}

The driver is written in Python (\file{src/scbi} in the SCBI
repository). It replaces the former Bash driver (\seeref{bash-plugins}).

\subsection{Installing and running}
\index{install}

The driver needs \code{python3} (3.11 or later) and its YAML module
(\code{python3-yaml} on Debian). From a checkout of SCBI:

\cmd{make}

copies the driver into \file{\$HOME/.local/lib/scbi}, writes the command
\file{\$HOME/.local/bin/scbi}, and copies the plug-ins into
\file{\$HOME/.config/scbi} and the completion support into
\file{\$HOME/.bash\_completion.d}. From a checkout it can also be run
directly with:

\cmd{PYTHONPATH=<scbi>/src python3 -m scbi [options] module1 ...}

The name of the command displayed in the messages is taken from the
environment variable \code{SCBI\_ARGV0} when set (the \code{scbi}
command sets it).

\subsection{Compatibility with the Bash driver}

The driver accepts the same command line, options, ini files and build
plans as the former Bash driver, gives the same output and builds the
same sandbox. It runs no Bash code: no runtime file, no Bash plug-in and
no Bash environment file is read.

\begin{itemize}
	\item The plug-ins are YAML ones (\seeref{yaml-plugin}). A Bash plug-in
	without its YAML version is an error; it is converted with
	\code{python3 -m scbi.convert <plug-in>}.
	\item The environment files are Python files (\seeref{python-env-files}).
	\item The settings of the runtime files (\file{1\_setup},
	\file{6\_distpkg}, \file{8\_mail}...) are computed by the driver with
	the same defaults: \code{SCBI\_ROOT} (\file{\$HOME/dev}),
	\code{SCBI\_BDIR}, \code{SCBI\_PREFIX}, \code{SCBI\_ARCHIVES},
	\code{SCBI\_PATCH}, \code{SCBI\_LOGS}, \code{SCBI\_GIT\_REPO},
	\code{SCBI\_SVN\_REPO}, \code{SCBI\_HG\_REPO}, \code{KEEP\_LOG\_DAYS},
	\code{SCBI\_EMAIL\_NOTIFICATION}, the distribution
	(\code{SCBI\_OS\_NAME}...), the installed packages and the \code{os@-}
	aliases of the \file{.pkgs-<distrib>} files. They are changed through
	the environment or an environment file, not by editing the runtime
	files.
	\item The runtime functions cannot be redefined: the extension points
	are the hooks of the environment file (\code{define\_var},
	\code{rewrite\_vcs}, \code{rewrite\_archive}, \code{proxy},
	\code{module\_final\_step}).
	\item The environment of a module (the \code{env} hooks of its
	dependencies, of the aggregated modules of a meta-module, its
	\code{build-env} and \code{tests-env}) is computed by the driver; each
	environment action goes through the \code{define\_var} of the Python
	environment file, if any. With \file{\_os\_windows}
	(\code{SCBI\_OS\_MODULE=windows}) the \code{define-var} of that file
	(\code{;} separator, \code{cygpath -u} for \code{PATH}) is reproduced.
	\item The OS packages (\code{os@-} dependencies, \code{check-pkg})
	and the \code{auto} variants are checked for the supported
	distributions (\code{SCBI\_OS\_NAME} \code{deb}, \code{ubt},
	\code{cos}, \code{fed}, \code{rhl}, \code{mingw}, \code{win},
	\code{none}). The \code{auto} variants of a plan are checked in plan
	order (in parallel with the Bash driver: the order of their messages
	may differ).
	\item The values of the ini files are expanded as \code{eval echo}
	does in Bash (variables, \code{\textasciitilde{}}, quotes, \code{\$(command)},
	globs), without a shell.
	\item The cached build plans are stored in
	\file{\$SCBI\_BDIR/.cache/plan-<signature>.json}, a different file than
	the Bash driver one: both drivers can use the same build directory.
	\item The command hooks are run by the driver
	(\seeref{yaml-command-language}), with the hook environment described
	below; a step is reproduced with \code{scbi replay}.
\end{itemize}

\subsection{Environment files}
\label{python-env-files}
\index{environment!file}

The environment files are Python files, searched as described in
\seeref{envfile}:
\file{\$PWD/.scbi-env.py}, \file{\$PWD/../.scbi-env.py},
\file{\$HOME/.scbi-env.py}, then \file{\$SCBI\_PLUGINS/.env.py}
(\file{env-<name>} for \code{\ddash{}env=<name>}). A Bash environment file
without its Python version is an error. The settings of a Bash file are
converted with:

\cmd{python3 -m scbi.envconvert .env-<name>}

which writes \file{.env-<name>.py}; the functions it may define are
reported and converted by hand to the hooks below.

The file is run once when the driver starts, with \code{SCBI\_ENV\_DIR}
(its directory) and \code{getvar(name, default)} (the value of a driver
variable, or \code{default} when it is empty, as
\code{\$\{name:-default\}}). It may define:

\begin{description}
	\item[settings] module variables starting with an upper case letter
	and holding a string, e.g. \code{SCBI\_PLAN = getvar("SCBI\_PLAN",
	"default")} or \code{SCBI\_c\_gmp\_BUILD\_TYPE = "Debug"}: driver
	variables, given to the hooks. Use a name starting with \code{\_} for
	a variable of the file only. Another environment file can be included
	with \code{exec(compile(open(path).read(), path, "exec"))}, e.g. with
	\code{path = os.path.join(SCBI\_ENV\_DIR, ".env-shared.py")};
	\item[\code{PASSTHROUGH}] a list of variables of the user's environment
	given to the hooks (see below);
	\item[\code{define\_var(env, action, name, value)}] called for each
	environment action (\code{ADD}, \code{SET}, \code{PREPEND},
	\code{APPEND}, \code{REMOVE}, \code{UNSET}) of the plug-ins
	(the environment of each module), instead of the default;
	\code{env.apply(action, name, value)} does the default action,
	\code{env.get(name)} reads a variable (\seeref{define-var-override});
	\item[\code{rewrite\_vcs(record)}, \code{rewrite\_archive(record)}] the
	fields of a \code{vcs} / \code{archive} hook (a list: proxy, options,
	protocol, url, [file,] dir); the function returns the fields to use;
	\item[\code{proxy(name, env)}] the proxy \code{name} of a record:
	\code{env} is the environment (a dictionary) of the VCS or download
	command, to change;
	\item[\code{module\_final\_step(ctx)}] called after each module.
	\code{ctx} has the attributes \code{prefix}, \code{target},
	\code{variant}, \code{module}, \code{formodule}, \code{modref},
	\code{depends\_kind}, \code{is\_meta}, \code{is\_aggregated},
	\code{is\_up\_to\_date} (\seeref{module-final-step}) and the methods \code{get(var)},
	\code{is\_enabled(feature)}, \code{module\_ref(modref)} (module,
	variant, kind, reference in the plan), \code{module\_name(modref)},
	\code{target\_dir(module, variant)}, \code{ilog(...)} and
	\code{env\_actions(hook="env", modref=None)}, the (action, variable,
	value) of the environment hooks of the module (aggregated modules
	included), to write launch scripts for example.
\end{description}

\begin{lstlisting}
SCBI_PLAN = getvar("SCBI_PLAN", "default")
PASSTHROUGH = ["CC"]

def rewrite_vcs(record):
    return [f.replace("git@server:", "https://server/") for f in record]

def module_final_step(ctx):
    for action, var, value in ctx.env_actions():
        ctx.ilog(action, var, value)
\end{lstlisting}

\subsection{Hook environment}
\index{environment!hook}

A command hook of a YAML plug-in runs with an environment built for that
call only, and discarded after it: nothing accumulates between hooks or
modules. It contains:

\begin{itemize}
	\item from the user's environment only \code{PATH}, \code{HOME},
	\code{USER}, \code{LOGNAME}, \code{SHELL}, \code{TERM}, \code{TMPDIR},
	\code{DISPLAY}, \code{LANG}, \code{LANGUAGE}, \code{LC\_*} and the
	proxy variables (\code{http\_proxy}, \code{https\_proxy},
	\code{ftp\_proxy}, \code{no\_proxy} and their upper-case forms);
	\item the variables of \code{PASSTHROUGH} (environment file);
	\item every exported variable set or changed by the driver: the
	\code{SCBI\_*} variables, the settings of the environment files and
	the environment of the module (the \code{env} hooks of its
	dependencies, its \code{build-env} or \code{tests-env}).
\end{itemize}

The plug-in variables (\code{vars}) and the hook parameters are
variables of the body, not environment variables (use \code{export VAR =
...} to give one to the commands).

\subsection{Reproducing a step}
\label{replay}
\index{replay}

For a command hook of a YAML plug-in the file
\file{\$TVDIR/logs/<step>.cmd} is a replay file (YAML): the directory,
the environment, the parameters, the plug-in variables, the
config-options and the body of the hook (\code{run}, which can be edited)
with the plug-in functions it may call. When a step fails the driver
displays:

\begin{footnotesize}
	\begin{verbatim}
2026/11/13 13:23:30 : h-handson-lib (FAILED) to reproduce:
2026/11/13 13:23:30 : h-handson-lib (FAILED) scbi replay /<...>/logs/build.cmd
2026/11/13 13:23:30 : h-handson-lib (FAILED) use --trace option for debug
    \end{verbatim}
\end{footnotesize}

\cmd{scbi replay [\ddash{}trace] <step>.cmd}

reruns the hook; \ddash{}trace displays each command (and assignment)
before running it, as \code{bash -x} does. The step logs contain the same
trace (lines starting with \code{\_TRACE:}) unless
\code{SCBI\_DLOG=yes}.

\index{replay!script}
\cmd{scbi replay \ddash{}script <step>.cmd > step.sh}

runs nothing but displays a Bash script doing the step by hand: the
environment of the hook (exported), the driver variables, the parameters
(\code{PREFIX}, \code{TARGET}, \code{VARIANT}...), the plug-in variables,
the configuration options of the module (array \code{CONFIG\_OPTIONS}),
the plug-in functions called, the directory of the hook and its body
translated to Bash. What is known when the script is generated is
resolved (\code{cross}, \code{variant}, \code{enabled()},
\code{build-type()}, the functions with known arguments such as
\code{get-build-type}); file tests, \code{ok(...)}, command status and the
variables set by the hook stay Bash. The script can be edited and run with
\code{bash step.sh} (\code{env -i bash step.sh} for an environment as
isolated as the hook's). \code{all-modules} and \code{hook-output} are not
available in a replay.

\subsection{Sub-commands}

The sub-commands are implemented by the Python driver. \code{show},
\code{shell}, \code{store} and \code{source-archive} have the same options
and output as with the former Bash driver; \code{shell} spawns the user's
\code{\$SHELL} in the environment computed by the driver (and runs the
\code{run} hooks of the module for \ddash{}run without a command).
\code{replay} reruns a step (see above). \code{lint} and \code{format}
work on YAML plug-ins only (\seeref{linter}, \seeref{formatter}).

A standalone source archive (\ddash{}standalone) contains the driver
(the Python package in \file{lib}, the command \file{bin/scbi}), the
plug-ins of the modules and a Python environment file
(\file{.scbi-env-std.py}).

\subsection{Testsuite}
\index{testsuite}

\begin{description}
	\item[\code{make test}] The regression testsuite (pytest): each test
	driver (\file{tests/drivers/testNNN.py}) builds the test plug-ins
	(\file{tests/scripts.d}, YAML) in its own copy of the test directories
	and checks the output; the drivers run in parallel when pytest-xdist
	is installed, the JUnit report is \file{tests/junit.xml}.
	\code{make test T="testNNN..."} runs some of them.
	\item[\code{make unit}] The unit tests of the driver (pytest).
\end{description}

When run by the testsuite (\code{SCBI\_TESTSUITE=yes}) the driver does not
load \file{\$HOME/.scbi}, takes \code{SCBI\_OS\_MODULE} and \code{TODAY}
from the environment, uses the rsync checksum mode and logs the sync
messages; the harness (\file{tests/harness.py}) gives it the test
directories (\code{SCBI\_ROOT}\ldots) through the environment. With \code{SCBI\_OS\_NAME=test} the
installed packages are those of \code{SCBI\_TEST\_PKGS} (\code{"name=version
..."}), checked as Debian packages.

\section{Support tools}

\subsection{Show}
\label{listing}
\label{show}
\index{show}
\index{tools|show}

This \code{list} sub-command support listing build plan,  dependencies and showing module's reference.

\cmd{scbi show [options] [plugins]}

The following options are supported:

\begin{description}[font=\texttt]
	\item[\ddash{}depends:{[}direct|full{]}] Recursively list module's dependencies. Either list all dependencies recursively (the default) or only the direct dependencies of the given module.

	\item[\ddash{}rdepends] List all plug-ins having as dependency the plug-in passed on the command line. The variants if any are displayed around brackets and the kind of dependency (test or build) in parenthesis.

	\item[\ddash{}externals:{[}only{]}] Recursively list externals and modules dependencies. If sub-option \code{only} is specified it only displays the externals.

	\item[\ddash{}no-version] Do not display modules or externals versions.

	\item[\ddash{}filter:{[}all|run|dev{]} ] Restrict the listing of dependencies or externals to either \code{all} (default) dependencies, the \code{dev} dependencies needed to build the software or the \code{run} dependencies needed to execute the software. Those last dependencies may be computed automatically from the \code{dev} dependencies listed in plugin modules.

	\item[\ddash{}build-plan:{[}history{][}=filter{]}] List the final build plan that will be used. This is after loading main plan, inheriting from other plan \code{@load} and resolving the command line modules specification. With the sub-option \code{history} the definition history, from inherited plan for example, is displayed. This is handy for complex plan definition as it helps tracking the setting history. If \code{filter} is given it must contain a comma separated list of plug-in and only those plug-ins will be listed in the output.

	\item[\ddash{}module-ref:{[}version|variant|full{]} ] Display module's variant, version or both given in the command line or in the build plan.

	\item[\ddash{}stat] Display some statistics about of current setup.
\end{description}

\subsection{Shell}
\label{shell}
\index{shell}
\index{tools|shell}

This \code{shell} sub-command support running application or entering a shell (\code{\$SHELL}) with the module's environment variables set. This is meant to be used to build or test in the very same environment used by SCBI while building the given module on the command line. It is also possible to run directly a command using the module's environment.

\cmd{scbi shell [options] [plugins]}

The following options are supported:

\begin{description}[font=\texttt]

	\item[\ddash{}mode:{[}dev|sandbox|sb|tests|use{]}] Specify a mode for entering the shell. This controls the environment to be set and the directory in which the shell will be moved. The default mode is \code{use}.

	\begin{description}[font=\texttt]
		\item[sandbox] Specifying \code{sandbox} or \code{sb} move the shell working directory into the module's build directory sandbox. This mode is meant to debug (or test some other options) the build of the given module. Not only the environment is setup from all dependencies but also the build environment of the specified module is setup. That is, in this mode the environment is exactly the one SCBI sees when starting the configuration, build or install steps.

		\item[tests] As above but setup also the tests environment (that is all environment of the tests dependencies).

		\item[dev] As \code{sandbox}, but also move the shell working directory into the module user's checkout. Alternatively one can specify the module's version \code{dev} instead.

		\item[use] The shell stays in the current working directory and setup the environment for the module to be used by another one. That is the given module is a dependency (and all dependents modules recursively) for the work to be done.
	\end{description}

	\item[\ddash{}run{[}="command args..."{]}] \label{cmd!run}Run the given command with the module's environment variables set. This is meant to be used to run a command which is depending on some libraries or binaries that are in the sandbox. If optional \code{command args...} is not specified the hook \code{run} is used to get the command to run.

	\item[\ddash{}stat] Display some statistics about of current setup.
\end{description}

\subsection{Private Store}
\label{private store}
\label{store}
\index{private store}
\index{tools|store}

It is sometimes needed to use some private information (like software keys) to activate a module. Such information cannot be stored directly into a plug-in which could be made public. To cope with this specific case SCBI comes with support for storing pair of information into an external private store.

This support is given by the \code{store} sub-command:

\cmd{scbi store [options] [key1, key2...] [value]}

The following options are supported:

\begin{description}[font=\texttt]
	\item[-h | \ddash{}help] List options and usage information.

	\item[-v | \ddash{}version] Display version information of the SCBI driver and versions from plug-ins distributions coming from other sources\footnote{Note that for this to be supported the plug-ins distribution must have generated and installed a file name \file{.scbi*version.txt} next to the plug-ins.}.

	\item[-e | \ddash{}env=<name>] Use environment file \code{.env-<name>} instead of the default \code{.env}. (\seeref{build-env})

	\item[\ddash{}stat] Display some statistics about of current setup.

	\item[\ddash{}plugins=<directory>] Specify a non default location for the modules and plug-ins directory. This overrides the \code{SCBI\_PLUGINS} environment.

	\item[\ddash{}list-keys] List all registered keys.

	\item[\ddash{}list{[}:full{]}] List keys given as parameter or empty string if not defined. If \code{:full} is given the values for the given keys are also displayed.

	\item[-d | \ddash{}delete] Delete the given keys.
\end{description}

Some exmaples:

\begin{itemize}
	\item To set a key

	\cmd{scbi store LICKEY 89AXCDPPP6BGG}

	\item To list all stored keys

	\cmd{scbi store \ddash{}list-keys}

	\item To get value associated with a key

	\cmd{scbi store LICKEY}

	\item To remove a key

    \cmd{scbi store \ddash{}delete LICKEY}
\end{itemize}

All keys are stored into the file \file{\$SCBI\_PLUGINS/.store} (if using the default environment \file{\$HOME/.config/scbi/.store}).

\subsection{Linter}
\label{linter}
\index{linter}

The sub-command \code{scbi lint} can be used to check for common plug-in errors.

For example:

\cmd{scbi lint lcms2}

It will report:

\begin{itemize}
	\item Function not recognized as hook name (warning),
	\item Lists all variants,
	\item Check that parameters \code{PREFIX}, \code{TARGET}, etc. are declared with proper parameter number,
	\item Check that the number of expected parameters is correct,
	\item Reports undeclared hook parameter (warning),
	\item Reports parameters used but not declared (error).
\end{itemize}

The option \code{\ddash{}error} will only report errors.

With the Python driver (\seeref{python-driver}) \code{scbi lint} checks
YAML plug-ins (\seeref{yaml-plugin}) only: a Bash plug-in is reported as
to be converted (\code{python3 -m scbi.convert}). A plug-in is given by
name (\file{\$SCBI\_PLUGINS/<name>.yaml}) or by path. All the problems
found are reported:

\begin{itemize}
	\item errors: unknown keys (hooks with a typo, with the closest
	known name), structure of the hooks (qualifiers, \code{common} for a
	non-cumulative hook, nested \code{cross}, missing fields of
	\code{vcs} and \code{archive}), values of \code{out-of-tree},
	\code{only-explicit-build} (true or false), \code{aggregate} (direct,
	recursive or no) and \code{propagate-version} (version, variant, both
	or no), conditions, functions in values and environment actions;
	\item warnings: empty hooks, and variables used by a hook (shell code,
	values, environment actions) which are not known there: not a
	parameter of the hook (a parameter of another hook is named as such,
	e.g. \code{VERSION} used in \code{config}), not set by the hook, the
	plug-in variables or environment actions, nor a driver
	(\code{SCBI\_*}) or a usual environment variable.
\end{itemize}

The exit status is 1 when an error is found.

\subsection{Formatter}
\label{formatter}
\index{formatted}
\index{format}

The sub-command \code{scbi format} can be used to format plug-ins by reordering the hooks in a canonical order. It also removes the trailing white-spaces and the duplicate blank lines.

For example:

\cmd{scbi format lcms2}

The option \code{\ddash{}replace} will replace the plug-in after formatting otherwise the formatted plug-in is displayed on the console.

With the Python driver (\seeref{python-driver}) \code{scbi format}
formats YAML plug-ins (\seeref{yaml-plugin}) only, a Bash plug-in is
reported as to be converted (the converter already writes the canonical
form). An invalid plug-in is not formatted (see \code{scbi lint}). The
canonical form is:

\begin{itemize}
	\item the keys in this order: \code{plugin}, \code{inherit},
	\code{vars}, \code{functions}, \code{variants}, \code{with-variants};
	the sources \code{vcs}, \code{archive}, \code{patches}; the
	dependencies \code{depends}, \code{build-depends},
	\code{tests-depends}; the environment \code{env}, \code{build-env},
	\code{tests-env}, \code{external-env}; the steps \code{setup},
	\code{out-of-tree}, \code{only-explicit-build}, \code{config-options},
	\code{config}, \code{build}, \code{install}, \code{wrapup},
	\code{tests} (each step between its \code{pre-} and \code{post-}
	hooks); then \code{run}, \code{version}, \code{prefix}; and the
	meta-module hooks \code{modules}, \code{aggregate},
	\code{propagate-version}, \code{plan};
	\item inside a hook the qualifiers \code{\_}, \code{common},
	\code{default}, the variants in alphabetical order, then \code{cross};
	the fields of \code{vcs} and \code{archive} in their order;
	\item block style, indented by 2, multi-line values as literal blocks
	(\code{|}), quotes only where needed, a blank line between the hooks.
\end{itemize}

The comments are kept: a comment line goes with the key or list item it
precedes (and moves with it), an end of line comment with its line; the
comments at the top of the file (separated from the first key by a blank
line) and at the end stay there.

\subsection{Create Source Archive}
\label{createsourcearchive}
\index{source archive}

The tool \code{scbi source-archive} can be used to create source archive for a plug-in. This is useful if a \code{vcs} and \code{archive} hooks are defined for a plug-in. One can then avoid using the \code{vcs} repository and use a specific archive uploaded in some safe/secure server without requiring an Internet connection for example.

The sources are downloaded using the \code{vcs} hook defined for the plug-in. The archive's created is by default is named \code{<REPOSITORY-NAME>-<VERSION>.tar.gz} expect if the plug-in has defined the \code{archive} hook. In this later case the archive will be named according to the template in the \code{archive} hook, \seeref{hookarchive}. The supported archive formats are:

\begin{description}[style=nextline]
	\item[.tar] Archive tar not compressed.
	\item[.tar.gz] Archive tar compressed with best gzip compression.
	\item[.tar.bz2] Archive tar compressed with best Bzip2 compression.
	\item[.tar.zst] Archive tar compressed with best Zstandard compression.
	\item[.tar.xz] Archive tar compressed with best XZ compression.
	\item[.zip] Archive zip compressed with default zip compression.
\end{description}

For example:

\cmd{scbi source-archive lcms2:2.12}

Will create an archive named \file{Little-CMS-2.12.tar.gz}. This is the default naming as no \code{archive} hook is defined for this plug-in.

The tool can also create a \code{MD5}, \code{SHA-1} or \code{SHA-256}
file for the generated archive. Use the following command to get the usage output:

\cmd{scbi source-archive \ddash{}help}

\subsection{Completion support}
\label{completion}
\index{completion}

A script is provided to support bash completion for scbi. The script is \file{bash\_completion.d/scbi} and must be copied into \file{/etc/bash\_completion.d/} OS directory.

Note that for this to work, the bash completion package must be installed, on Debian based distributions this is achieved with:

\cmd{apt install bash-completion}

\subsection{User's checkout}
\label{userco}
\index{user's checkout}

This is certainly the most important use case. A complex software is built with SCBI, but a bug (due to configuration, build or dependencies) is found in one module. We need to debug this module and fix it, so the complete cycle would be:

\begin{itemize}
	\item Check-out the module
	\item Compile manually in debug mode
	\item Debug the application
	\item Fix the code
	\item Commit the changes
	\item Push, integrate the new changes (possibly in a new branch)
\end{itemize}

\code{SCBI} does support this scenario directly by allowing a user's checkout to be used instead of the sources in the sandbox. It is highly discouraged to modify the sources in the sandbox which should stay untouched by users. Beware, depending on the \code{SCBI} options, the modifications in the source may be overwritten, so lost.

The recommended steps are (we assume the current VCS for the module is Git):

\subsubsection{Checkout modules}

All modules that will be worked on must be checked-out.

\begin{shellcommand}
	\item cd \$HOME/dev
	\item git clone https://github.com/TurboGit/scbi-handson-lib.git
\end{shellcommand}

Let's switch to the \code{broken} branch for the demo:

\begin{shellcommand}
	\item cd scbi-handson-lib
	\item git checkout broken
\end{shellcommand}

As the clone is not done into \code{\$HOME/dev/repositories/git} the variable \code{SCBI\_GIT\_REPO} must be set to point to the root checkout directory, \seeref{build-env}.

\begin{shellcommand}
	\item export SCBI\_GIT\_REPO=\$HOME/dev
\end{shellcommand}

Mercurial and Subversion VCS are also supported, the variables for each are:

\begin{description}[style=standard]
	\item[Git] \tabto{3cm} SCBI\_GIT\_REPO\index{user's checkout!SCBI\_GIT\_REPO}
	\item[Mercurial] \tabto{3cm} SCBI\_HG\_REPO\index{user's checkout!SCBI\_HG\_REPO}
	\item[Subversion] \tabto{3cm} SCBI\_SVN\_REPO\index{user's checkout!SCBI\_SVN\_REPO}
\end{description}

\subsubsection{Build using the sources from checkout}

\subsection{Analyzing build failures}
\label{debugging}

When a build fails it may be needed to look at the full logs and the actual commands executed for the failing step (configure, build, install...).

\subsubsection{Look at the sandbox status}

The SCBI driver does record all needed information in the sandbox directory \file{<module>/build/logs/}.

The files created in this directory are:

\begin{description}[font=\file,style=standard]
	\item[env.cmd] \tabto{3cm} The environment set to configure, build or install the module.
	\item[build-plan] \tabto{3cm} The build plan with the variant and version of all modules.
	\item[config.cmd] \tabto{3cm} The replay file of the configuration (\seeref{replay}).
	\item[config.log] \tabto{3cm} The full log issued during the configuration.
	\item[build.cmd] \tabto{3cm} The replay file of the build.
	\item[build.log] \tabto{3cm} The full log issued during the build.
	\item[install.cmd] \tabto{3cm} The replay file of the installation.
	\item[install.log] \tabto{3cm} The full log issued during the installation.
	\item[<plug-ins>] \tabto{3cm} The plug-ins needed for the build.
\end{description}

In all the log files one can find a trace of every command executed. All trace line are prefixed with \code{\_TRACE:}. The \file{config.log} contains the full command used to configure the module and the \file{build.log} the full command used to build the module.

\subsubsection{Replay one specific step}

It is possible to replay a single command and display the full log to analyze what went wrong:

\begin{description}
	\item[The configuration step] \tabto{3cm}  \cmd{scbi \ddash{}config \ddash{}log:yes h-handson-lib}
	\item[The build step] \tabto{3cm} \cmd{scbi \ddash{}build \ddash{}log:yes h-handson-lib}
\end{description}

Let's reproduce the issue:

\cmd{scbi --build --plan=broken h-handson-lib}

\begin{footnotesize}
	\begin{verbatim}
		/<...>/h-handson-lib/<...>/src/hello/hello.cpp:4:5: error: ‘x’ was not declared in this scope
		4 |     x "hello";
		|     ^
	\end{verbatim}
\end{footnotesize}

The failure is because a bug in \code{hello.cpp}.

Edit \file{<...>/h-handson-lib/build/src/hello.cpp} and replace \code{x} by \code{return}. Then restart the build:

\cmd{scbi --build --plan=broken h-handson-lib}

\subsubsection{Use the replay files}

It is possible to replay the configure, build or install step just by
running the corresponding \code{.cmd} file with \code{scbi replay}
(\seeref{replay}); the \ddash{}trace option displays the commands as they
are executed.

In case of failure \code{SCBI} output the command to use to replay:

\begin{footnotesize}
	\begin{verbatim}
2024/09/19 13:23:30 : h-handson-lib (FAILED) scbi replay /<...>/h-handson-lib/<...>/logs/build.cmd
2024/09/19 13:23:30 : h-handson-lib (FAILED) use --trace option for debug
    \end{verbatim}
\end{footnotesize}

The replay file holds the directory, the environment, the parameters and
the body of the hook (which can be edited). The hook runs in its own
environment and won't pollute the working shell environment.

To run the step by hand, outside \code{scbi}, the replay file can be
turned into a shell script: \code{scbi replay \ddash{}script
/.../logs/build.cmd > build.sh}.

One can then edit the sources in the sandbox and replay the step:

\cmd{scbi replay /.../logs/build.cmd}

Here just fix the syntax error by changing \code{x} by \code{return}.

\cmd{scbi replay /.../logs/build.cmd}

This time the compilation complete without issue:

\section{Complete example}

Many scripts come with \code{scbi}, they are all good examples to learn about different features.

As a complete example here, let's build latest GIMP version. The plug-in is the file \file{gimp.yaml} (placed into \file{\$SCBI\_PLUGINS}, \file{\$HOME/.config/scbi} by default).

Note that this was compiling at the time this doc was written, but some dependencies on the OS may required the plug-in to be updated.

\begin{lstlisting}
plugin: gimp

# the sources are handled in Git
vcs:
  proxy: default
  options: none
  protocol: git
  url: https://github.com/GNOME/gimp

# all dependencies, most of them are standard Debian packages
# except libmypaint, mypaint-brushes and libgegl
depends:
  - gtk-doc-tools
  - libbabl-dev
  - libgegl-dev
  - libgexiv2-dev
  - libpoppler-glib-dev
  - python-gtk2-dev
  - python-cairo-dev
  - mypaint
  - libmng-dev
  - libxpm-dev
  - libmypaint
  - mypaint-brushes
  - libgegl

# the build is done in the source directory
out-of-tree: false

# the environment of the three dependent modules is set by
# their plug-ins
config: ./autogen.sh --prefix=$PREFIX

build: make -j$SCBI_JOBS

# installation into the sandbox install directory of the module
install: make install

# the global installation
prefix: /opt/gimp
\end{lstlisting}

As seen above, \code{gimp} module depends on three other modules and we do need some configuration from those dependencies during the configuration. The exported environment for the three dependencies are:

\begin{itemize}
	\item Hook \code{env} of \file{libmypaint.yaml}:

	\begin{lstlisting}
env:
  - add-to-var PKG_CONFIG_PATH $PREFIX/lib/pkgconfig
	\end{lstlisting}

	\item Hook \code{env} of \file{mypaint-brushes.yaml}:

	\begin{lstlisting}
env:
  - add-to-var PKG_CONFIG_PATH $PREFIX/share/pkgconfig
	\end{lstlisting}

	\item Hook \code{env} of \file{libgegl.yaml}:

	\begin{lstlisting}
env:
  - add-to-var PKG_CONFIG_PATH $PREFIX/lib/pkgconfig
  - add-to-var PATH $PREFIX/bin
	\end{lstlisting}

\end{itemize}

The full description for those three modules are provided with scbi.

For this version of GIMP we need specific versions of the dependencies. A build-plan \code{.plan-gimpdev} is used to describe this:

\begin{lstlisting}
 libmypaint:v1.3.0
 mypaint-brushes:v1.3.0
\end{lstlisting}

That is, we need version 1.3.0 of \code{libmypaint} and \code{mypaint-brushes}.

At this point we can build GIMP with a simple:

\cmd{scbi \ddash{}plan=gimpdev \ddash{}deps gimp}

\section{Bash plug-ins and the Bash driver}
\label{bash-plugins}
\index{Bash plug-in}

Before the Python driver, SCBI was a Bash driver (\file{scbi} and
\file{scbi-*}, with the runtime files \file{scripts.d/[0-9]*}) and the
plug-ins were Bash scripts. The Bash driver is no longer part of SCBI; the
Bash plug-ins are converted to YAML once (see below).

\subsection{Bash plug-in format}

A Bash plug-in is a file named as the plug-in (no suffix) defining a Bash
function per hook, named \code{<plug-in>[-<variant>|-common][-cross]-<hook>}.
The parameters are given as positional parameters (\code{local
PREFIX=\$1}, \code{local TARGET=\$2}, \code{local VARIANT=\$3}...), a
value hook prints its values (\code{echo}, one per line), an environment
hook calls the helpers \code{add-to-var}, \code{set-var}... and a command
hook is Bash code:

\begin{lstlisting}
function lcms2-vcs()
{
	echo default
	echo none
	echo git
	echo http://github.com/mm2/Little-CMS
}

function lcms2-env()
{
	local PREFIX=$1
	add-to-var PKG_CONFIG_PATH $PREFIX/lib/pkgconfig
}

function lcms2-build()
{
	local PREFIX=$1
	local TARGET=$2
	local VARIANT=$3
	make -j$SCBI_JOBS
}
\end{lstlisting}

The YAML equivalents of the Bash constructs:

\begin{description}
	\item[\code{inherit-plugin [options] <name>}] the key \code{inherit} (\seeref{inheritance}).
	\item[\code{with-variant native <packages> \ddash{}env ...}] the key \code{with-variants} (\seeref{native variant}).
	\item[\code{get-config-options OPTIONS \$PREFIX \$TARGET \$VARIANT}] \code{OPTIONS = config-options} (\seeref{get config options}).
	\item[\code{\$(get-build-type <kind> <default>)}] the same in values, \code{V = get-build-type ...} in command hooks.
	\item[\code{check-tool}, \code{check-tools}] \code{command-path} in command hooks.
	\item[\code{get-module-version}, \code{check-module-version}] \code{version(<plug-in>)} in conditions, \code{check-versions}.
	\item[\code{scbi-store-set-key}, \code{scbi-store-get-key}] the \code{scbi store} sub-command.
	\item[\code{scbi-rewrite-vcs}, \code{scbi-rewrite-archive}, \code{proxy-<name>}, \code{module-final-step}, a redefinition of \code{define-var}] the functions \code{rewrite\_vcs}, \code{rewrite\_archive}, \code{proxy}, \code{module\_final\_step} and \code{define\_var} of the Python environment file (\seeref{python-env-files}).
	\item[\code{call-variant-hooks}] no equivalent: the hooks of the variants are selected by the qualifiers (\seeref{yaml-plugin}).
\end{description}

\subsection{Calling variant hooks (Bash plug-ins)}
\label{call variant hooks}
\index{call-variant-hooks}\index{helpers!call-variant-hooks}

The support routine \code{call-variant-hook} can be used to call a set of hook in a module based on the variants.

\begin{lstlisting}
call-variant-hooks hname $PREFIX $TARGET $VARIANT \
    [$P1 $P2...]
\end{lstlisting}

Will call all hooks in the current plug-in (<plugin>) with arguments \code{\$PREFIX}, \code{\$TARGET}, \code{\$VARIANT} and optional parameters \code{\$P<n>} in the form:

\begin{lstlisting}
   <plugin>-<variant>-hname
\end{lstlisting}

Where \code{<variant>} is all possible values found in \code{\$VARIANT}.

\subsection{Converting Bash plug-ins}

A Bash plug-in is converted with:

\cmd{python3 -m scbi.convert [\ddash{}check] [\ddash{}output-dir=<dir>] <plug-in>...}

Everything that cannot be expressed in the YAML format is reported and the
plug-in is not converted; it must be fixed first. This is the case for hook
parameters not matching the hook signature or values computed by arbitrary
shell code.

A hook of a variant which only calls the same hook of other variants (like
\code{c-darktable-all-depends} calling the \code{depends} hooks of the
\code{ai}, \code{hdr} and \code{jxl} variants) is converted into a
variant including other variants (\seeref{yaml-variants}), after checking
that the hooks selected are the same for every hook, variant and cross
mode; otherwise it is reported.

The converted plug-in is written as \file{<name>.yaml} next to the Bash
plug-in (or into the \ddash{}output-dir directory); with \ddash{}check
nothing is written. The exit status is 1 if a plug-in cannot be converted.

The Bash environment files (\file{.env-<name>}) are converted with
\code{python3 -m scbi.envconvert <file>} (\seeref{python-env-files}).
