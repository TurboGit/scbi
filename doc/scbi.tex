\section{Introduction}

SCBI is a Source Code Build Infrastructure.

The goal is to automate the build of software from its sources. The main features are:

\begin{itemize}
	\item recursive build of the dependencies;
	\item build from a VCS (\emph{Git}, \emph{Subversion} and \emph{Mercurial} are supported);
	\item build variants and automatic variants;
	\item cross compilation;
	\item build of a specific branch or tag;
	\item build from an archive;
	\item build from a user's checkout, for easy debugging in a controlled environment;
	\item build plans (modules with a specific variant and/or version).
\end{itemize}

The driver is written in Python (it needs \code{python3} and its YAML
module, \code{python3-yaml} on Debian); the plug-in modules are YAML files.

For the developers of new plug-in modules, the setup, the copy of the sources and the installation are done by SCBI: they just need to fill in the hooks to configure, build and install (generally just calling \code{configure} from \code{autotools} or \code{cmake}, and \code{make}).

Those hooks are very close to what would be typed to build manually from the command line. The goal is to reduce as much as possible the gap between a manual build and the commands of a plug-in module.

When properly set up, building any software should be as easy as:

\cmd{scbi \ddash{}plan=ver mysoft}

We'll see how to achieve that in this document.

\section{Using}

\subsection{Module reference}
\label{modref}
\index{module reference}

A module is described by an SCBI plug-in (one plug-in per file). It can be referenced in different places (as a dependency in other plug-ins, in a build plan, etc.) with the following format, called a \emph{module reference}:

\code{[for\_module=]name[/variant][:version]}
\label{dev}

\begin{description}[style=nextline]
	\item[for\_module] The name of the plug-in depending on this module. This is optional and can be used to select a specific variant or version when the plug-in \code{name} is a dependency of \code{for\_module}. In a build plan an alternative syntax can be used, see \code{@for} (\seeref{formodule}).

	\item[name] The name of the plug-in. This is the main reference for the plug-in. The corresponding plug-in file (\file{<name>.yaml}) must be located in \code{\$SCBI\_PLUGINS}.

	\item[variant] \label{variant}A name identifying a build variant of the module. For example an application can be built with different configurations and/or dependencies.

	\begin{description}[font=\texttt]
		\item[<ID>] The variant name. It selects the hooks of the plug-in defined for this variant.

		\item[native] \index{variant!native}The variant using the packages of the distribution. This name is mandatory for such a variant and required by the \code{auto} mode (see below). When a \code{native} variant is referenced the \code{build-depends} hook is not used (\seeref{native variant}).

		\item[auto] \index{variant!auto}A special variant which checks the dependencies of the \code{native} variant and uses it if all of them are available (not necessarily installed). The \code{auto} variant is not defined in a plug-in, it is only used in references. With \code{native} and \code{auto} a module is either built or taken from the distribution depending on the packages available on the running OS. Used together with other variants, \code{auto} must be the first one in the module reference, just after the slash. For example:

		\code{module/auto.fast:v1.3}

		Finally, the \code{auto} variant can only be defined in a build plan or on the command line.

		\item[@] \index{variant!@}Only available on the command line: the variant is the one of the build plan. If the build plan does not give one, the \code{default} variant is used as if none was specified.
	\end{description}

	\item[version] The version to build. This version string can be either:

	\begin{description}[font=\texttt]
		\item[<ID>] A VCS version (a branch, a tag or a Git SHA-1 for example), or an archive version when it starts with \code{\#}.
		\item[dev] \index{version!dev}The sources are taken from the user's checkout.
		\item[keep] \index{version!keep}The module sources are not updated: the \emph{setup}, \emph{config}, \emph{build}, \emph{install} and \emph{wrapup} steps are not run and the module stays as it was built last time. If the module has not been built yet, \code{keep} is ignored.
		\item[skip] \index{version!skip}The module is completely ignored, as if the plug-in was not in the dependencies.
		\item[force] \index{version!force}Enables a module which would otherwise be skipped (set to \code{skip} in a build plan for example).
		\item[@] \index{version!@}Only available on the command line: the version is the one of the build plan. If the build plan does not give one, the default version is used (e.g. \code{master} for Git) as if none was specified.
	\end{description}

	On the command line, a version or variant given explicitly overrides the build plan. A plain module name does not: to build the default variant or version of a module whose build plan says otherwise (or \code{skip}), give \code{force} as version.

	That is, the following command never overrides the build plan, as it is a plain reference to the module:

	\cmd{scbi --plan=xyz mod}

	But this will do:

	\cmd{scbi --plan=xyz mod:force}
\end{description}

The following are examples of module references:

\begin{description}[style=nextline]
	\item[lcms2] Build \code{lcms2} from the main branch of the repository (master/trunk).

	\item[lcms2/fast] Build the \emph{fast} variant of \code{lcms2} from the main branch of the repository.

	\item[gimp=lcms2/slow] When it is a direct dependency of \code{gimp}, build the \emph{slow} variant of \code{lcms2} from the main branch of the repository.

	\item[lcms2:v2.0] Build \code{lcms2} from the branch (or tag) \emph{v2.0} of the repository.

	\item[lcms2/fast:v2.0] Build the \emph{fast} variant of \code{lcms2} from the branch (or tag) \emph{v2.0} of the repository.

	\item[lcms2/@:v2.0] Build \code{lcms2} with the variant given by the build plan, from the branch (or tag) \emph{v2.0} of the repository.

	\item[lcms2:bfaf7b82ed] Build \code{lcms2} from the commit \emph{bfaf7b82ed} of the repository (Git only).

	\item[lcms2:\#v1.0] Build \code{lcms2} from the archive of version \emph{v1.0}.

	\item[lcms2:dev] Build \code{lcms2} from the user's checkout found in \code{\$SCBI\_GIT\_REPO} (assuming \code{lcms2} uses Git). For a discussion about user's checkouts \seeref{userco}.

	\item[lcms2:skip] Do not build \code{lcms2}. This is especially useful in a build plan or on the command line to ignore a module.
\end{description}

\subsection{Environment}
\label{build-env}
\index{environment}

The build is controlled by a set of variables (the environment). SCBI comes with defaults that can be used as-is, but the build can be fine-tuned with the following variables, set in an environment file (\seeref{envfile}) or in the environment of the \code{scbi} command.

\subsubsection{Description}

\begin{description}[before=\let\item\myitem]
	\item[SCBI\_DEFAULT\_ENV] The name of the environment file to use when \ddash{}env is not given (\file{.env-<name>.yaml}).

	\item[SCBI\_ENV\_DIR] The directory of the environment file being loaded.

	\item[SCBI\_VERSION] The version of the scbi driver.
	\\This version is \version.

	\item[SCBI\_PLUGINS] The directory of the plug-ins.
	Default is \file{\$HOME/.config/scbi}.

	\item[SCBI\_PLAN] The name of the build-plan to use if any.

	\item[SCBI\_ROOT] The root directory of SCBI. \\
	Default is \file{\$HOME/dev}.

	\item[SCBI\_BDIR] The build directory, also called the sandbox (\seeref{sandbox}). \\
	Default is \file{\$SCBI\_ROOT/builds}.

	\item[SCBI\_MODULES\_DIR{[<module-name>[@src|@build]]}] The \emph{install}, \emph{source} or \emph{build} directory of a module (for its variant in the build): \code{\$\{SCBI\_MODULES\_DIR[<module-name>]\}} is the install directory, \code{\$\{SCBI\_MODULES\_DIR[<module-name>@src]\}} the source directory and \code{\$\{SCBI\_MODULES\_DIR[<module-name>@build]\}} the build directory. It can be used in the hooks of the plug-ins (values, environment actions and commands).

	\item[SCBI\_CACHE\_DIR] The directory of the build cache, which makes it possible to reuse a previous build instead of rebuilding a module. Set to \code{no} to disable the cache. Default is \file{\$HOME/.cache/scbi}.

	\item[SCBI\_PROGRESS] \index{progress}When the output is a terminal,
	\code{scbi} shows the progress of the build, \code{[<n>/<total>]
	<module>}: the module being handled and the number of modules to
	handle (with \ddash{}deps, all the dependencies). It is never written
	to the logs. The values (also given by the option
	\ddash{}progress:{[}bar|line|no{]}, which takes precedence) are:
	\begin{description}
		\item[bar] (default) a status bar on the last row of the terminal
		(the output scrolls above it) with also the time elapsed since the
		start of the build, refreshed every second;
		\item[line] a transient line after an empty line, at the end of
		the output, redrawn after each output line and erased at the end;
		\item[no] no progress (also with \ddash{}quiet).
	\end{description}

	\item[SCBI\_PREFIX] The global install directory: after being installed in the sandbox, each module is copied into it. \\Default is \file{\$SCBI\_BDIR/install}. A module can disable the global installation (\seeref{global-install}).

	\item[SCBI\_GIT\_REPO] The directory of the user's Git checkouts. \\ Default is \file{\$SCBI\_ROOT/repositories/git}.

	\item[SCBI\_SVN\_REPO] The directory of the user's Subversion checkouts. \\ Default is \file{\$SCBI\_ROOT/repositories/svn}.

	\item[SCBI\_HG\_REPO] The directory of the user's Mercurial checkouts. \\ Default is \file{\$SCBI\_ROOT/repositories/hg}.

	\item[SCBI\_ARCHIVES] The directory of the downloaded archives. \\Default is \file{\$SCBI\_BDIR/.archives}.

	\item[SCBI\_LOGS] The directory of the logs. \\Default is \file{\$SCBI\_BDIR/.logs}.

	\item[SCBI\_PATCH] The directory of the patches. \\Default is \file{\$SCBI\_BDIR/.patches}.

	\item[SCBI\_HOST] The host triplet (the system running SCBI).

	\item[SCBI\_TARGET] The target triplet of the builds. \\Default is \code{\$SCBI\_HOST}.

	\item[SCBI\_JOBS] The number of parallel jobs of a build, to be used in the plug-ins (\code{make -j\$SCBI\_JOBS}). \\Default is the number of cores. It can be changed with the \ddash{}jobs option.
	\label{njobs}
	\item[SCBI\_HALF\_JOBS] Half the number of parallel jobs, to be used in the plug-ins. \\Default is the number of cores divided by 2. It can be changed with the \ddash{}jobs option.\label{half-njobs}

	\item[SCBI\_TMP] The directory of the standalone archives (\seeref{standalone}). \\Default is \file{/tmp}.

	\item[SCBI\_INI\_FILE] An additional ini file (\seeref{inifile}).

	\item[KEEP\_LOG\_DAYS] The number of days the logs are kept in \code{\$SCBI\_LOGS}. \\Default is 120.

	\item[SCBI\_OS\_NAME] The 3-letter acronym of the distribution (\code{deb}, \code{ubt}, \code{fed}...), computed by the driver; it can be set to force a distribution (\seeref{os-deps}).
\end{description}

The driver also sets the following variables, which the plug-ins can use:

\begin{description}[before=\let\item\myitem]
	\item[SCBI\_OS\_VERSION, SCBI\_OS\_MAJOR\_VERSION] The version of the distribution, and its major version.

	\item[SCBI\_OS\_CODENAME, SCBI\_OS\_ID] The code name and the identifier of the distribution (as given by \code{lsb\_release}).

	\item[SCBI\_IS\_WINDOWS] \code{yes} on Windows, else \code{no}.

	\item[SCBI\_CURRENT\_MODULE] The name of the module being handled.

	\item[SCBI\_BINARY] The path of the \code{scbi} command.
\end{description}

\subsubsection{Environment files}
\label{envfile}
\index{environment!file}

The environment is set by an environment file (a YAML file,
\seeref{env-files}), the first one found in this order:

\begin{description}
	\item[\code{\$PWD/.scbi-env.yaml}] In the current directory.

	\item[\code{\$PWD/../.scbi-env.yaml}] In the parent of the current directory: an environment shared by a set of repositories.

	\item[\code{\$HOME/.scbi-env.yaml}] In the home directory: an environment shared by all builds of the user.

	\item[\code{\$SCBI\_PLUGINS/.env.yaml}] The default environment, with the plug-ins.
\end{description}

Instead of the default \file{.env.yaml} (or \file{.scbi-env.yaml} for local environment files) a specific environment file can be selected with the \code{\ddash{}env=<name>} option: \file{.env-<name>.yaml} (\file{.scbi-env-<name>.yaml} for local files, \seeref{options}).

For example, to build \code{lcms2} with the environment \file{.env-next.yaml}:

\cmd{scbi \ddash{}env=next lcms2}

Or using an environment variable:

\cmd{export SCBI\_DEFAULT\_ENV=next}

\cmd{scbi lcms2}

\subsection{Discriminants}
\label{discriminants}
\index{discriminants}
\index{plan|discriminants}

A list of discriminants is computed for each build. They depend on the host and the target, and are used in the barriers of build plans (\seeref{plan-barrier}), in \code{@on} directives and in the conditions of plug-ins (\code{on <discriminants>}) to tune the build.

The discriminants are:

\begin{itemize}
	\item the host name;
	\item the domain name;
	\item the OS (e.g. \code{windows}, \code{linux});
	\item the OS name (e.g. \code{debian});
	\item a 3-letter acronym of the OS name (e.g. \code{deb}, \code{fed});
	\item the major version of the OS;
	\item the code name of the OS;
	\item the architecture (e.g. \code{x86\_64}, \code{i686});
	\item the words of the OS description (e.g. \code{debian}, \code{gnu}, \code{linux});
	\item for a cross build, the \code{cross} discriminant and each part of the target triplet prefixed with \code{target-} (e.g. \code{target-mingw32}, \code{target-arm}).
\end{itemize}

The option \ddash{}stat displays the discriminants of the running machine.

\subsection{Build plans}
\label{build-plan}
\index{build plan}

A build plan is a file giving the variant and version to build for each module. It is equivalent to giving all of them on the command line:

\cmd{scbi lcms2:v2 aws:v1}

A build plan is better: the build is reproducible and the versions are recorded in a file (kept in a version control system for example).

A build plan is a file named \file{.plan-<name>} listing a module reference (\seeref{modref}) per line:

File \file{.plan-next}:
\begin{lstlisting}
 lcms2:v2
 aws:v1
\end{lstlisting}

By default, a version given for a meta-module is propagated to its modules, and recursively to the modules of its meta-modules (\seeref{propagate-version}). This is a \emph{soft} setting: it does not override a version given for a module anywhere in the build plan or on the command line.

The following directives are supported:

\begin{description}
	\item[\code{\#}] Starts a comment line.

	\item[\code{@load <name>}] Loads another build plan as the base of this one; the lines after it override the loaded plan.

	This is a simple way to derive a build plan from another one.

	File \file{.plan-next}:

	\begin{lstlisting}
		# the next line will load build plan standard
		@load standard
		lcms2:v2
		aws:v1
	\end{lstlisting}

	\item[\code{@set <variable-name> = <value>}] Sets a variable, used in the following lines as \code{\$<variable>} or \code{\$\{<variable>\}}. This makes it possible to share a version between related plug-ins for example.

	\begin{lstlisting}
		@set VERSION = v2
		@set VARIANT = fast

		module1/$VARIANT:$VERSION
		module2:$VERSION
	\end{lstlisting}

	\item[\code{@ref <m2> as <m1> [version <pattern>]}] Gives \code{<m2>} the variant and version of \code{<m1>}.

	\begin{lstlisting}
		module1/var:1.2
		@ref module2 as module1
	\end{lstlisting}

	Here \code{module2} will use the variant and version of \code{module1}. The above plan is equivalent to:

	\begin{lstlisting}
		module1/var:1.2
		module2/var:1.2
	\end{lstlisting}

	This comes in handy in a plan loading another one, or for a plug-in inheriting from another one.

	A \code{pattern} computes the version of \code{module2} from the version of \code{module1}. It has three parts: \code{<prefix>/<regpat>/<suffix>}.

	\begin{description}
		\item[prefix] If present, a string added before.
		\item[regpat] A regular expression: the part of the version of \code{module1} it matches is used.
		\item[suffix] If present, a string added after.
	\end{description}

	\begin{lstlisting}
	module1/var:1.2.3
	@ref module2 as module1 version v/[0-9].[0-9]/
	\end{lstlisting}

	Here \code{module2} uses the variant of \code{module1} and a version made of \code{v} followed by the major and minor versions of \code{module1}. The above plan is equivalent to:

	\begin{lstlisting}
		module1/var:1.2.3
		module2/var:v1.2
	\end{lstlisting}

	\item[\code{@on <discriminants> use <module-reference>}] Sets a module reference only when all the discriminants (\seeref{discriminants}) match the running OS; it then overrides the previous definitions.

	\begin{lstlisting}
	#  Skip lcms2 on Debian-9
	@on deb,9 use lcms2:skip
	#  Use v2 of lcms2 on Fedora
	@on fed use lcms2:v2
	\end{lstlisting}

	\item[\code{@for <plug-in> use <modref>}] Gives the variant and/or version of a module when it is a dependency of \code{<plug-in>}.
	\label{formodule}

    \begin{lstlisting}
	@for c-darktable use c-exiv2/auto:v0.27.5
    \end{lstlisting}

	\item[\code{@alias <plug-in1> use <plug-in2>}] An alias for dependencies: when \code{<plug-in1>} is not found, \code{<plug-in2>} is used instead. This comes in handy to give a public alternative to a private plug-in.

	\begin{lstlisting}
	@alias private-plugin use alternative-plugin
	\end{lstlisting}

	\item[\code{[ <barrier> ... ] /variant:version}] A group: the modules of the group get the same variant and/or version. When a barrier is given, the group is used only if the barrier is true.

	A group is written as:

	\begin{description}
		\label{plan-barrier}
		\item[ {[} <barrier>] A square bracket and an optional barrier. The barrier is a condition: \code{=} or \code{/=} followed by names of variants of the build plan (the variants given with \code{\ddash{}plan=name/variant1.variant2}) or of discriminants (\seeref{discriminants}).

		Several names separated with commas must all be set:

		\code{= deb,9}

		A barrier can have up to three alternatives, separated with blanks. With \code{=} the barrier is true when one of them matches, with \code{/=} when none of them matches. For example:

		\begin{itemize}
		\item {[} = deb,9 deb,11

		is true on Debian 9 and 11;

		\item {[} /= deb,9 deb,11

		is true everywhere but on Debian 9 and 11.

		\end{itemize}

		Without a barrier the group is always used.

		\item[ {]} /variant:version ] The end of the group, with the variant and the version given to its modules. Both \code{variant} and \code{version} are optional.
	\end{description}

	Without a barrier, the group is always used:

	\begin{lstlisting}
		lcms2:v2
		[
			moduleA
			moduleB
		] /speed:v3
	\end{lstlisting}

	With a barrier on a variant (used with \code{\ddash{}plan=name/variant1.variant2} for example):

	\begin{lstlisting}
		lcms2:v2
		[ = variant1
			moduleA
			moduleB
		] /speed:v3
	\end{lstlisting}

	With a barrier on discriminants (used on Debian 10):

	\begin{lstlisting}
		lcms2:v2
		[ = deb,10
			moduleA
			moduleB
		] /speed:v3
	\end{lstlisting}
\end{description}

Finally, a build plan is used with the \ddash{}plan option:

\cmd{scbi \ddash{}plan=next lcms2 aws}

If a module is set to \code{skip} in the build plan, building its default version needs \code{force} on the command line:

\cmd{scbi \ddash{}plan=next lcms2:force aws}

Variants of the build plan, separated with dots, can be given after its name. In the following example the \code{mpi} variant of the build plan \code{next} is set: the groups with the barrier \code{= mpi} are used.

\cmd{scbi \ddash{}plan=next/mpi lcms2:force aws}

The \code{scbi show \ddash{}build-plan} command lists the resulting build plan (all modules with their variant and version, \seeref{listing}).

The build plan file is the first one found in this order:

\begin{description}
	\item[\code{\$PWD/.scbi-plan-<name>}] A local build plan in the current directory.

	\item[\code{\$SCBI\_PLUGINS/.plan-<name>}] A global build plan, with the plug-ins.
\end{description}

\subsection{Standalone source archive}
\label{standalone}
\index{source archive}

The \code{\ddash{}standalone} option creates a self-contained source archive: it embeds all the sources, the plug-ins and the driver needed to rebuild the software without access to the repositories or to the source archives.

A build script is at the root of the archive, so a build from such an archive boils down to:

\begin{description}
	\item[Uncompress] \cmd{tar xf sa-archive.tgz}
	\item[Enter the directory] \cmd{cd sa-archive}
	\item[Start the build] \cmd{./build}
\end{description}

The archive is created in \file{/tmp}, or in the directory given by the \code{SCBI\_TMP} variable (such an archive can be very large).

The file \file{build-deps} at the root of the archive contains the \code{apt} command installing all the external (OS) dependencies needed to build the software.

\subsection{Command line}

\subsubsection{Description}

The SCBI command line:

\cmd{scbi [command] [options] module-ref1 [module-ref2 ... module-refn]}

For a description of the module reference, \seeref{modref}.

Running \code{scbi} with \code{\ddash{}stat} and no module lists the available modules and build plans; with the completion activated, the \code{[TAB]} key lists them too (\seeref{completion}).

\subsubsection{Commands}
\label{cmdline}

The following sub-commands are available:

\begin{description}
	\item[show] Displays the build plan, the dependencies and the module references (\seeref{show}).

	\item[shell] Starts a shell, or runs a command, in the environment of modules (\seeref{shell}).

	\item[store] Handles the SCBI private store (\seeref{store}).

	\item[lint] Checks the syntax of plug-ins and reports possible errors (\seeref{linter}).

	\item[format] Rewrites YAML plug-ins in their canonical form (\seeref{formatter}).

	\item[replay] Reruns a step of a module from its replay file, or displays a script to run it by hand (\seeref{replay}).

	\item[source-archive] Creates a source archive from the VCS of a plug-in (\seeref{createsourcearchive}).
\end{description}

\subsubsection{Options}
\label{options}

The following options are supported:

\begin{description}[font=\texttt]
	\item[-h | \ddash{}help] Displays the usage and the options.

	\item[-v | \ddash{}version] Displays the version of the SCBI driver and of the plug-in distributions\footnote{A plug-in distribution gives its version with a file \file{.scbi*version.txt} installed next to the plug-ins.}.

	\item[-q | \ddash{}quiet] Does not display the information logs.

	\item[\ddash{}color:{[}no|light|dark{]}] Colored output for a \code{light} or \code{dark} console background. The default is \code{no}.

	\item[\ddash{}ini{[}=<section>{]}] Uses the given \code{section} of the ini files (\seeref{inifile}). Without a section only the global and common values are used.

	\item[\ddash{}prefix=<dir>] The global install directory, instead of \file{\$SCBI\_PREFIX}.

	\item[\ddash{}build-dir=<dir>] The build directory (sandbox), instead of \file{\$SCBI\_BDIR}.

	\item[\ddash{}flat] A flatter directory structure in the sandbox: the build directory of a module is moved at the top of the sandbox and named with a number. This comes in handy on Windows to avoid paths that are too long for the OS.

	\item[-e | \ddash{}env=<name>] Uses the environment file \file{.env-<name>.yaml} instead of the default \file{.env.yaml} (\seeref{build-env}).

	\item[\ddash{}plan=<name>{[}/<variants>{]}] Uses the build plan \file{.plan-<name>} with optional variants separated with dots (\seeref{build-plan}).

	\item[\ddash{}enable-<name>] Enables the feature \emph{name} (\seeref{enable-feature}).

	\item[-t | \ddash{}target=<name>] The target to build for, the host by default. Only needed for cross-compilation.

	\item[-S | \ddash{}no-setup] Skips the setup step.

	\item[-W | \ddash{}no-wrapup] Skips the wrapup step.

	\item[-I | \ddash{}no-install] Skips the install step.

	\item[-u | \ddash{}update] Updates the repositories before building.

	\item[-s | \ddash{}setup] Does the setup step (default).

	\item[-c | \ddash{}config] Does the config step (default).

	\item[-b | \ddash{}build]  Does the build step (default).

	\item[\ddash{}build-target=<target>] \index{build-target}The build step
	runs the \code{build-<target>} hook of the module instead of
	\code{build} (\seeref{hooks}).

	\item[-i | \ddash{}install] Does the install step (default).

	\item[\ddash{}clean-install] Cleans the install directory of the module before installing.

	\item[\ddash{}clear-cache] Clears the cache of the module plan, to recompute the automatic variants and the propagation of the meta-modules. This is done automatically in most cases, when:
	\begin{itemize}
		\item the build plan has changed (name or content);
		\item packages have been installed or removed (\code{apt}, \code{dnf}, \code{pacman});
		\item the discriminants of the OS have changed (name, version, etc.);
		\item the references of the modules of the command line have changed;
		\item the build target has changed.
	\end{itemize}
	Other changes are not detected, or too costly to detect.

	\item[-w | \ddash{}wrapup] Does the wrapup step (default).

	\item[\ddash{}archive] Uses an archive only when the module reference asks for one (\code{:\#<version>}). Without this option, an archive of the module found in the archive directory (\file{\$SCBI\_ARCHIVES}) is used.

	\item[\ddash{}tests{[:only]}{[=OPTIONS]}] Builds the module and runs its testsuite if any. With \code{only} the testsuite is run without building. \code{OPTIONS} is given to the \code{tests} hook (parameter \code{OPTIONS}, \seeref{tests-hook}).

	\item[-d | \ddash{}deps{[:warning]}] Checks all the dependencies and builds them if needed. With \code{warning}, a missing external dependency is reported but does not stop the build. Without this option only the modules of the command line are built: when there are several, they are built in an order where none comes before one of its dependencies (direct or not, through the modules of a meta-module too), the given order being kept otherwise, and the new order is displayed (\code{build order: ...}).

	\item[-a | \ddash{}create-archive] Creates a binary archive when the build succeeds.

	\item[\ddash{}standalone] Creates a standalone source archive (\seeref{standalone}).

	\item[-l | \ddash{}log:{[}yes|no|on-failure{]}] What is displayed of the command logs: everything, nothing, or (default \code{on-failure}) the end of the log of a failing step.

	\item[-f | \ddash{}force] Rebuilds, without checking whether the build id has changed.

	\index{build id}A module is rebuilt only when its build id changes. The build id is computed from the sources (the revision of the checkout, the archive), the module reference, the target and the OS, the build types, the patches, the values of the \code{external-env} hook, the build ids of the direct dependencies, and the plug-in \emph{resolved} for the module reference (as displayed by \code{scbi show \ddash{}resolved}, \seeref{show}). So a comment, a change of formatting or of the order of the keys (hooks, variables, functions, qualifiers) or of the dependencies (\code{depends}, \code{build-depends}, \code{tests-depends}: the \code{env} hooks of two dependencies setting the same variable are applied in this order, use \ddash{}force after swapping them), a hook of another variant or a guarded item not selected do not rebuild the module, while a change of a hook it uses, of a function or of a variable does, in its plug-in or in the ones it inherits. The \code{env} hook of a module is not part of its own build id: it sets the environment of the modules depending on it, so a change rebuilds these modules (it is part of their build id), not the module itself. The build id of the sandbox is removed when a build starts and written when it completes: an interrupted or failed build is redone at the next run (\code{trigger: not yet built}), even when the build id is the one of the previous build (a change of the plug-in reverted). The same holds for the wrapup of a meta-module.

	\item[-p | \ddash{}purge{[:only]}] Removes the build directory of the module, then builds it unless \code{only} is given.

	\item[\ddash{}dry-run] Only lists the modules to handle.

	\item[\ddash{}progress:{[}bar|line|no{]}] \index{progress}How the progress of
	the build is shown on a terminal (\code{bar} without argument and by
	default, see \code{SCBI\_PROGRESS}).

	\item[\ddash{}stat{[}:short|full{]}] Displays the setup (directories, discriminants...) and, without module, the available modules and build plans. With \code{short} only the setup is displayed; with \code{full} the build times of the modules are added.

	\item[-n | \ddash{}no-patch] Does not apply the patches.

	\item[-j | \ddash{}jobs=<n>] The number of parallel jobs, sets \code{SCBI\_JOBS} (\seeref{njobs}).

	\item[\ddash{}safe] Safe mode: when a module is built, its previous build directory is removed first, so that an old configuration or old build artifacts cannot interfere with the new build.

	\item[\ddash{}plugins=<directory>] The directory of the plug-ins, instead of \code{\$SCBI\_PLUGINS}.
\end{description}

A Bash completion is provided (\seeref{completion}): it gives the possible values of many options, like the build plans for \code{\ddash{}plan=}, and the modules.

\subsubsection{Options from INI file}
\label{inifile}

Options can be stored in ini files, in sections: \code{\ddash{}ini=<section>} activates a section. The global settings (at the beginning of the file, before any section) and the \code{common} section are always used, \code{common} taking precedence over the global settings. A sub-command also uses the section \code{scbi-<sub-command>}, for settings specific to it.

The ini files are:

\begin{itemize}
	\item \$HOME/.scbi
	\item \$PWD/.scbi
	\item \$SCBI\_INI\_FILE
\end{itemize}

The following keys are supported in the ini files:

\begin{itemize}
	\item \code{env}, \code{plan}, \code{target}: as the options of the same name;
	\item \code{root-dir}, \code{plugins}, \code{prefix}, \code{build-dir}, \code{git-repo}, \code{svn-repo}, \code{hg-repo}, \code{archives}, \code{patch}, \code{log}, \code{jobs}: the directories and settings \code{SCBI\_ROOT}, \code{SCBI\_PLUGINS}, \code{SCBI\_PREFIX}, \code{SCBI\_BDIR}, \code{SCBI\_GIT\_REPO}, \code{SCBI\_SVN\_REPO}, \code{SCBI\_HG\_REPO}, \code{SCBI\_ARCHIVES}, \code{SCBI\_PATCH}, \code{SCBI\_LOGS}, \code{SCBI\_JOBS};
	\item \code{setup}, \code{config}, \code{build}, \code{install}, \code{wrapup}, \code{color}, \code{quiet}, \code{force}, \code{update}, \code{purge}, \code{archive}, \code{stat}: the options of the same name (\code{yes} or \code{no}, or the value of the option);
	\item \code{safe}, \code{tar}, \code{no-patch}, \code{clear-cache}: the options of the same name when set to \code{yes};
	\item \code{deps}: \code{yes} for \ddash{}deps;
	\item \code{modules}: the modules to build, as on the command line;
	\item \code{enable}: the features to enable (comma or blank separated);
	\item \code{options}: other options, as on the command line;
	\item \code{run}: a command to run in the environment of the modules (as \code{scbi shell \ddash{}run}, \seeref{shell});
	\item \code{tests} (\code{yes} or \code{only}), \code{tests-list}: as \ddash{}tests.
\end{itemize}

Any other key is set as an exported variable (e.g. \code{SCBI\_PROGRESS = line}).

Example:

\begin{lstlisting}[language={Ini}]
prefix = $HOME/sandbox

[aws]
   env = std
   modules = c-aws

[common]
   git-repo = $HOME/dev/git
   jobs = 2

[scbi-show]
   stat = no
\end{lstlisting}

\section{Creating new plug-ins}

A new plug-in is a single YAML file (one per module) in
\code{\$SCBI\_PLUGINS}, named \file{<plug-in>.yaml}.

The plug-in describes, with hooks, the steps of the build: mainly the
configuration, the build and the installation, the main steps of most
software builds. The steps are a few commands (in the command language,
\seeref{yaml-command-language}); other hooks describe where to get the
sources (a repository or an archive), the dependencies and the environment.

The format of the file is described first, then all the hooks and the
order in which SCBI calls them.

\subsection{Plug-in format}
\label{yaml-plugin}
\index{YAML plug-in}

A plug-in is a YAML file named \file{<name>.yaml}. It is a recipe: the
driver only reads it.

\subsubsection{Structure}

The file is a mapping. The following keys are reserved, all the other ones
are hook names (including \code{pre-<step>} and \code{post-<step>}):

\begin{description}[font=\texttt]
	\item[plugin] The name of the plug-in (optional); it must match the file name.
	\item[vars] Variables of the plug-in, \code{\{NAME: value\}}, available in all its hooks.
	\item[variants] Variants including other variants
	(\seeref{yaml-variants}), \code{\{all: [ai, hdr, jxl]\}}.
	\item[inherit] List of inherited plug-ins (\seeref{inheritance}), each
	one a mapping with the keys \code{from}, \code{hooks},
	\code{custom-hooks}, \code{no-variant} and \code{name}.
	\item[with-variants] Variants with no build step, which only depend on
	other modules or OS packages (e.g. a \code{native} variant using the OS
	libraries, \seeref{native variant}):
	\code{\{native: \{packages: [...], env: [...]\}\}}.
	\item[functions] Functions callable from the command hooks (or used
	as custom hooks with \code{inherit}), written in the command language:
	\code{\{name: \{params: [A, B], run: <commands>\}\}}.
\end{description}

All scalars are strings: \code{yes}, \code{no}, \code{true} or
\code{1.10} are never converted to booleans or numbers.

\subsubsection{Hooks and variants}

The value of a hook is either its body (the plain hook) or a mapping where each key names \emph{exactly one} qualifier:
\code{\_} (the plain hook), \code{common} (cumulative hooks only),
\code{default} or a variant name. The key \code{cross} holds the same kind of
mapping (or directly a body), used when the target is not the host. There is
no key combining variants: for a module reference \code{m/a.b} the driver
takes the first variant defined for a hook like \code{config} or
\code{install}, and all of them for a cumulative hook like \code{depends}
or \code{config-options} (\seeref{hooks}, \emph{Calling order}).

\begin{lstlisting}
plugin: c-gmp
with-variants:
  native:
    packages: [os@-gmp-dev:[v]]
    env: [set-var GMP_INCLUDE_DIR /usr/include]
vcs:
  proxy: default
  options: none
  protocol: mercurial
  url: https://gmplib.org/repo/gmp/
build-depends: [c-sandbox]
depends:
  vcs: [os@-autotools-dev, os@-automake]
env:
  - add-to-var C_INCLUDE_PATH $PREFIX/include
  - add-to-var LD_LIBRARY_PATH $PREFIX/lib
out-of-tree: false
config:
  _: ./configure --prefix=$PREFIX
  vcs: ./configure --enable-maintainer-mode --prefix=$PREFIX
  cross:
    _: ./configure --prefix=$PREFIX/$TARGET --host=$TARGET
build: make -j$SCBI_JOBS
install: make install
\end{lstlisting}

\subsubsection{Variants including other variants}
\label{yaml-variants}
\index{YAML plug-in!variants}\index{variant!including variants}

A variant can be defined as including other variants, to share their
definitions without repeating them:

\begin{lstlisting}
variants:
  all: [ai, hdr, jxl]
\end{lstlisting}

For the module reference \code{c-darktable/all} the driver looks up the
hooks of the variants \code{all ai hdr jxl}, in this order: each variant
is followed by the variants it includes (recursively), and a variant
already listed is not repeated. So \code{all} gets the \code{depends} of
\code{ai}, \code{hdr} and \code{jxl} (a cumulative hook) and, for a hook
like \code{config}, the first one defined for \code{all}, \code{ai},
\code{hdr} or \code{jxl}. A hook defined for \code{all} itself is still
used.

Only the lookup of the hooks is affected: the variant keeps its name for
the sandbox directory, the build identifier, the logs and the build
plans.

\subsubsection{Hook bodies}
\label{yaml-hook-bodies}

The parameters of a hook are defined by SCBI (for example
\code{PREFIX TARGET VARIANT} for \code{config}, \code{VERSION} for
\code{archive}, \code{PREFIX TARGET VARIANT KIND REF} for \code{patches},
\code{PREFIX TARGET VARIANT OPTIONS} for \code{tests}, \seeref{hooks}). They
are variables of the body and are not declared in the plug-in.

There are three kinds of hooks:

\begin{description}
	\item[command hooks] \code{setup}, \code{config}, \code{build},
	\code{install}, \code{wrapup}, \code{tests}, \code{version}, \code{run}
	and the \code{pre-}/\code{post-} steps. The body is a text in the
	command language (\seeref{yaml-command-language}), run by the driver
	without any shell. A syntax error is reported, with its line, when the
	plug-in is loaded.
	\item[value hooks] \code{vcs}, \code{archive}, \code{depends},
	\code{patches}, \code{config-options}, \code{prefix},
	\code{out-of-tree}... The body is a list of values (a single value can be
	given as a string). \code{vcs} and \code{archive} can also be given as a
	mapping of their fields (\code{proxy}, \code{options}, \code{protocol},
	\code{url}, \code{file}, \code{dir}).
	\item[environment hooks] \code{env}, \code{build-env},
	\code{tests-env}. The body is a list of actions, \code{<action>
	<arguments>}, applied in order: \code{set-var PATH /usr/bin},
	\code{add-to-var CPATH \$PREFIX/include}... The actions are described in
	\seeref{set-env}.
\end{description}

Values and environment actions are not shell code: they are expanded by the
driver (\seeref{yaml-expansion}). An item of a value or environment list can
be guarded by a condition (\seeref{yaml-conditions}).

\subsubsection{Expansion}
\label{yaml-expansion}
\index{YAML plug-in!expansion}

The values, the arguments of the environment actions and the words of the
commands are expanded as follows:

\begin{description}
	\item[\$VAR, \$\{VAR\}] The value of a variable: a hook parameter, a
	variable of the plug-in (\code{vars}), a local variable, a driver
	variable (\code{SCBI\_*}) or an environment variable.
	\item[\$\{VAR:-default\}] The value, or \code{default} when the
	variable is empty.
	\item[\$\{VAR:+word\}] \code{word} when the variable is not empty,
	else nothing.
	\item[\$\{VAR\%pattern\}, \$\{VAR\%\%pattern\}] The value without the
	shortest (\code{\%}) or longest (\code{\%\%}) suffix matching the glob
	pattern.
	\item[\$\{VAR\#pattern\}, \$\{VAR\#\#pattern\}] The value without the
	shortest (\code{\#}) or longest (\code{\#\#}) prefix matching the glob
	pattern.
	\item[\$\{VAR/pattern/string\}, \$\{VAR//pattern/string\}] The value with
	the first (\code{/}) or every (\code{//}) part matching the pattern
	replaced by \code{string} (\code{\textbackslash/} for a \code{/} in the
	pattern).

	The patterns, words and strings of these forms are expanded first: they
	can use variables, e.g. \code{\$\{VALUE\#\$PREFIX/\}}.
	\item[{\$\{SCBI\_MODULES\_DIR[<module>[@src|@build]]\}}] The install,
	source or build directory of a module (\seeref{build-env}).
	\item[\$(<function> <args>)] The result of a function
	(\seeref{yaml-functions}). The arguments are expanded as in a shell,
	including unquoted glob patterns.
\end{description}

\index{local variable (in values)}
An item \code{NAME = <value>} of a value or environment list sets a local
variable for the following items of the list (it gives no value and is not
part of the environment). When \code{<value>} starts with a function name
the variable is the result of the function (\code{BT = get-build-type
CMAKE Release} is \code{BT = \$(get-build-type CMAKE Release)}), else it
is \code{<value>} expanded. For example:

\begin{lstlisting}
config-options:
  - BT = get-build-type CMAKE Release
  - -DLLVM_ENABLE_ASSERTIONS=$(if $BT == Debug then ON else OFF)
  - -DOPT=$(uppercase $VARIANT)
\end{lstlisting}

The same option without a variable:
\code{-DLLVM\_ENABLE\_ASSERTIONS=\$(if build-type(CMAKE,Release) == Debug
then ON else OFF)}.

\subsubsection{Functions}
\label{yaml-functions}
\index{YAML plug-in!functions}

The functions below are evaluated by the driver. They are called as
\code{\$(<function> <args>)} in values, environment actions and the words
of commands, or as \code{NAME = <function> <args>} in an assignment (a
local variable of a value list, \seeref{yaml-expansion}, or a variable of a
command hook, \seeref{yaml-command-language}). The functions marked
\emph{(commands)} are only available in command hooks, the ones marked
\emph{(final step)} only in the function \code{module-final-step} of an
environment file (\seeref{module-final-step}).

A function gives a value or a list. In a command, a list alone in an
unquoted word gives one word per element (an element with blanks stays one
word, an empty list no word); elsewhere the elements are joined with
spaces, e.g. \code{cmake \$(config-options) ../src}.

\begin{itemize}
	\item Information on the build:

\begin{description}
	\item[get-version {[<plug-in>]}] The version of the module in the build plan, or with an argument the version of the given plug-in (for this module, as the condition \code{version(<plug-in>)}). \code{NONE} when the build plan gives no version.
	\item[get-build-type <kind> <default>] The build type of the module
	(\seeref{build-kind}): \code{\$SCBI\_<module>\_BUILD\_TYPE}, else
	\code{\$SCBI\_<kind>\_BUILD\_TYPE}, else \code{<default>}.
	\item[is-enabled <feature> {[<then>]} {[<else>]}] \code{<then>}
	(default \code{yes}) when the feature is enabled for the module, else
	\code{<else>} (default empty) (\seeref{enable-feature}).
	\item[config-options] \emph{(commands)} The list of the values of the
	\code{config-options} hooks of the module for its variant
	(\seeref{config-options}).
	\item[all-variants <variant>] \emph{(commands)} The list of the
	variants of a variant string (\code{a.b} gives \code{a} and \code{b}),
	empty for \code{default}.
	\item[all-modules] \index{all-modules}\emph{(commands)} The list of
	the modules of the build of the module, in build order: its
	dependencies (all kinds), the meta-modules and the modules they
	aggregate, and the module itself. The status of each one is given by
	the conditions \code{depends-kind(\$M)}, \code{is-meta(\$M)},
	\code{is-aggregate(\$M)} and \code{is-aggregated(\$M)}
	(\seeref{yaml-conditions}). For example, to keep the modules installed
	on their own: \code{if depends-kind(\$M) == default and not
	is-aggregated(\$M):}.
	\item[hook-output <module> <hook> {[<args>]}] \index{hook-output}
	\emph{(commands)} The output of a hook of another module (its variant
	is the one of the build plan), called with the arguments: for example a
	custom hook, the function \code{<module>-<hook>} of its plug-in. Empty
	when the module has no such hook. For a value hook (\code{modules},
	\code{depends}...) the list of its values.
\end{description}

\item Files and the system:

\begin{description}
	\item[last-modified-directory <glob>] The most recently modified file
	or directory matching the pattern, empty when none matches.
	\item[ls <glob>...] The files matching the patterns, one per line (as
	\code{ls}).
	\item[basename <path>] The last component of the path.
	\item[dirname <path>] The path without its last component (\code{.}
	when there is none).
	\item[get-os-inc-dir <file>] The directory of a header file of the
	system (\file{/usr/include}...).
	\item[get-os-lib <file>, get-os-lib-dir <file>] A library of the system
	(\code{libGL.so}, \code{serial/libhdf5.so}...) and its directory.
	\item[get-os-bin <program>, get-os-bin-dir <program>] A program of the
	system (\file{/usr/bin}...) and its directory.
	\item[command-path <tool>] The full path of the tool found in
	\code{PATH}, empty when not found (as \code{command -v}).
	\item[store-key <key>] The value of a key of the private store
	(\seeref{store}), empty when not found.
\end{description}

\item Commands:

\begin{description}
	\item[output <command line>] The standard output of the command (run
	without shell), without its final newlines. In a command hook the
	status of the command is the status of the step.
	\item[output-words <command line>] \emph{(commands)} The words of the
	standard output of the command, as a list.
	\item[status] \emph{(commands)} The exit status of the previous step
	(\code{\$?} in a shell).
\end{description}

\item Text:

\begin{description}
	\item[uppercase <words>, lowercase <words>] The words in upper or lower
	case.
	\item[replace <value> <chars1> {[<chars2>]}] \index{replace}The value
	with each character of \code{<chars1>} replaced by the character at the
	same position in \code{<chars2>} (both of the same length), or removed
	when \code{<chars2>} is empty or not given. For example \code{\$(replace
	\$PYTHON\_VERSION . '')} gives \code{312} for \code{3.12}. A value with
	blanks is quoted.
	\item[first-line <value>] \emph{(commands)} The first line of the
	value.
	\item[if <condition> then <words> {[else <words>]}] \index{if (in values)}
	The words after \code{then} when the condition (\seeref{yaml-conditions})
	is true, else the words after \code{else} (nothing without \code{else}).
	\code{then} and \code{else} are keywords only outside quotes and
	parentheses. The words may contain other function calls:
	\code{\$(if cross then \$(config-options) else -DNATIVE=ON)}.
\end{description}

\item The final step of a module (\seeref{module-final-step}):

\begin{description}
	\item[env-actions {[<hook> [<modref>]]}] \index{env-actions}
	\emph{(final step)} The environment actions of the \code{env} hook (or
	of \code{<hook>}) of the module (or of \code{<modref>}), and of the
	modules it aggregates for a meta-module: a list of triples, action
	(\code{ADD}, \code{SET}...), variable and value (possibly empty), to use
	with a \code{for} with three names: \code{for A V X in
	\$(env-actions):}.
	\item[module-ref <modref>] \index{module-ref}\emph{(final step)} The
	module, variant, kind and reference of a module in the build plan (a
	list of four words).
	\item[module-name <modref>] \index{module-name}\emph{(final step)} The
	name of the module (for a meta-module, its full name).
	\item[target-dir <module> <variant> {[<sub>]}] \index{target-dir}
	\emph{(final step)} The install directory of the module variant, with
	the sub-directory.
\end{description}
\end{itemize}

\subsubsection{Conditions}
\label{yaml-conditions}
\index{YAML plug-in!condition}

Conditions are used to guard the items of value and environment lists, in
\code{\$(if ...)} and in the \code{if} blocks of command hooks. An item of
a list is guarded with a mapping of a single key \code{if <condition>},
whose value is an item or a list of items:

\begin{lstlisting}
patches:
  - fix-common.diff
  - if ref =~ ^7.8: fix-7.8.diff
  - if version(lib2) > 1.9: [a.diff, b.diff]
build-env:
  - if target =~ mingw32: set-var OS Windows_NT
\end{lstlisting}

A condition compares two operands with \code{==}, \code{!=},
\code{=\textasciitilde} (regular expression), or \code{<}, \code{<=},
\code{>}, \code{>=} (versions, as \code{check-module-version},
\seeref{check-version}); an operand alone is true when it is true or not
empty. Conditions are combined with \code{not}, \code{and}, \code{or} and
parentheses. The operands are:

\begin{description}
	\item[ref] The version of the module.
	\item[target, host] The target and host triplets.
	\item[cross] True when the target is not the host.
	\item[variant] The variant of the module.
	\item[kind] The kind of the module version (\code{DEV}, \code{BRANCH},
	\code{VERSION}...).
	\item[version(<plug-in>)] The version of a module in the build plan (as \code{\$(get-version <plug-in>)}).
	\item[build-type(<kind>{[,<default>]})] As the function
	\code{get-build-type}.
	\item[enabled(<feature>)] True when the feature is enabled.
	\item[on <discriminants>] True when all the discriminants (separated
	with commas) are set, as in build plans (\seeref{discriminants}).
	\item[exists(<path>)] True when the path exists.
	\item[empty(<value>)] True when the value is empty
	(\code{empty(\$VAR)}).
	\item[dir(<module>)] The install directory of a module (environment
	hooks only).
	\item[\$VAR, "text"] A variable, a quoted string; unquoted words are
	strings too.
	\item[is-dir(<path>), is-file(<path>), is-link(<path>)]
	\emph{(commands)} True when the path is a directory, a regular file, a
	symbolic link.
	\item[ok("<command line>")] \emph{(commands)} True when the command
	succeeds. Any command or built-in, with arguments and redirections; its
	standard output is discarded, its error output is shown unless
	redirected (\code{2> /dev/null}).
	\item[status] \emph{(commands)} The exit status of the previous step,
	e.g. \code{status == 0}.
	\item[depends-kind(\$M), is-meta(\$M), is-aggregate(\$M), is-aggregated(\$M)]
	\emph{(commands)} The status of a module of \code{all-modules}: the
	kind of dependency (\code{default}, \code{build} or \code{tests}), a
	meta-module, a meta-module aggregating its modules, a module installed
	in an aggregate.
\end{description}

Conditions never select between variants: this is done with the
qualifiers (\seeref{yaml-plugin}).

\subsubsection{Command language}
\label{yaml-command-language}
\index{YAML plug-in!command language}

The command hooks and the functions of a plug-in are written in a small
command language interpreted by the driver: no shell is involved.
External commands are run as processes in the environment of the hook
(\seeref{hookenv}), the built-ins are part of the driver. A body is a text
block, one step per line; \code{\#} starts a comment, blank lines are
ignored and a line ending with \code{\textbackslash} continues on the next
one. Blocks are given by indentation:

\begin{lstlisting}
config: |
  BT = get-build-type CMAKE Release
  if not is-link(../src/.git):
      ln -s ../../src/.git ../src/.git
  if cross:
      cmake -DCMAKE_BUILD_TYPE=$BT -DTARGET=$TARGET $(config-options) ../src
  else:
      cmake -DCMAKE_BUILD_TYPE=$BT $(config-options) ../src
version: |
  write prj.gpr:
      with "aunit";
      project prj is end prj;
  if ok("gprbuild -p -q $(if cross then --target=$TARGET) prj.gpr 2> /dev/null"):
      echo $VERSION_OK
  else:
      echo $VERSION_ERROR
\end{lstlisting}

\textbf{Commands.} A command line is split into words as by a shell
(quotes, backslash) and each word is expanded (\seeref{yaml-expansion}).
Unquoted glob patterns are replaced by the matching files (left as they are
when nothing matches). A variable holding a list gives a word per element;
other values are never split; an unquoted word expanding to nothing is
removed. Leading \code{NAME=value} words set the environment of the command
only. \code{\&\&}, \code{||}, pipes \code{|} and the redirections
\code{>}, \code{>>}, \code{<}, \code{2>}, \code{2>>}, \code{2>\&1},
\code{\&>} work as in a shell.

\textbf{Assignments.} \code{NAME = <words>} sets a variable of the hook
(one word gives a value, several a list); \code{NAME = <function> <args>}
sets it to the result of a function (\seeref{yaml-functions}). The
variables are local to the hook call; \code{export NAME = ...} also puts
the variable in the environment of the following commands.

\textbf{Built-in commands.} \index{YAML plug-in!built-in commands}
They run in the driver; any other command is an external program or a
function of the plug-in.

\begin{description}
	\item[cd {[<dir>]}] \index{cd}Changes the current directory of the hook
	(\code{\$HOME} without argument); fails when the directory does not
	exist. \code{\$PWD} is the current directory.
	\item[echo {[-n]} <words>] \index{echo}Writes the words separated by a
	space, followed by a newline unless \code{-n} is given. It gives the
	output of a hook returning a value (\code{version}...).
	\item[return {[N]}, exit {[N]}] \index{return}\index{exit}End the
	hook (or the plug-in function) with the status \code{N} modulo 256
	(\code{return -1} is 255), or with the status of the previous step.
	\item[true, :, false] Succeed (\code{true}, \code{:}) or fail
	(\code{false}), doing nothing.
	\item[export NAME{[=value]}...] \index{export}Puts the variables in
	the environment of the following commands, setting them first when a
	value is given.
	\item[unset NAME...] \index{unset}Removes the variables from the hook
	and from its environment.
	\item[check-versions <v1> <op> <v2>] \index{check-versions}Succeeds
	when the comparison of the two versions is true; \code{<op>} is one of
	\code{=}, \code{==}, \code{!=}, \code{<}, \code{<=}, \code{>},
	\code{>=}.
	\item[copy <source>... <destination>] \index{copy}Copies files and
	directories, directories always recursively (symbolic links are
	copied as links), as \code{cp -r}: into \code{<destination>} when it
	is an existing directory (it must be one for several sources), else to
	\code{<destination>}. Existing files are replaced, existing
	directories merged. It has no option; the system \code{cp} is still
	available for other options (\code{cp -a}...).
	\item[delete <path>...] \index{delete}Deletes files and symbolic links,
	as \code{rm -f}. A directory is an error (use \code{delete-tree}), so
	that a path which turns out to be a directory (an empty variable in
	\code{\$DIR/\$NAME}...) is not deleted.
	\item[delete-tree <path>...] \index{delete-tree}Deletes files and
	directories, directories recursively, as \code{rm -fr}.

	Both delete only in the sandbox (\code{\$SCBI\_BDIR}): the location of
	each path (its directory with \code{..} and symbolic links resolved,
	then its name) must be under the sandbox. All the paths are checked
	first: on an error nothing is deleted and the command fails. A symbolic
	link is deleted, not its target; a missing path is not an error. They
	have no option.
	\item[log <level> <message>] \index{log}Displays a message for the
	user, as a message of the driver: with the time-stamp and indented by
	two spaces per level (\code{<level>}, an integer >= 1), on the console
	(not with \ddash{}quiet), in the report log of the module and in the
	logs of the step. It tells what a long hook is doing, for example in a
	wrapup:

\begin{lstlisting}
wrapup: |-
  log 1 working on step 1
  ...
  log 2 working on step 2.1
\end{lstlisting}

	gives

\begin{lstlisting}
2026/11/19 14:25:55 : wrapup starting
2026/11/19 14:25:59 :   working on step 1
2026/11/19 14:25:59 :     working on step 2.1
2026/11/19 14:33:39 : wrapup completed
\end{lstlisting}

	The message is the other words, joined by a space. In the
	\code{module-final-step} function of an environment file it is a
	message for the module. Without the driver (\code{scbi replay}) the
	message is written indented, without time-stamp.
	\item[apply-var <action> <variable> {[<value>]}] Applies an environment
	action, in the function \code{define-var} of an environment file only
	(\seeref{define-var-override}).
	\item[<function> <args>] A function of the plug-in (\code{functions:}),
	its parameters set to the arguments.
\end{description}

\textbf{Blocks.} \index{YAML plug-in!blocks of commands}
A block line ends with \code{:}; its body is the following lines indented
more than it.

\begin{description}
	\item[if <condition>:] Runs its body when the condition
	(\seeref{yaml-conditions}) is true. It can be followed by any number of
	\code{elif <condition>:} and by an \code{else:}: the first branch whose
	condition is true is run.
	\item[for NAME in <words>:] Runs its body once for each word, with
	\code{NAME} set to the word. The words are expanded as the ones of a
	command (a list variable gives its elements, glob patterns the matching
	files).
	\item[for NAME1 NAME2... in <words>:] With several names the words are
	taken by groups: the body is run with \code{NAME1} set to the first word
	of each group, \code{NAME2} to the second... (empty for the missing words
	of the last group). For example \code{for A V X in \$(env-actions):}
	(\seeref{module-final-step}).
	\item[write FILE:] Writes the body, expanded, to the file (created or
	truncated); \code{\textbackslash\$}, \code{\textbackslash`} and
	\code{\textbackslash\textbackslash} give the character, as in a
	here-document.
	\item[append FILE:] As \code{write}, appending to the file.
	\item[write-raw FILE:, append-raw FILE:] As \code{write} and
	\code{append}, the body not expanded.
\end{description}

\textbf{Status.} The status of a body is the status of its last step: a
failing command does not stop the body, unless the next one is chained with
\code{\&\&}. An error message gives the plug-in file, the hook and the
line.

\subsection{Hooks}
\label{hooks}

Each hook is a key of the plug-in file, all of them are optional. In
this reference a hook which can be given per variant is written
\code{<hook> [<variant>]} and \code{<hook> [common|<variant>]} for the
cumulative hooks (\seeref{yaml-plugin}). The parameters are variables
of the hook body; the result of a value hook is its list of values.

\subsubsection{Description}

\begin{description}[font=\large\texttt]

	\item[vcs {[}<variant>{]}] \index{hook!vcs}Describes the VCS of the module sources.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} NONE
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item proxy: the name of a proxy, or \emph{default} for the default one of the system (\seeref{proxy}).
			\item options: a comma-separated list of options: \emph{none}, \emph{no-recursive}, \emph{lfs}, \emph{submodule:PATH:URL}. The latter changes the \code{URL} of a submodule when the repository is cloned or updated; several \emph{submodule} options can be given.
			\item protocol: \emph{git}, \emph{svn}, \emph{hg}.
			\item URL: the location of the repository, with its protocol.
			\item DIR (optional): the directory of the module when the repository hosts several projects, mostly for non-standard Subversion layouts. If \code{URL} points to the tree containing the \code{trunk}, \code{branches} and \code{tags} directories, SCBI looks for the sources in:
			\begin{itemize}
				\item \code{<root>/trunk/\$DIR}
				\item \code{<root>/[branches|tags]/<VER>/\$DIR}
				\item \code{<root>/[branches|tags]/\$DIR/<VER>}
			\end{itemize}.
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
vcs:
  proxy: default
  options: none
  protocol: git
  url: http://github.com/mm2/Little-CMS
\end{lstlisting}

	The fields can also be given as a list of values, in this order. The
	\code{vcs} hook of a given variant can be selected by the environment:

	\begin{description}[style=standard]
		\item[\code{SCBI\_<module>\_VCS\_VARIANT}] \hfill \\
		When set, the \code{vcs} hook of the variant \code{\$\{SCBI\_<module>\_VCS\_VARIANT\}} of the module \code{<module>} is used before the other ones.

		\item[\code{SCBI\_VCS\_VARIANT}] The same for all the modules.
	\end{description}

	\index{rewrite!rewrite-vcs}
	Finally, the function \code{rewrite-vcs} of the environment
	file (\seeref{env-files}) receives the five values of the
	\code{vcs} hook and prints them, possibly rewritten.

	\item[archive {[}<variant>{]}] \label{hookarchive}\index{hook!archive}Describes the archive of the module sources: its name and location.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$VERSION}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
		\item proxy: the name of a proxy, or \emph{default} for the default one of the system (\seeref{proxy}).
		\item options: the options given to the download tool (see protocol below), or \emph{none}.
		\item protocol: \emph{scp}, \emph{cp}, \emph{wget}, \emph{curl}, \emph{ftp}, \emph{none}.
		\item URL: where the archive can be downloaded.
		\item file: the name of the archive, possibly with \$VERSION.
		\item DIR (optional): the directory of the sources (possibly with \$VERSION) when the archive hosts several projects.
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
archive:
  proxy: default
  options: --no-check-certificate
  protocol: wget
  url: http://some.server.fr/sources
  file: cmake-$VERSION.tar.gz
\end{lstlisting}

	The \code{archive} hook of a given variant can be selected by the environment:

	\begin{description}[style=standard]
		\item[\code{SCBI\_<module>\_ARCHIVE\_VARIANT}] \hfill \\
		When set, the \code{archive} hook of the variant \code{\$\{SCBI\_<module>\_ARCHIVE\_VARIANT\}} of the module \code{<module>} is used before the other ones.

		\item[\code{SCBI\_ARCHIVE\_VARIANT}] The same for all the modules.
	\end{description}

	\index{rewrite!rewrite-archive}
	Finally, the function \code{rewrite-archive} of the
	environment file (\seeref{env-files}) receives the six values of
	the \code{archive} hook and prints them, possibly rewritten.

	\item[patches {[}common|<variant>{]}] \index{hook!patches}The patch files to apply (in \code{\$SCBI\_PATCH}). \code{REF} is the version of the module, to apply a patch to some versions only.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT \$KIND \$REF}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <patch-file-1>
			\item <patch-file-2>
			\item if ref =\textasciitilde{} 7.8: <patch-for-7.8>
			\item ...
		\end{enumerate}
	\end{description}

	\item[version {[}<variant>{]}] \index{hook!version}A command hook printing the version of the installed module.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} version or \code{\$VERSION\_OK} or \code{\$VERSION\_ERROR}
		\begin{enumerate}
			\item the version of the installed module, or \$VERSION\_OK (installed, version unknown) or \$VERSION\_ERROR (not installed or not working).
		\end{enumerate}
	\end{description}

	\item[external-env {[}common|<variant>{]}] \index{hook!external-env}Values added to the build identifier of the module: the module is rebuilt when they change. This is needed when the build depends on an external setting. The values have no meaning, they must only change with the setting: the value of the controlling variable is generally enough.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} value
		\begin{enumerate}
			\item \code{\$SOME\_VAR}
		\end{enumerate}
	\end{description}

	\item[build-depends {[}common|<variant>{]}] \index{hook!build-depends}The modules needed to build the module but not to use it: generally tools like \code{cmake}, \code{swig} or \code{gcc}. A dependency can be a full module reference (\seeref{modref}), with a variant and/or a version, but this is generally a bad idea: to keep the plug-in generic, give the module name only and set the variant and version in a build plan.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <module1>
			\item <module2>
			\item ...
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
build-depends: [gnat]
\end{lstlisting}

	\item[tests-depends {[}common|<variant>{]}] \index{hook!tests-depends}The modules needed to run the testsuite of the module: generally tools or frameworks like \code{cunit}, only needed by the tests.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <module1>
			\item <module2>
			\item ...
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
tests-depends: [libcunit1]
\end{lstlisting}

	\item[depends {[}common|<variant>{]}] \index{hook!depends}The modules needed to build and to use the module: other SCBI modules or packages of the distribution (\seeref{os-deps}). As for \code{build-depends}, give the module name only and set the variant and version in a build plan.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <module1>
			\item <module2>
			\item ...
		\end{enumerate}
	\end{description}

	Example:
	\begin{lstlisting}
depends:
  - xmlada
  - asis
\end{lstlisting}

	\item[env {[}common|<variant>{]}] \index{hook!env}The environment needed to use the module: it is set for the modules depending on it (and for its own steps). The actions are described in \seeref{set-env}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\begin{enumerate}
			\item \code{add-to-var} <name> <value>
			\item ...
		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}

	Example:
	\begin{lstlisting}
env:
  - add-to-var PKG_CONFIG_PATH $PREFIX/lib/pkgconfig
  - add-to-var PATH $PREFIX/bin
\end{lstlisting}

	\item[build-env {[}common|<variant>{]}] \index{hook!build-env}The environment needed to build the module.
	It is only set for the steps of the module, not for the modules depending on it.

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\begin{enumerate}
			\item set-var <name> <value>
			\item ...
		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}

	Example:
\begin{lstlisting}
build-env:
  - set-var PATH /some/path/bin
\end{lstlisting}

	\item[tests-env {[}common|<variant>{]}] \index{hook!tests-env}The environment needed to run the testsuite of the module (\ddash{}tests), in addition to the one of its \code{tests-depends}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} NONE
	\end{description}

	\item[setup {[}<variant>{]}] \index{hook!setup}Puts the sources in place before the configuration. This is generally not needed, as SCBI sets up the sources from the \code{vcs} or \code{archive} hook; it is useful in complex cases, or when the sources depend on the running environment.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} NONE
	\end{description}

	\item[out-of-tree {[}<variant>{]}] \index{hook!out-of-tree}Whether the module is built out of its source tree (in \file{build}) or in it. Default is \code{true}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} \code{\textbf{true} | false}
	\end{description}

	Example:
	\begin{lstlisting}
out-of-tree: false
\end{lstlisting}

	\item[only-explicit-build {[}<variant>{]}] \index{hook!only-explicit-build}When \code{true}, the module is only built when it is on the command line, not as a dependency; as a dependency its environment is still used. Default is \code{false}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} \code{true | \textbf{false}}
	\end{description}

	Example:
	\begin{lstlisting}
only-explicit-build: false
\end{lstlisting}

	\item[config {[}<variant>{]}] \index{hook!config}Configures the sources before the build, generally with GNU \code{configure} or \code{cmake}. The source tree is always \code{../src}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\begin{enumerate}
			\item ./configure \ddash{}prefix=\$PREFIX ../src
		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}
	Example:
\begin{lstlisting}
config: |-
  cmake $(config-options) ../src
\end{lstlisting}

	\item[config-options {[}common|<variant>{]}] \index{hook!config-options}The options of the configuration: the \code{config} hook gives them to \code{cmake} or \code{configure} with \code{\$(config-options)} (\seeref{get config options}).
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET [\$VARIANT]}
		\item[return] \tabto{2cm} array
		\begin{enumerate}
			\item <option1>
			\item <option2>
			\item ...
		\end{enumerate}
	\end{description}
	Example:
\begin{lstlisting}
config-options:
  common:
    - -DCMAKE_INSTALL_PREFIX=$PREFIX
    - -DCMAKE_C_COMPILER=$CMAKE_C_COMPILER
    - -DCMAKE_CXX_COMPILER=$CMAKE_CXX_COMPILER
  default:
    - -DCMAKE_BUILD_TYPE=RelWithDebInfo
\end{lstlisting}

	\item[build {[}<variant>{]}] \index{hook!build}Builds the module, generally with \code{make}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\begin{enumerate}
			\item make
		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}
	Example:
\begin{lstlisting}
build: make -j$SCBI_JOBS
\end{lstlisting}

	\item[build-<target> {[}<variant>{]}] \index{hook!build-<target>}The
	command run instead of \code{build} when the option
	\code{\ddash{}build-target=<target>} is given, e.g. a \code{build-runtime}
	hook to rebuild only the runtime of a compiler. It is resolved as
	\code{build} (variants, \code{cross:}); \code{build} is only replaced
	when the module has a \code{build} hook, and it is an error if it has no
	\code{build-<target>} hook. \code{<target>} is made of letters, digits,
	\code{\_} and \code{-} (and is not \code{env} or \code{depends}).
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} NONE
	\end{description}

	Example:
	\begin{lstlisting}
build-runtime: make -C gcc -j$SCBI_JOBS gnatlib
\end{lstlisting}

	\item[install {[}<variant>{]}] \index{hook!install}Installs the module in \code{\$PREFIX}, generally with \code{make install}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\begin{enumerate}
			\item make install
		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}

	\item[wrapup {[}<variant>{]}] \index{hook!wrapup}Whatever is needed after the installation.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} NONE
	\end{description}

	\item[prefix {[}<variant>{]}] \index{hook!prefix}The global install directory of the module: \code{NONE} skips the global installation (the module is only installed in its sandbox). Without this hook the module is installed in \code{\$SCBI\_PREFIX}.
	\label{global-install}
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} string
		\begin{enumerate}
			\item <install\_dir>
			\\ or
			\item NONE
		\end{enumerate}
	\end{description}

	\item[tests {[}<variant>{]}] \index{hook!tests}Runs the testsuite of the module (\ddash{}tests).
	\label{tests-hook}
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT [\$OPTIONS]}
		\item[return] \tabto{2cm} NONE
	\end{description}

	\item[run {[}common|<variant>{]}] \index{hook!run}The command line run by \code{scbi shell \ddash{}run} without argument (\seeref{cmd!run}).

	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\begin{enumerate}
			\item myprog
			\item option1
			\item option2...
		\end{enumerate}
		\item[return] \tabto{2cm} NONE
	\end{description}

\end{description}

\subsubsection{Calling order}
\index{hook!calling order}

The hooks giving information (\code{vcs}, \code{archive}, \code{version}, \code{patches}, \code{external-env}, \code{out-of-tree}, \code{prefix}, the dependencies, the environments, \code{config-options}, \code{run}...) are called by the driver when needed, in no specific order.

The steps are run in this order:

\begin{enumerate}
	\item setup
	\item config
	\item build
	\item install
	\item tests (with \ddash{}tests)
	\item wrapup
\end{enumerate}

For each step the driver may have a generic internal step, and the plug-in
can define \code{pre-} and \code{post-} hooks; they run in this order:

\begin{description}[font=\texttt,style=nextline]
	\item[generic pre-<step>] \index{hook!pre-}The internal pre-step of the driver (\code{pre-install} removes the previous installation).
	\item[pre-<step>] The \code{pre-<step>} hook of the plug-in.
	\item[<step>] The hook of the step.
	\item[generic <step>] The internal step of the driver (for \code{setup} and \code{install}).
	\item[post-<step>] \index{hook!post-}The \code{post-<step>} hook of the plug-in.
\end{description}

For example, the generic setup step puts the sources in place (the build directory and the sources to compile) from the \code{vcs}, \code{archive}, \code{patches} and \code{out-of-tree} hooks.

The cumulative hooks (\code{patches}, \code{depends}, \code{build-depends}, \code{tests-depends}, \code{env}, \code{build-env}, \code{tests-env}, \code{external-env}, \code{config-options} and \code{modules}) can have a \code{common} qualifier, always used in addition to the variant hooks. The plain hook (\code{\_}) is used only when there is no hook for the variants of the module. The hooks are taken in this order:

\begin{enumerate}
	\item \code{cross: common}
	\item \code{cross: <variant>}
	\item \code{cross: \_}
	\item \code{common}
	\item \code{<variant>}
	\item \code{\_}
\end{enumerate}

The \code{cross} hooks are used when the target is not the host; when one is defined it replaces the hook of the same qualifier.
\index{hook!cross}

The other hooks have no \code{common} qualifier: the first one defined in this order is used:

\begin{enumerate}
	\item \code{cross: <variant>}
	\item \code{cross: \_}
	\item \code{<variant>}
	\item \code{\_}
\end{enumerate}

\subsection{Meta-module}
\label{meta-module}
\index{meta-module}

A meta-module is a module listing other modules to build. It groups related modules which are generally built together but do not depend on each other. Other modules can depend on a meta-module.

A module defining the \code{modules} hook (possibly with variants) is a meta-module. A meta-module defining the \code{aggregate} hook is an aggregate meta-module.

\begin{description}[style=nextline]
	\item[modules {[}common|<variant>{]}] \index{hook!modules}The modules of the meta-module.
		\begin{description}[font=\textit,style=standard]
			\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET [\$VARIANT]}
			\item[return] \tabto{2cm} array
				\begin{enumerate}
					\item <module1>
					\item <module2>
		\end{enumerate}
	\end{description}

	\item[propagate-version {[}<variant>{]}] \index{hook!propagate-version}\label{propagate-version}Whether the version and/or the variant of the meta-module are propagated to its modules. Default is \code{version}.
		\begin{description}[font=\textit,style=standard]
			\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET [\$VARIANT]}
			\item[return] \tabto{2cm} \code{\textbf{version} | variant | both | no}
		\end{description}

	\item[aggregate {[}<variant>{]}] \index{hook!aggregate}\label{aggregate}With \code{direct} or \code{recursive} the meta-module is an aggregate meta-module: the installations of its modules are copied into the meta-module, and the environment of these modules points to it. This groups the artifacts of several modules in a single place. With \code{direct} only the modules of the \code{modules} hook are aggregated, with \code{recursive} their dependencies too. Default is \code{no}.
	\begin{description}[font=\textit,style=standard]
	\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET [\$VARIANT]}
	\item[return] \tabto{2cm} \code{direct | recursive | \textbf{no}}
	\end{description}

	\item[prefix {[}<variant>{]}] \index{hook!prefix}\label{prefix}The global install directory of an aggregate meta-module (not used by the other meta-modules): \code{NONE} skips the global installation. Without this hook the module is installed in \code{\$SCBI\_PREFIX}.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} \code{\$PREFIX \$TARGET \$VARIANT}
		\item[return] \tabto{2cm} string
		\begin{enumerate}
			\item <install\_dir>
			\\ or
			\item NONE
		\end{enumerate}
    \end{description}
\end{description}

A meta-module can also give the build plan used to build its modules:

\begin{description}
	\item[plan {[}<variant>{]}] \index{hook!plan}The name of the build plan.
	\begin{description}[font=\textit,style=standard]
		\item[parameter] \tabto{2cm} NONE
		\item[return] \tabto{2cm} string
		\begin{enumerate}
			\item <plan-name>
		\end{enumerate}
	\end{description}
\end{description}

Example:

\begin{lstlisting}
modules:
  - gnatcoll-core
  - gnatcoll-bindings
  - gnatcoll-db
plan: stable
\end{lstlisting}

A module listed in a meta-module can itself be a meta-module. A meta-module can define only a limited set of hooks, that is:

\begin{itemize}[font=\texttt]
	\item setup
	\item propagate-version
	\item external-env
	\item build-depends
	\item plan
	\item modules
	\item prefix
	\item wrapup
\end{itemize}

A meta-module has no sources, but a version can be given for it: it is propagated to its modules, and recursively to the modules of its meta-modules. Set the \code{propagate-version} hook to \code{no} to disable this.

The \code{external-env} hook makes sure that the \code{wrapup} hook is run again when needed: if \code{wrapup} uses environment variables or features (\seeref{enable-feature}) to generate a package for example, list them in \code{external-env}.

\subsection{User's defined final step}
\label{module-final-step}
\index{hook!module-final-step}

After the successful build of a module or of an aggregate meta-module,
the function \code{module-final-step} of the environment file
(\seeref{env-files}) is run, if defined. It can be used to update the
packaging of an application for example. It is written in the command
language (\seeref{yaml-command-language}), with these variables:

\begin{description}
	\item [PREFIX] The install directory of the module.
	\item [TARGET] The build target.
	\item [VARIANT] The variant of the module.
	\item [MODULE] The name of the module.
	\item [FORMODULE] The module depending on this one, \code{@root} for a module of the command line.
	\item [MODREF] The module reference, as found in the dependencies.
	\item [DEPENDS\_KIND] The kind of dependency: \code{default}, \code{build} or \code{tests}.
	\item [IS\_META] \code{no}, \code{yes} (a meta-module) or \code{aggregate} (an aggregate meta-module).
	\item [IS\_AGGREGATED] The aggregate mode of the meta-module aggregating the module (\code{direct} or \code{recursive}), else \code{no}. In a \code{direct} aggregate only the modules of the meta-module are aggregated, their dependencies are not (\code{no}); in a \code{recursive} one the dependencies are aggregated too. The build dependencies of a meta-module (its \code{build-depends}) are never aggregated.
	\item [IS\_UP\_TO\_DATE] \code{yes} when the module was up-to-date (not rebuilt), else \code{no}.
\end{description}

and the functions \code{env-actions}, \code{module-ref},
\code{module-name} and \code{target-dir}, available in this function only
(\seeref{yaml-functions}).

The output of the function goes to the console. A failing function is
reported and the build goes on. Example:

\begin{lstlisting}
functions:
  module-final-step:
    run: |-
      #  Handle only standard dependencies
      #  (skip build & tests dependencies)
      if $DEPENDS_KIND != default:
          return
      APP = /some/dir/$MODULE
      #  Copy if not up-to-date or not yet copied
      if $IS_UP_TO_DATE == no or not is-dir($APP):
          rsync -a $PREFIX/. $APP
\end{lstlisting}

\index{define-var!redefinition}
\code{env-actions} gives the environment actions of the module, for
example to write a launch script setting the environment of an
application:

\begin{lstlisting}
functions:
  module-final-step:
    run: |-
      write $PREFIX/env.sh:
          #  $MODULE
      for A V X in $(env-actions):
          if $A == SET:
              append $PREFIX/env.sh:
                  export $V="${X/$PREFIX/\$ROOT}"
\end{lstlisting}

\subsection{Setting environment}
\label{set-env}
\index{variable!add}
\index{variable!set}
\index{variable!unset}
\index{variable!prepend}
\index{variable!append}
\index{variable|delete}
\index{helpers!define-var}
\index{helpers!add-to-var}
\index{helpers!prepend-to-var}
\index{helpers!append-to-var}
\index{helpers!set-var}
\index{helpers!unset-var}
\index{helpers!remove-from-var}

The \code{env}, \code{build-env} and \code{tests-env} hooks are lists of
actions, applied in order. The actions on variables give a fine control on
how a value is set and avoid duplicate values in lists such as \code{PATH};
each of them goes through the function \code{define-var} of the
environment file when it is defined (\seeref{define-var-override}).

\begin{description}[style=nextline]
	\item[define-var <ACTION> <VARIABLE> <VALUE>] Sets the variable according to the action (a one-letter alias can be used):
	\begin{description}
		\item[PREPEND | P] Puts \code{<VALUE>} at the start of the list \code{<VARIABLE>} (removing it from its previous place): it is found before the current values.
		\item[APPEND | A] Puts \code{<VALUE>} at the end of the list \code{<VARIABLE>} (removing it from its previous place): it is found after the current values.
		\item[ADD] Adds \code{<VALUE>} to the list \code{<VARIABLE>} if it is not already there, at any place.
		\item[REMOVE | R] Removes \code{<VALUE>} from \code{<VARIABLE>}: the single value of the variable, or one of the values of a list such as \code{PATH} or \code{LD\_LIBRARY\_PATH}.
		\item[SET | S] Sets \code{<VARIABLE>} to \code{<VALUE>}, removing all the previous values.
		\item[UNSET | U] Unsets \code{<VARIABLE>}.
	\end{description}

	\item[prepend-to-var <VARIABLE> <VALUE>] Short for \code{define-var PREPEND <VARIABLE> <VALUE>}.
	\item[append-to-var <VARIABLE> <VALUE>] Short for \code{define-var APPEND <VARIABLE> <VALUE>}.
	\item[add-to-var <VARIABLE> <VALUE>] Short for \code{define-var ADD <VARIABLE> <VALUE>}.
	\item[remove-from-var <VARIABLE> <VALUE>] Short for \code{define-var REMOVE <VARIABLE> <VALUE>}.
	\item[set-var <VARIABLE> <VALUE>] Short for \code{define-var SET <VARIABLE> <VALUE>}.
	\item[unset-var <VARIABLE>] Short for \code{define-var UNSET <VARIABLE>}.
\end{description}

The other actions are:

\begin{description}[style=nextline]
	\item[export <VARIABLE> <VALUE>] Sets and exports the variable, without going through the \code{define-var} of the environment file.
	\item[system-compiler] Uses the compiler of the system: \code{PATH} set to \file{/usr/local/bin:/usr/bin:/bin}, the compiler paths (\code{C\_INCLUDE\_PATH}, \code{CPLUS\_INCLUDE\_PATH}, \code{LIBRARY\_PATH}, \code{LD\_LIBRARY\_PATH}, \code{ADA\_PROJECT\_PATH}) unset.
	\item[target-env {[<PREFIX> [<TARGET>]]}] Uses the compiler installed in \code{<PREFIX>} (by default the one of the \code{gcc} found in \code{PATH}) for \code{<TARGET>}: its \file{bin} directory put first in \code{PATH} and the compiler paths set to its directories.
	\item[no-target-env {[<PREFIX> [<TARGET>]]}] As \code{target-env}, but the compiler paths are set for the host (to build native tools during a cross build).
	\item[mkdir <DIR>] Creates the directory (and its parents).
	\item[import <COMMAND>] Runs the command (without shell) and applies the variable assignments, \code{export} and \code{unset} statements it prints, as \code{eval \$(opam env)} would.
	\item[local <NAME> <VALUE>] A variable for the following actions of the hook (also written \code{NAME = <value>}, \seeref{yaml-expansion}).
	\item[assign <NAME> <VALUE>] Sets a variable of the driver, part of the environment if it is already exported.
\end{description}

Example:

\begin{lstlisting}
build-env:
  - set-var MYMODULE_USE_CLANG no
env:
  - add-to-var CMAKE_PREFIX_PATH /some/path
  - prepend-to-var PATH /priority/dir/bin
\end{lstlisting}

\subsubsection{Overriding define-var}
\label{define-var-override}
\index{define-var!environment file}\index{environment!define-var}

All the actions above end in a single function, \code{define-var}. An
environment file (\seeref{env-files}) can define its own
\code{define-var} function to change how the environment of the modules
is set, for all the plug-ins at once:

\begin{lstlisting}
functions:
  define-var:
    params: [ACTION, NAME, VALUE]
    run: ...
\end{lstlisting}

It is run for each action of the \code{env}, \code{build-env} and
\code{tests-env} hooks, in order, with:

\begin{description}
	\item[\code{ACTION}] \code{ADD}, \code{SET}, \code{PREPEND},
	\code{APPEND}, \code{REMOVE} or \code{UNSET} (the short form
	\code{S}, \code{P}... when a plug-in uses it with \code{define-var});
	\item[\code{NAME}, \code{VALUE}] the variable and the value, expanded.
\end{description}

The action is done only if the function runs the built-in command
\index{apply-var}\code{apply-var <ACTION> <NAME> [<VALUE>]}, which does
the default action (as described above, with the recording in the
\file{env.cmd} file of the module): the function can change the value or
the variable, apply several actions, or ignore an action (it is then not
recorded in \file{env.cmd} either). For example, to keep
\code{LD\_LIBRARY\_PATH} unchanged and use \file{/opt/local} instead of
\file{/usr/local}:

\begin{lstlisting}
functions:
  define-var:
    params: [ACTION, NAME, VALUE]
    run: |-
      #  no module may change LD_LIBRARY_PATH
      if $NAME == LD_LIBRARY_PATH:
          return
      #  the packages are installed in /opt/local, not /usr/local
      apply-var $ACTION $NAME ${VALUE//\/usr\/local//opt/local}
\end{lstlisting}

To get the actions of a module without changing the build environment
(to write a launch script for example), use \code{\$(env-actions)} in
\code{module-final-step} instead (\seeref{module-final-step}).

\subsection{Setting a proxy}
\label{proxy}
\index{proxy}

Downloading an archive or a repository from the Web may need a proxy. The \code{vcs} and \code{archive} hooks give the name of a proxy; the function \code{proxy} of the environment file (\seeref{env-files}) is then run with this name as parameter, in the environment of the download or VCS commands: the variables it exports (or unsets) are the environment of these commands.

A typical setting is:

\begin{lstlisting}
functions:
  proxy:
    params: [NAME]
    run: |-
      if $NAME == enterprise:
          for V in http_proxy https_proxy ftp_proxy:
              export $V=http://myproxy.org:3128
          export no_proxy=localhost,.net
\end{lstlisting}

This setting only applies to the download of the archive or repository: the other downloads, not needing a proxy, are not affected.

\subsection{Feature}
\label{enable-feature}
\index{feature}\index{helpers!is-enabled}\index{is-enabled}

A feature is a flag enabled with the option \code{\ddash{}enable-<feature>} or with the variables:

\begin{description}[style=nextline]
	\item [SCBI\_<feature>\_FEATURE] The feature for all the plug-ins (\code{true} or \code{false}).
	\item [SCBI\_<plugin>\_<feature>\_FEATURE] The feature for the given plug-in (\code{true} or \code{false}).
\end{description}

The meaning of a feature is up to the plug-ins: for the driver it is only a flag.

In a plug-in the feature is checked with the function \code{is-enabled}:

\code{is-enabled <name> [then-value] [else-value]}

which gives \code{then-value} (default \code{yes}) when the feature is enabled, else \code{else-value} (default empty). In a condition, \code{enabled(<name>)} is true when the feature is enabled.

For example, to enable the \emph{installer} feature:

\cmd{scbi \ddash{}enable-installer ...}

or

\cmd{export SCBI\_installer\_FEATURE=true}

A feature check in a command hook:

\begin{lstlisting}
wrapup: |
  if enabled(installer) or enabled(appli):
      makeself ...
\end{lstlisting}

A compiler option depending on a feature, in a \code{config-options} hook:

\begin{lstlisting}
config-options:
  - -DCMAKE_CXX_FLAGS=-march=$(is-enabled safe-arch x86_64 native)
\end{lstlisting}

\subsection{Build kind}
\label{build-kind}
\index{helpers!get-build-type} \index{build kind}

The most common build variant is \code{Release} vs \code{Debug}. Rather than defining variant hooks for it, use the function \code{get-build-type}:

\cmd{get-build-type <config> <default>}

(\code{\$(get-build-type <config> <default>)} in a value,
\code{VAR = get-build-type <config> <default>} in a command hook,
\code{build-type(<config>,<default>)} in a condition).

\code{<config>} names the configuration tool (\code{CMAKE} or \code{CONFIGURE} for example), but it can be any string.

The function gives the build kind of the module for this tool, from the first variable set among:

\begin{description}[style=nextline]
	\item [SCBI\_<module>\_BUILD\_TYPE] The build kind of the module.
	\item [SCBI\_<CONFIG>\_BUILD\_TYPE] The build kind of all the modules using the tool.
\end{description}

or \code{<default>} when none is set. It is used in the \code{config} hook:

\begin{lstlisting}
config: |
  BUILD_TYPE = get-build-type CMAKE Release
  cmake -DCMAKE_INSTALL_PREFIX=$PREFIX -DCMAKE_BUILD_TYPE=$BUILD_TYPE ../src
\end{lstlisting}

Here, when no variable is set, the build type is \code{Release}. For a \code{Debug} build, set in the environment file (or in the shell):

\begin{lstlisting}
SCBI_CMAKE_BUILD_TYPE = "Debug"
\end{lstlisting}

for all the modules using \code{cmake}, or:

\begin{lstlisting}
SCBI_lcms2_BUILD_TYPE = "Debug"
\end{lstlisting}

for the \code{lcms2} module only. In both cases the plug-in must use \code{get-build-type} as above. In the variable name, the dashes of the plug-in name are replaced by underscores (\code{SCBI\_c\_lcms2\_BUILD\_TYPE} for \code{c-lcms2}).

\subsection{Checking installed tools}
\index{helpers!check-tool}\index{check-tool}

A plug-in may need a tool which is not a dependency, for example \code{makeself} to create a self-installer, and check that it is installed.

In a command hook the function \code{command-path} gives the path of a tool (empty if not found):

\begin{lstlisting}
wrapup: |
  MS = command-path makeself
  if empty($MS):
      echo Required tool makeself missing
      exit 1
\end{lstlisting}

\subsection{Checking dependency version}
\label{check-version}
\index{helpers!get-module-version}\index{get-module-version}
\index{helpers!check-module-version}\index{check-module-version}

A plug-in can check the version of a dependency in the build plan, for example to apply a patch for a given version of a dependency.

In a condition \code{version(<plug-in>)} is the version of the plug-in in the build plan, compared as versions with \code{<}, \code{<=}, \code{>}, \code{>=} or with a regular expression (\code{=\textasciitilde}):

\begin{lstlisting}
patches:
  - if version(lib2) > 1.9: new-lib2.diff
config: |
  if version(lib2) =~ ^2.0:
      ./configure --with-lib2-2.0
  else:
      ./configure
\end{lstlisting}

In a command hook \code{check-versions <v1> <op> <v2>} succeeds when the comparison is true.

\subsection{Inheritance}
\label{inheritance}
\index{inheritance}\index{inherit-plugin}\index{helpers!inherit-plugin}

A plug-in can inherit the definitions of other plug-ins, listed with the
key \code{inherit}:

\begin{lstlisting}
inherit:
  - from: <name>
    hooks: [<hook1>, <hook2>]
    custom-hooks: [<hook1>, <hook2>]
    no-variant: false
    name: <name>
\end{lstlisting}

\begin{description}
	\item[from] The plug-in to inherit from.
	\item[no-variant] When \code{true}, the variant hooks are not inherited, only the plain ones.
	\item[hooks] The hooks to inherit; all of them when not given.
	\item[custom-hooks] The functions of the plug-in to inherit.
	\item[name] The name under which the inherited hooks are known (the hook \code{post-install} of a plug-in inherited with \code{name: base} is called \code{base-post-install}). This makes it possible to inherit the same hook from several plug-ins and call them in turn.
\end{description}

The hooks of the plug-in itself take precedence over the inherited ones:
a plug-in can, for example, only redefine the \code{vcs} or \code{archive}
hook of another one.

\subsection{Variants without build (with-variants)}
\label{native variant}
\index{native variant}\index{variant!native}
\index{with-variants}

A plug-in often needs a native variant, using the libraries of the OS instead of building from sources: a variant whose hooks do nothing, except the \code{depends} hook listing the packages of the OS and possibly the \code{env} hook.

The key \code{with-variants} defines such a variant, native or any other
variant which only depends on other modules or packages:

\begin{lstlisting}
with-variants:
  native:
    packages: [pckA:[v], pckB]
    env: [set-var ROOT_DIR /usr]
\end{lstlisting}

The key is the name of the variant (\code{native} here, but any name can be
used). \code{packages} lists the modules or OS packages the variant
depends on, or \code{NONE}; \code{env} gives the environment actions. With \code{NONE} the \code{depends} hook is empty: the dependency was installed by hand on the machine (because the OS does not package the library, for example). The \code{[v]} tag checks that the installed package has the version given for the module in the build plan.

With the example above, in a plug-in \code{natv} with version \code{1.2} in the build plan, the variant \code{native} has:

\begin{itemize}
	\item a \code{depends} hook listing \code{pckA:1.2} and \code{pckB};
	\item an \code{env} hook with the actions of \code{env};
	\item \code{prefix} set to \code{NONE};
	\item empty \code{build-env}, \code{build-depends}, \code{config}, \code{build} and \code{install} hooks.
\end{itemize}

\subsection{Getting configuration options}
\label{config-options}
\label{get config options}
\index{get-config-options}\index{helpers!get-config-options}

The configuration options often depend on the variant built, for example to enable an external module.

In a command hook, \code{\$(config-options)} (or \code{OPTIONS = config-options}) gives the list of the values of the \code{config-options} hooks of the module: the \code{common} one, then those of each variant of the module reference.

The \code{common} hook holds the options used whatever the variant.

For example:

\begin{lstlisting}
plugin: mod
config-options:
  common: [-DPREFIX=/my/path]
  mpi: [-DMPI=ON]
  openmp: [-DOpenMP=ON]
config: cmake $(config-options) ../src
\end{lstlisting}

If the current module reference is \code{mod/mpi} the \code{cmake} command will be:

\begin{lstlisting}
	cmake -DPREFIX=/my/path -DMPI=ON ../src
\end{lstlisting}

And if the module reference is \code{mod/mpi.openmp} the \code{cmake} command will be:

\begin{lstlisting}
	cmake -DPREFIX=/my/path -DMPI=ON -DOpenMP=ON ../src
\end{lstlisting}

Each option is one argument of the command, even when it contains spaces.

\subsection{OS dependencies}
\label{os-deps}
\label{OS dependencies}
\index{os dependencies}

The \code{depends} hook lists dependencies on other plug-ins or on external libraries and tools. As the names of the packages differ between distributions and versions, an OS-independent name can be used:

\begin{lstlisting}
	os@-<name>
\end{lstlisting}

\code{os@-<name>} is looked up in a table giving the name of the package for the OS.

A distribution is named by a 3-letter acronym (\code{deb}, \code{ubt}, \code{rhl} for example); the \code{\ddash{}stat} option lists the supported distributions.

The tables are read from these files, in this order:

\begin{enumerate}
	\item \file{.pkgs-<distrib>[-<id>]} in \code{\$SCBI\_PLUGINS};
	\item \file{.scbi-pkgs-<distrib>[-<id>]} in \code{\$SCBI\_BDIR} (the sandbox);
	\item \file{.scbi-pkgs-<distrib>[-<id>]} in the current directory.
\end{enumerate}

\begin{description}
	\item [\code{<distrib>}] The acronym of the distribution, possibly followed by its \emph{major} and \emph{minor} version, separated by a tilde \textasciitilde{}.

For example on \code{Debian 10.6} the files are read in this order:

\begin{enumerate}
	\item \code{.pkgs-deb}
	\item \code{.pkgs-deb\textasciitilde{}10}
	\item \code{.pkgs-deb\textasciitilde{}10.6}
\end{enumerate}

So \code{.pkgs-deb\textasciitilde{}10} can add entries or override the ones of \code{.pkgs-deb}.

\item [\code{<id>}] An optional string, for the tables of a project. Such a file is read after the one without \code{<id>}, so it can override its entries.
\end{description}

\subsection{Private Store}
\index{Private Store}
\index{API|Private Store}

The private store (\seeref{store}) keeps private values, such as license keys, out of the plug-ins. In a plug-in, \code{\$(store-key <key>)} gives the value of a key; a command hook can also run the \code{scbi store} sub-command:

\begin{lstlisting}
config-options:
  - --license=$(store-key LICKEY)
wrapup: |
  scbi store LICKEY 89AXCDPPP6BGG
\end{lstlisting}

\section{The driver}
\label{python-driver}
\index{Python driver}

The driver is written in Python (\file{src/scbi} in the SCBI
repository). It reads the YAML plug-ins and the YAML environment files,
and runs no shell code.

\subsection{Installing and running}
\index{install}

The driver needs \code{python3} (3.11 or later) and its YAML module
(\code{python3-yaml} on Debian). From a checkout of SCBI:

\cmd{make}

copies the driver into \file{\$HOME/.local/lib/scbi}, writes the command
\file{\$HOME/.local/bin/scbi}, and copies the plug-ins into
\file{\$HOME/.config/scbi} and the completion support into
\file{\$HOME/.bash\_completion.d}. From a checkout it can also be run
directly with:

\cmd{PYTHONPATH=<scbi>/src python3 -m scbi [options] module1 ...}

The name of the command displayed in the messages is taken from the
environment variable \code{SCBI\_ARGV0} when set (the \code{scbi}
command sets it).

The driver also computes the settings not given by the environment or the
environment file: the directories (\seeref{build-env}), the number of
days the logs are kept (\code{KEEP\_LOG\_DAYS}), the e-mail notification
(\code{SCBI\_EMAIL\_NOTIFICATION}), the distribution (\code{SCBI\_OS\_NAME}:
\code{deb}, \code{ubt}, \code{cos}, \code{fed}, \code{rhl}, \code{mingw},
\code{win} or \code{none}), its installed packages and the \code{os@-}
aliases (\seeref{os-deps}). The values of the ini files are expanded as by
a shell (variables, \code{\textasciitilde{}}, quotes, \code{\$(command)},
globs), without running one. The resolved build plan is cached in
\file{\$SCBI\_BDIR/.cache/plan-<signature>.json} (see \ddash{}clear-cache).

\subsection{Environment files}
\label{env-files}
\index{environment!file}

The environment files are YAML files, searched as described in
\seeref{envfile}:
\file{\$PWD/.scbi-env.yaml}, \file{\$PWD/../.scbi-env.yaml},
\file{\$HOME/.scbi-env.yaml}, then \file{\$SCBI\_PLUGINS/.env.yaml}
(\file{env-<name>} for \code{\ddash{}env=<name>}). The environment files
of the previous versions of SCBI (Bash) are converted as described in
\seeref{bash-convert}; a Bash or Python environment file found without
its YAML version is an error.

The file is read once when the driver starts. All its keys are optional:

\begin{description}
	\item[inherit] A list of environment file names: \code{shared} for
	\file{.env-shared.yaml} (or \file{.scbi-env-shared.yaml}) in the same
	directory. They are read first, in order (recursively); the settings and
	functions of this file override theirs.
	\item[vars] The settings, a mapping of variable names to values, e.g.
	\code{SCBI\_PLAN: \$\{SCBI\_PLAN:-default\}} or
	\code{SCBI\_c\_gmp\_BUILD\_TYPE: Debug}. They are expanded in order
	(\seeref{yaml-expansion}), with the driver variables, the previous
	settings and \code{SCBI\_ENV\_DIR} (the directory of the file); the
	functions of values can be used, e.g. \code{\$(output python3 -V)}.
	They become driver variables, given to the hooks.
	\item[passthrough] A list of variables of the user's environment given
	to the hooks (\seeref{hookenv}).
	\item[functions] Functions in the command language
	(\seeref{yaml-command-language}), as in the plug-ins (\code{params},
	\code{run}). Some of them are hooks of the driver:
	\begin{description}
		\item[define-var] (\code{ACTION}, \code{NAME}, \code{VALUE}) run for
		each environment action of the plug-ins instead of the default
		(\seeref{define-var-override}).
		\item[rewrite-vcs, rewrite-archive] Get the fields of a \code{vcs} or
		\code{archive} hook as parameters (proxy, options, protocol, url,
		[file,] dir) and print the fields to use, one per line; with no
		output the fields are kept.
		\item[proxy] (\code{NAME}) sets the environment of the VCS or
		download commands for the proxy \code{NAME} of a \code{vcs} or
		\code{archive} hook (\seeref{proxy}).
		\item[module-final-step] Run after each module
		(\seeref{module-final-step}).
	\end{description}
	The other functions can be called by these ones.
\end{description}

\begin{lstlisting}
inherit: [shared]
vars:
  SCBI_PLAN: ${SCBI_PLAN:-default}
  SCBI_BDIR: ${SCBI_BDIR:-$HOME/builds}
passthrough: [CC]
functions:
  rewrite-vcs:
    params: [PROXY, OPTIONS, PROTOCOL, URL]
    run: |-
      echo $PROXY
      echo $OPTIONS
      echo $PROTOCOL
      echo ${URL/git@server:/https:\/\/server\/}
  module-final-step:
    run: |-
      for A V X in $(env-actions):
          echo $MODULE: $A $V $X
\end{lstlisting}

\subsection{Hook environment}
\label{hookenv}
\index{environment!hook}

A command hook runs with an environment built for that call only, and
discarded after it: nothing accumulates between hooks or modules. It
contains:

\begin{itemize}
	\item from the user's environment only \code{PATH}, \code{HOME},
	\code{USER}, \code{LOGNAME}, \code{SHELL}, \code{TERM}, \code{TMPDIR},
	\code{DISPLAY}, \code{LANG}, \code{LANGUAGE}, \code{LC\_*} and the
	proxy variables (\code{http\_proxy}, \code{https\_proxy},
	\code{ftp\_proxy}, \code{no\_proxy} and their upper-case forms);
	\item the variables of \code{passthrough} (environment file);
	\item every exported variable set or changed by the driver: the
	\code{SCBI\_*} variables, the settings of the environment files and
	the environment of the module (the \code{env} hooks of its
	dependencies, its \code{build-env} or \code{tests-env}).
\end{itemize}

The plug-in variables (\code{vars}) and the hook parameters are
variables of the body, not environment variables (use \code{export VAR =
...} to give one to the commands).

\subsection{Reproducing a step}
\label{replay}
\index{replay}

For each step, the file \file{<target>-<variant>/logs/<step>.cmd} of the
module in the sandbox is a replay file (YAML): the directory, the
environment, the parameters, the plug-in variables, the configuration
options and the body of the hook (\code{run}, which can be edited) with
the plug-in functions it may call. When a step fails the driver
displays:

\begin{footnotesize}
	\begin{verbatim}
2026/11/13 13:23:30 : h-handson-lib (FAILED) to reproduce:
2026/11/13 13:23:30 : h-handson-lib (FAILED) scbi replay /<...>/logs/build.cmd
2026/11/13 13:23:30 : h-handson-lib (FAILED) use --trace option for debug
    \end{verbatim}
\end{footnotesize}

\cmd{scbi replay [\ddash{}trace] <step>.cmd}

reruns the hook; \ddash{}trace displays each command (and assignment)
before running it, as \code{bash -x} does. The logs of the steps contain
the same trace (lines starting with \code{\_TRACE:}), except with
\ddash{}log:yes.

\index{replay!script}
\cmd{scbi replay \ddash{}script <step>.cmd > step.sh}

runs nothing but displays a Bash script doing the step by hand: the
environment of the hook (exported), the plug-in functions called, the
directory of the hook and its body translated to Bash. What is known when
the script is generated is written as its value: the parameters
(\code{PREFIX}, \code{TARGET}, \code{VARIANT}...), the plug-in variables,
the driver variables (\code{SCBI\_*}), the configuration options, the
conditions on the build (\code{cross}, \code{variant}, \code{enabled()},
\code{build-type()}...) and the functions with known arguments (such as
\code{get-build-type}). File tests, \code{ok(...)}, command status and the
variables set by the hook stay Bash. The variables of the user's terminal
(\code{HOME}, \code{USER}, \code{LOGNAME}, \code{SHELL}, \code{TERM},
\code{LANG}, \code{DISPLAY}, \code{CDPATH}) and of the driver
(\code{SCBI\_*}, \code{DO\_*}) are not exported by the script: the ones of
the shell running it are used. The script can be edited and run with
\code{bash step.sh}. \code{all-modules} and \code{hook-output} are not
available in a replay; \code{log} writes its message indented, without
time-stamp (as \code{scbi replay}).

\cmd{scbi replay \ddash{}script:inline <step>.cmd}

displays the same commands on a single line, run in a sub-shell, to be
pasted in a terminal: \code{( cd <dir> || exit 1; export A=... B=...;
<commands> )}. The \code{write} blocks are written with \code{printf}.

\subsection{Standalone archives}

A standalone source archive (\ddash{}standalone, \seeref{standalone})
contains the driver (the Python package in \file{lib}, the command
\file{bin/scbi}), the plug-ins of the modules and an environment file
(\file{.scbi-env-std.yaml}).

\subsection{Testsuite}
\index{testsuite}

\begin{description}
	\item[\code{make test}] The regression testsuite (pytest): each test
	driver (\file{tests/drivers/testNNN.py}) builds the test plug-ins
	(\file{tests/scripts.d}, YAML) in its own copy of the test directories
	and checks the output; the drivers run in parallel when pytest-xdist
	is installed, the JUnit report is \file{tests/junit.xml}.
	\code{make test T="testNNN..."} runs some of them.
	\item[\code{make unit}] The unit tests of the driver (pytest).
\end{description}

When run by the testsuite (\code{SCBI\_TESTSUITE=yes}) the driver does not
load \file{\$HOME/.scbi}, takes \code{SCBI\_OS\_MODULE} and \code{TODAY}
from the environment, uses the rsync checksum mode and logs the sync
messages; the harness (\file{tests/harness.py}) gives it the test
directories (\code{SCBI\_ROOT}\ldots) through the environment. With \code{SCBI\_OS\_NAME=test} the
installed packages are those of \code{SCBI\_TEST\_PKGS} (\code{"name=version
..."}), checked as Debian packages. With \code{SCBI\_TEST\_PROGRESS=yes} each step of the build progress (\ddash{}progress) is printed on a line, \code{progress [n/N] module}.

\section{Support tools}

\subsection{Show}
\label{listing}
\label{show}
\index{show}
\index{tools|show}

The \code{show} sub-command lists the build plan and the dependencies, and shows module references.

\cmd{scbi show [options] [plugins]}

The following options are supported:

\begin{description}[font=\texttt]
	\item[\ddash{}depends:{[}direct|full{]}] Lists the dependencies of the modules: all of them recursively (\code{full}, the default) or only the direct ones.

	\item[\ddash{}rdepends] Lists the plug-ins depending on the given plug-in. The variants are displayed in brackets and the kind of dependency (test or build) in parentheses.

	\item[\ddash{}externals:{[}only{]}] Lists the external and module dependencies recursively; with \code{only}, the external ones only.

	\item[\ddash{}no-version] Does not display the versions of the modules and externals.

	\item[\ddash{}filter:{[}all|run|dev{]} ] Restricts the dependencies or externals listed to \code{all} of them (default), the \code{dev} ones (needed to build) or the \code{run} ones (needed to run the software, computed from the \code{dev} ones for the packages of the OS).

	\item[\ddash{}build-plan:{[}history{][}=filter{]}] Lists the resulting build plan: after loading the plan, the plans it loads (\code{@load}) and the module references of the command line. With \code{history} the history of each setting is displayed (which plan set it), handy for complex plans. \code{filter} is a comma-separated list of plug-ins to list.

	\item[\ddash{}module-ref:{[}version|variant|full{]} ] Displays the variant, the version or both of the modules, from the command line or the build plan.

	\item[\ddash{}resolved] \index{resolved plug-in}Displays the plug-in of each module resolved for its module reference (the variant and version of the command line, else of the build plan) and the target: the plug-in the driver actually uses, without variants. Each hook is written once, as a plain hook: the one selected for the variant (variants including others, \code{common}, \code{cross}, inheritance and OS variants applied), or for a cumulative hook (\code{depends}, \code{env}, \code{config-options}...) the items of all the selected ones, in order. In the value and environment lists the \code{if} guards are evaluated (an item whose guard cannot be evaluated outside a build is kept with it); the command bodies, the functions and the variables are kept as written. The hooks doing nothing (the placeholders of the OS variants) are left out. The output is a valid YAML plug-in, preceded by a comment giving the module reference, the target and the plan. It is what the build id of the module compares (without its \code{env} hook, \seeref{options}). For example:

	\cmd{scbi show \ddash{}resolved c-darktable/all}

	\cmd{scbi \ddash{}target=x86\_64-w64-mingw32 show \ddash{}resolved c-gmp}

	\item[\ddash{}stat] Displays the setup (see the \ddash{}stat option).
\end{description}

\subsection{Shell}
\label{shell}
\index{shell}
\index{tools|shell}

The \code{shell} sub-command starts a shell (\code{\$SHELL}), or runs a command, in the environment of the modules: to build or test by hand in the very environment SCBI uses for these modules.

\cmd{scbi shell [options] [plugins]}

The following options are supported:

\begin{description}[font=\texttt]

	\item[\ddash{}mode:{[}dev|sandbox|sb|tests|use{]}] The environment set and the directory of the shell. The default mode is \code{use}.

	\begin{description}[font=\texttt]
		\item[sandbox] (or \code{sb}) The shell goes to the build directory of the module in the sandbox, with the environment of its dependencies and its build environment: exactly the environment of the configuration, build and install steps. This mode is meant to debug the build of the module, or try other options.

		\item[tests] As \code{sandbox}, with the tests environment too (the environment of the tests dependencies).

		\item[dev] As \code{sandbox}, but the shell goes to the user's checkout of the module (as with the version \code{dev}).

		\item[use] The shell stays in the current directory, with the environment needed to use the modules (as a dependency: their environment and the one of their dependencies, recursively).
	\end{description}

	\item[\ddash{}run{[}="command args..."{]}] \label{cmd!run}Runs the command in the environment of the modules, for example a program using libraries of the sandbox. Without a command, the one given by the \code{run} hook of the module is run.

	\item[\ddash{}stat] Displays the setup (see the \ddash{}stat option).
\end{description}

\subsection{Private Store}
\label{private store}
\label{store}
\index{private store}
\index{tools|store}

Some modules need private information, such as license keys, which cannot be written in a plug-in that may be public. SCBI keeps such values in a private store, handled with the \code{store} sub-command:

\cmd{scbi store [options] [key1, key2...] [value]}

The following options are supported:

\begin{description}[font=\texttt]
	\item[-h | \ddash{}help] Displays the usage and the options.

	\item[-v | \ddash{}version] Displays the versions of the driver and of the plug-ins.

	\item[-e | \ddash{}env=<name>] Uses the environment file \file{.env-<name>.yaml} (\seeref{build-env}).

	\item[\ddash{}stat] Displays the setup.

	\item[\ddash{}plugins=<directory>] The directory of the plug-ins, instead of \code{\$SCBI\_PLUGINS}.

	\item[\ddash{}list-keys] Lists the keys of the store.

	\item[\ddash{}list{[}:full{]}] Lists the given keys (an empty string for an unknown one); with \code{:full}, with their values.

	\item[-d | \ddash{}delete] Deletes the given keys.
\end{description}

Some examples:

\begin{itemize}
	\item To set a key

	\cmd{scbi store LICKEY 89AXCDPPP6BGG}

	\item To list all stored keys

	\cmd{scbi store \ddash{}list-keys}

	\item To get value associated with a key

	\cmd{scbi store LICKEY}

	\item To remove a key

    \cmd{scbi store \ddash{}delete LICKEY}
\end{itemize}

The keys are stored in the file \file{\$SCBI\_PLUGINS/.store} (\file{\$HOME/.config/scbi/.store} by default). A plug-in reads a key with \code{\$(store-key <key>)} (\seeref{yaml-functions}).

\subsection{Linter}
\label{linter}
\index{linter}

The \code{scbi lint} sub-command checks plug-ins for common errors:

\cmd{scbi lint lcms2}

A plug-in is given by name (\file{\$SCBI\_PLUGINS/<name>.yaml}) or by path.
All the problems found are reported:

\begin{itemize}
	\item errors: unknown keys (hooks with a typo, with the closest
	known name), structure of the hooks (qualifiers, \code{common} for a
	non-cumulative hook, nested \code{cross}, missing fields of
	\code{vcs} and \code{archive}), values of \code{out-of-tree},
	\code{only-explicit-build} (true or false), \code{aggregate} (direct,
	recursive or no) and \code{propagate-version} (version, variant, both
	or no), conditions, functions in values and environment actions, a
	literal level of \code{log} which is not an integer >= 1;
	\item warnings: empty hooks, \code{out-of-tree} in a meta-module
	(\code{modules} and no sources: it is not built), and variables used by a hook (shell code,
	values, environment actions) which are not known there: not a
	parameter of the hook (a parameter of another hook is named as such,
	e.g. \code{VERSION} used in \code{config}), not set by the hook, the
	plug-in variables or environment actions, nor a driver
	(\code{SCBI\_*}) or a usual environment variable.
\end{itemize}

The option \ddash{}error only reports the errors. The exit status is 1 when an error is found.

\subsection{Formatter}
\label{formatter}
\index{format}

The \code{scbi format} sub-command writes plug-ins in a canonical form: the
hooks in a canonical order, no trailing blanks, no duplicate blank lines.

\cmd{scbi format lcms2}

The formatted plug-in is displayed, or written back to the file with the
option \ddash{}replace. An invalid plug-in is not formatted (see
\code{scbi lint}). The canonical form is:

\begin{itemize}
	\item the keys in this order: \code{plugin}, \code{inherit},
	\code{vars}, \code{functions}, \code{variants}, \code{with-variants};
	the sources \code{vcs}, \code{archive}, \code{patches}; the
	dependencies \code{depends}, \code{build-depends},
	\code{tests-depends}; the environment \code{env}, \code{build-env},
	\code{tests-env}, \code{external-env}; the steps \code{setup},
	\code{out-of-tree}, \code{only-explicit-build}, \code{config-options},
	\code{config}, \code{build}, \code{install}, \code{wrapup},
	\code{tests} (each step between its \code{pre-} and \code{post-}
	hooks); then \code{run}, \code{version}, \code{prefix}; and the
	meta-module hooks \code{modules}, \code{aggregate},
	\code{propagate-version}, \code{plan};
	\item inside a hook the qualifiers \code{common} (always first),
	\code{\_}, \code{default}, the variants in alphabetical order, then
	\code{cross} (inside it the same order);
	the fields of \code{vcs} and \code{archive} in their order;
	\item block style, indented by 2, multi-line values as literal blocks
	(\code{|}), quotes only where needed, a blank line between the hooks.
\end{itemize}

The comments are kept: a comment line goes with the key or list item it
precedes (and moves with it), an end of line comment with its line; the
comments at the top of the file (separated from the first key by a blank
line) and at the end stay there.

\subsection{Create Source Archive}
\label{createsourcearchive}
\index{source archive}

The \code{scbi source-archive} sub-command creates a source archive for a plug-in having both a \code{vcs} and an \code{archive} hook: the build can then use this archive, put on a safe server for example, instead of the repository (without Internet access for example).

The sources are taken from the repository of the \code{vcs} hook. The archive is named \file{<REPOSITORY-NAME>-<VERSION>.tar.gz}, or after the template of the \code{archive} hook when the plug-in has one (\seeref{hookarchive}). The supported formats are:

\begin{description}[style=nextline]
	\item[.tar] An uncompressed tar archive.
	\item[.tar.gz] A tar archive, best gzip compression.
	\item[.tar.bz2] A tar archive, best Bzip2 compression.
	\item[.tar.zst] A tar archive, best Zstandard compression.
	\item[.tar.xz] A tar archive, best XZ compression.
	\item[.zip] A zip archive, default compression.
\end{description}

For example:

\cmd{scbi source-archive lcms2:2.12}

creates the archive \file{Little-CMS-2.12.tar.gz} (the default name, this plug-in having no \code{archive} hook).

The sub-command can also create an \code{MD5}, \code{SHA-1} or \code{SHA-256}
file for the archive; the options are listed by:

\cmd{scbi source-archive \ddash{}help}

\subsection{Completion support}
\label{completion}
\index{completion}

A Bash completion script is provided: \file{bash\_completion.d/scbi}, installed by \code{make} in \file{\$HOME/.bash\_completion.d} (or copy it in \file{/etc/bash\_completion.d/}).

The completion package of the system must be installed; on Debian-based distributions:

\cmd{apt install bash-completion}

\subsection{User's checkout}
\label{userco}
\index{user's checkout}

This is certainly the most important use case. A complex piece of software is built with SCBI, and a bug (in the configuration, the build or the dependencies) is found in one module. The module must be debugged and fixed; the complete cycle is:

\begin{itemize}
	\item check out the module;
	\item compile it by hand in debug mode;
	\item debug the application;
	\item fix the code;
	\item commit the changes;
	\item push and integrate the changes (possibly in a new branch).
\end{itemize}

SCBI supports this directly: a user's checkout can be used instead of the sources of the sandbox. Do not modify the sources in the sandbox: depending on the options, SCBI may overwrite them and the changes would be lost.

The recommended steps are (assuming the module uses Git):

\subsubsection{Checkout modules}

Check out the modules to work on:

\begin{shellcommand}
	\item cd \$HOME/dev

\file{.cmd} file with \code{scbi replay} (\seeref{replay}); the \ddash{}trace

\cmd{scbi replay /.../logs/build.cmd}

\section{The Sandbox}
\label{sandbox}

This section describes the structure of the sandbox. It is generally not needed to look into it, except to debug a new plug-in (\seeref{debugging}).

\vspace{1cm}

{\scriptsize
\dirtree{%
	.1 \textbf{[\$SCBI\_BDIR]}.
	.2 \textbf{[n]}\des{optional, simple number used in flat mode}.
	.2 \textbf{[.vcs]}.
	.3 \textbf{[<module>]} \des{sources checkout}.
	.2 \textbf{[.patches]}.
	.2 \textbf{[.archives]}.
	.3 <module>-<version>-src.tar.gz.
	.2 \textbf{[.logs]} \des{global log directory with history}.
	.3 \textbf{[YYYY-MM-DD]}.
	.4 <target>-<module>-report.log \des{the messages of the driver for the module (all its variants, all the runs of the day, without colors) and the output of the VCS, archive and generic commands}.
	.4 <target>-<module>-<variant>-<step>.log \des{the output of a step (also in <target>-<variant>/logs/<step>.log)}.
	.4 <target>-<module>-<variant>-env.log \des{the environment of the build}.
	.2 \textbf{[<module>]}.
	.3 build $\rightarrow$ \des{symlink to current/latest target build dir}.
	.3 build-id-<variant> \des{build id to check for changes}.
	.3 build-deps-<variant> \des{build id of all dependencies}.
	.3 src $\rightarrow$ \des{symlink to sources (vcs or archive)}.
	.3 archive $\rightarrow$ \des{symlink to extracted archive}.
	.3 \textbf{[archive-src]} \des{extract of archive}.
	.3 source-id \des{latest source-id (corresponding to build symlink)}.
	.3 source-id<variant> \des{version of the source (archive or vcs)}.
	.3 source-ref \des{the full source reference for QA purpose}.
	.3 install-<target>-id \des{version of the module installed globally}.
	.3 vcs $\rightarrow$ \des{symlink to repository (.vcs or user's checkout)}.
	.3 \textbf{[<target>-<variant>]} \des{directory, or symlink in flat mode}.
	.4 \textbf{[logs]} \des{commands \& output for each steps}.
	.4 \textbf{[build]} \des{build directory}.
	.4 source-id \des{sha1 to identify the sources}.
	.4 build-id \des{sha1 to identify the build}.
	.4 build-deps \des{build-id of all dependencies}.
	.4 \textbf{[install]} \des{installation directory}.
	.4 manifest \des{list of all files in install above}.
	.4 \textbf{[src]} \des{rsync of ../src}.
}
}

	Symbolic links are not available on Windows \code{MSYS}: they are replaced by files with a \file{.lnk} extension containing the location of the linked directory.

\section{Complete example}

The plug-ins coming with SCBI are good examples of the different features.

As a complete example, let's build the latest version of GIMP. The plug-in is the file \file{gimp.yaml} (in \file{\$SCBI\_PLUGINS}, \file{\$HOME/.config/scbi} by default).

This plug-in was working when this document was written, but changes in the dependencies of the OS may require updating it.

\begin{lstlisting}
plugin: gimp

# the sources are handled in Git
vcs:
  proxy: default
  options: none
  protocol: git
  url: https://github.com/GNOME/gimp

# all dependencies, most of them are standard Debian packages
# except libmypaint, mypaint-brushes and libgegl
depends:
  - gtk-doc-tools
  - libbabl-dev
  - libgegl-dev
  - libgexiv2-dev
  - libpoppler-glib-dev
  - python-gtk2-dev
  - python-cairo-dev
  - mypaint
  - libmng-dev
  - libxpm-dev
  - libmypaint
  - mypaint-brushes
  - libgegl

# the build is done in the source directory
out-of-tree: false

# the environment of the three dependent modules is set by
# their plug-ins
config: ./autogen.sh --prefix=$PREFIX

build: make -j$SCBI_JOBS

# installation into the sandbox install directory of the module
install: make install

# the global installation
prefix: /opt/gimp
\end{lstlisting}

As seen above, the \code{gimp} module depends on three other modules, whose environment is needed by the configuration. The environment of these three dependencies is:

\begin{itemize}
	\item Hook \code{env} of \file{libmypaint.yaml}:

	\begin{lstlisting}
env:
  - add-to-var PKG_CONFIG_PATH $PREFIX/lib/pkgconfig
	\end{lstlisting}

	\item Hook \code{env} of \file{mypaint-brushes.yaml}:

	\begin{lstlisting}
env:
  - add-to-var PKG_CONFIG_PATH $PREFIX/share/pkgconfig
	\end{lstlisting}

	\item Hook \code{env} of \file{libgegl.yaml}:

	\begin{lstlisting}
env:
  - add-to-var PKG_CONFIG_PATH $PREFIX/lib/pkgconfig
  - add-to-var PATH $PREFIX/bin
	\end{lstlisting}

\end{itemize}

The plug-ins of these three modules are provided with SCBI.

This version of GIMP needs specific versions of the dependencies, given by a build plan \file{.plan-gimpdev}:

\begin{lstlisting}
 libmypaint:v1.3.0
 mypaint-brushes:v1.3.0
\end{lstlisting}

That is, version 1.3.0 of \code{libmypaint} and \code{mypaint-brushes}.

GIMP is then built with:

\cmd{scbi \ddash{}plan=gimpdev \ddash{}deps gimp}

\section{Bash plug-ins and the Bash driver}
\label{bash-plugins}
\index{Bash plug-in}

Before the current driver, SCBI was a Bash driver (\file{scbi} and
\file{scbi-*}, with the runtime files \file{scripts.d/[0-9]*}) and the
plug-ins and environment files were Bash scripts. The Bash driver is no
longer part of SCBI: the Bash plug-ins and environment files are converted
once (\seeref{bash-convert}).

\subsection{Differences with the Bash driver}

The driver accepts the same command line, options, ini files and build
plans as the Bash driver, gives the same output and builds the same
sandbox. The differences are:

\begin{itemize}
	\item The plug-ins are YAML files (\seeref{yaml-plugin}). A Bash plug-in
	without its YAML version is an error.
	\item The environment files are YAML files (\seeref{env-files}).
	A Bash environment file without its YAML version is an error.
	\item The runtime files (\file{1\_setup}, \file{6\_distpkg},
	\file{8\_mail}...) are not read: their settings are computed by the
	driver with the same defaults, and changed through the environment or
	an environment file.
	\item The runtime functions cannot be redefined: the extension points
	are the functions of the environment file (\code{define-var},
	\code{rewrite-vcs}, \code{rewrite-archive}, \code{proxy},
	\code{module-final-step}). With \file{\_os\_windows}
	(\code{SCBI\_OS\_MODULE=windows}) the \code{define-var} of that file
	(\code{;} separator, \code{cygpath -u} for \code{PATH}) is reproduced.
	\item The command hooks are not Bash code but the command language
	(\seeref{yaml-command-language}), run with an isolated environment
	(\seeref{hookenv}); a step is reproduced with \code{scbi replay}
	instead of a Bash script.
	\item The \code{auto} variants of a plan are checked in plan order (the
	Bash driver checked them in parallel: the order of their messages may
	differ).
	\item The cached build plans are stored in
	\file{\$SCBI\_BDIR/.cache/plan-<signature>.json}, a different file than
	the one of the Bash driver: both drivers can use the same build
	directory.
	\item \code{scbi lint} and \code{scbi format} work on YAML plug-ins only.
\end{itemize}

\subsection{Bash plug-in format}

A Bash plug-in is a file named as the plug-in (no suffix) defining a Bash
function per hook, named \code{<plug-in>[-<variant>|-common][-cross]-<hook>}.
The parameters are given as positional parameters (\code{local
PREFIX=\$1}, \code{local TARGET=\$2}, \code{local VARIANT=\$3}...), a
value hook prints its values (\code{echo}, one per line), an environment
hook calls the helpers \code{add-to-var}, \code{set-var}... and a command
hook is Bash code:

\begin{lstlisting}
function lcms2-vcs()
{
	echo default
	echo none
	echo git
	echo http://github.com/mm2/Little-CMS
}

function lcms2-env()
{
	local PREFIX=$1
	add-to-var PKG_CONFIG_PATH $PREFIX/lib/pkgconfig
}

function lcms2-build()
{
	local PREFIX=$1
	local TARGET=$2
	local VARIANT=$3
	make -j$SCBI_JOBS
}
\end{lstlisting}

The YAML equivalents of the Bash constructs:

\begin{description}
	\item[\code{inherit-plugin [options] <name>}] the key \code{inherit} (\seeref{inheritance}).
	\item[\code{with-variant native <packages> \ddash{}env ...}] the key \code{with-variants} (\seeref{native variant}).
	\item[\code{get-config-options OPTIONS \$PREFIX \$TARGET \$VARIANT}] \code{\$(config-options)} or \code{OPTIONS = config-options} (\seeref{get config options}).
	\item[\code{\$(get-build-type <kind> <default>)}] the same function (\seeref{yaml-functions}).
	\item[\code{check-tool}, \code{check-tools}, \code{command -v}] \code{command-path}.
	\item[\code{get-module-version}, \code{check-module-version}] \code{\$(get-version <plug-in>)}, \code{version(<plug-in>)} in conditions, \code{check-versions}.
	\item[\code{scbi-store-get-key}, \code{scbi-store-set-key}] \code{\$(store-key <key>)}, the \code{scbi store} sub-command.
	\item[\code{cp -r}, \code{rm -f}, \code{rm -fr}] the built-in commands \code{copy}, \code{delete} and \code{delete-tree}.
	\item[\code{\$(command args)}] \code{\$(output command args)}.
	\item[\code{scbi-rewrite-vcs}, \code{scbi-rewrite-archive}, \code{proxy-<name>}, \code{module-final-step}, a redefinition of \code{define-var}] the functions \code{rewrite-vcs}, \code{rewrite-archive}, \code{proxy}, \code{module-final-step} and \code{define-var} of the environment file (\seeref{env-files}).
	\item[\code{call-variant-hooks}] no equivalent: the hooks of the variants are selected by the qualifiers (\seeref{yaml-plugin}).
\end{description}

\subsection{Calling variant hooks (Bash plug-ins)}
\label{call variant hooks}
\index{call-variant-hooks}\index{helpers!call-variant-hooks}

In a Bash plug-in, the routine \code{call-variant-hooks} called the hooks of a module for each of its variants:

\begin{lstlisting}
call-variant-hooks hname $PREFIX $TARGET $VARIANT \
    [$P1 $P2...]
\end{lstlisting}

calls the hooks of the current plug-in (\code{<plugin>}) named as below, with the arguments \code{\$PREFIX}, \code{\$TARGET}, \code{\$VARIANT} and the optional parameters \code{\$P<n>}:

\begin{lstlisting}
   <plugin>-<variant>-hname
\end{lstlisting}

for each variant \code{<variant>} of \code{\$VARIANT}. The YAML plug-ins
use the qualifiers of the cumulative hooks instead.

\subsection{Converting Bash plug-ins}
\label{bash-convert}

A Bash plug-in is converted with:

\cmd{python3 -m scbi.convert [\ddash{}check] [\ddash{}output-dir=<dir>] <plug-in>...}

Everything that cannot be expressed in the YAML format is reported and the
plug-in is not converted; it must be fixed first. This is the case for hook
parameters not matching the hook signature or values computed by arbitrary
shell code.

A hook of a variant which only calls the same hook of other variants (like
\code{c-darktable-all-depends} calling the \code{depends} hooks of the
\code{ai}, \code{hdr} and \code{jxl} variants) is converted into a
variant including other variants (\seeref{yaml-variants}), after checking
that the hooks selected are the same for every hook, variant and cross
mode; otherwise it is reported.

The converted plug-in is written as \file{<name>.yaml} next to the Bash
plug-in (or into the \ddash{}output-dir directory); with \ddash{}check
nothing is written. The exit status is 1 if a plug-in cannot be converted.

A Bash environment file is converted with:

\cmd{python3 -m scbi.envconvert .env-<name>}

which writes \file{.env-<name>.yaml}. Its settings are converted to
\code{vars} (\code{\$(command)} becomes \code{\$(output command)}) and the
inclusion of another environment file (\code{source
\$\{SCBI\_ENV\_DIR\}/.env-<x>}) to \code{inherit}. The functions it
defines, the commands and the values using pipes are reported, to be
converted by hand to the functions of the environment files
(\seeref{env-files}); the file is then not written. The Python
environment files of the first versions of the Python driver are not
read any more: they are rewritten in YAML.
